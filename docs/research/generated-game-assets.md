# Google can draw the art, Node makes it a sprite

Google's image lineup in October 2026 is a capable, cheap illustration engine with the best reference-image budget on the market (up to 14 reference images per call, $0.0336 per 1K image on `gemini-nano-banana-2.1`), but it has no alpha output, no mask input, no pixel-grid or seamless-tile mode, and no game-asset features of any kind, so every Google-generated asset needs a post-processing pass before it can go in a game ([Gemini API: Image generation](https://ai.google.dev/gemini-api/docs/image-generation); [Gemini API: Pricing](https://ai.google.dev/gemini-api/docs/pricing)). Three competitors output an alpha channel natively (OpenAI gpt-image-2.5, Ideogram 4.x, Leonardo), but measured output from the OpenAI preview had opaque pixels at alpha 252 to 254 with grey halos, so a cleanup pass is needed with them too ([OpenAI community thread](https://community.openai.com/t/transparent-backgrounds-are-now-available-in-preview-for-gpt-image-2-in-the-api/1391541)). Only the pixel-art-specific tools, Retro Diffusion and PixelLab, output on a true pixel grid, with palette lock, seamless tiles, tilesets with two-material transitions, 4- and 8-direction rotation, and skeleton-driven animation, at $0.03 to $0.25 per asset or $12 to $50 a month ([Retro-Diffusion/api-examples](https://github.com/Retro-Diffusion/api-examples); [PixelLab OpenAPI](https://api.pixellab.ai/v1/openapi.json)). A headless Node pipeline with no GPU covers everything the practitioner reports needed (chroma key, defringe, trim, grid detection, nearest-neighbour or k-means downscale, palette quantization, content-aware slicing, atlas packing) using `sharp`, `image-q` and `free-tex-packer-core`, with hosted background removal available for well under a cent per image when keying is not enough. A first complete asset set costs tens of dollars, not hundreds. Legally, raw generations are unprotectable in the US under the Copyright Office's January 2025 position (left intact when the Supreme Court declined Thaler on March 2, 2026), the Gemini API gives no IP indemnity while the same models through Google's Agent Platform do, and both Steam and itch.io require disclosure of shipped AI content. What still does not work well, from every independent report found: holding one character's identity and proportions across a directional sheet, seamless tiling, uniform pixel density across dozens of independently generated props, and any tool that emits a labelled autotile set. The recommendation is to run a small set of experiments with a Gemini key plus a Retro Diffusion balance before committing to an art style, because the style decision (pixel art versus painted top-down) decides which of the two candidate pipelines below is right.

How to read this report: statements from vendor documentation and terms are marked as documented facts with a link. Claims from a vendor's own marketing or blog are marked "(vendor claim)". Developer write-ups are marked by name. Conclusions I drew from the evidence rather than read in a source are marked "(inference)". Prices are USD list prices on the date the source was read, October 22, 2026, unless stated.

## Google ships five Nano Banana models and no Imagen

Every Imagen model is gone or going. The Gemini API changelog records the Imagen 4 GA models shut down on August 17, 2026, and the Vertex release notes deprecate every Imagen generation, editing and capability endpoint (including the mask-based `imagen-3.0-capability-001/002` and `imagen-product-recontext`) with a June 30, 2026 migration deadline; Imagen subject and style tuning was removed on December 31, 2025 ([Gemini API changelog](https://ai.google.dev/gemini-api/docs/changelog); [Vertex AI release notes](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/release-notes)). What remains is the Gemini-native "Nano Banana" family. Note that Google renamed Vertex AI to "Gemini Enterprise Agent Platform" during 2026; older sources say Vertex, newer ones say Agent Platform, and they are the same product line ([Vertex AI deprecations](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/deprecations)).

The two Google pages disagree on 2.1's character limit (5 versus 4) and on 4K token count (2,520 versus 3,780), so budget with the larger numbers ([Gemini API: gemini-nano-banana-2.1](https://ai.google.dev/gemini-api/docs/models/gemini-nano-banana-2.1)).

Reference images are ordinary image parts in the request. There is no named "reference" or "subject id" parameter; the prompt text says what each image is for, for example "the character in image 1, walking left" ([Gemini API: Image generation](https://ai.google.dev/gemini-api/docs/image-generation)). Each input image costs **1,120 tokens on 2.1**, so a 14-reference request adds about $0.024 of input ([Agent Platform: Nano Banana 2.1](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/nano-banana-2-1)). The limit table hints at a split: Pro accepts style references but lists no character slots, while 2.1 accepts characters but no style references. That suggests Pro for locking a whole set's look and 2.1 for locking a specific character's identity, but this is an inference from the limit table, not a benchmark. Nothing Google publishes measures consistency across many calls. The one detailed developer report, Ben Hoyle's March 2026 run of about 74 sprites on Nano Banana Pro, says the model "was good at keeping a cartoon style across a sheet and mostly kept character identity across poses" but "did not reliably keep exact proportions across separate generation calls," and it "did not space sprites in a uniform grid, even when asked" ([roboticape.com](https://roboticape.com/2026/03/07/generating-game-sprites-with-gemini-image-generation-nano-banana-pro-lessons-learned/)). He recommends one character per sheet and sheets of 3 to 6 items per row, 2 to 3 rows.

Google has no transparency. The output `mime_type` options are JPEG or PNG, the docs never mention alpha, and Google's own sticker prompt template ends with "The background must be white" ([Gemini API: Image generation](https://ai.google.dev/gemini-api/docs/image-generation)). Hoyle found that asking for a transparent background produced painted checkerboards or flat white and black backgrounds. Magenta and black keys failed because dark outlines matched the key and anti-aliasing blended key colour into edges. What worked was a solid `#00FF00` background plus "a clean white outline/border 2-3 pixels wide around every sprite in every frame," then HSV keying (hue within 22 degrees of 120, saturation above 0.3, value above 0.3), and he calls the white-outline line "the most important single line" in the prompt ([roboticape.com](https://roboticape.com/2026/03/07/generating-game-sprites-with-gemini-image-generation-nano-banana-pro-lessons-learned/)). Google's own segmentation and matting products were the deprecated Imagen capability models, and nothing replaced them. Third parties fill the gap: Replicate hosts `jide/nano-banana-2-transparent`, which renders on white and on black and derives alpha from the pair, and `jide/nano-banana-2-bg-remove` ([Replicate](https://replicate.com/jide/nano-banana-2-transparent)).

Editing is instruction-only. Google calls it "inpainting (semantic masking)": you send the image plus "change only X, keep everything else exactly the same." There is no binary mask parameter, outpainting is not covered, and third-party pages claiming "mask-based editing" for Nano Banana describe community ComfyUI nodes, not an API field ([Gemini API: Image generation](https://ai.google.dev/gemini-api/docs/image-generation)). Every edit is a full re-render at the model's output size, so an "edit" of a 32x32 sprite is a resynthesis at 1024x1024 that must be re-snapped afterwards (inference). Gemini 3 image models always think and this cannot be turned off. Thought images are not charged ([Gemini API: Image generation](https://ai.google.dev/gemini-api/docs/image-generation)).

The pixel grid is the other missing feature. The smallest output is 512px, and only on the deprecated 3.1 Flash Image; 2.1 and Lite start at 1K, where 1:1 is 1024x1024 and 4:1 is 2048x512 ([Gemini API: Image generation](https://ai.google.dev/gemini-api/docs/image-generation)). SpriteCook's test of Nano Banana 2 found "some pixels at 6px and others at 7px, with sub-pixel noise everywhere," colours bleeding across edges, and that the model "ignores or inconsistently follows canvas sizes such as 32x32 or 64x64"; their recipe is to generate at full resolution, detect the intended grid, resample one logical pixel per output pixel, then reduce the palette (vendor blog) ([spritecook.ai](https://www.spritecook.ai/blog/nanobanana-pixel-art-for-games)). Seamless tiling is not a feature, and a tileset vendor reports visible seams even with detailed prompts ([sorceress.games](https://sorceress.games/blog/ai-tileset-generator-game-ready-tilesets-from-a-prompt)). A 1024x1024 render is a natural 16x upscale of a 64x64 logical canvas, which is a 4x4 block of 16-pixel tiles; that is the obvious generation unit for a Stardew-like grid (inference).

Access is straightforward from Node. `npm install @google/genai` needs Node 20+ and should be pinned below 3.0.0; a Gemini API key goes in `GOOGLE_API_KEY`, or `enterprise: true` with a Cloud project and location selects the Agent Platform ([js-genai README](https://github.com/googleapis/js-genai/blob/main/README.md)). The docs now lead with the Interactions API: `ai.interactions.create({ model, input: [text part, image parts...], response_format: { type: "image", mime_type: "image/png", aspect_ratio: "1:1", image_size: "1K" } })`, with results read by iterating `interaction.steps` for `content_block.type === "image"` and `previous_interaction_id` for multi-turn edits; `image_size` must be uppercase ([Gemini API: Image generation](https://ai.google.dev/gemini-api/docs/image-generation)). Batch runs at **50% of standard cost with a 24-hour target turnaround** ([Gemini API: Batch API](https://ai.google.dev/gemini-api/docs/batch-api)). Per-model rate limits are shown only in AI Studio after login. The public page gives spend caps of $10, $50 and $200 per ten minutes for tiers 1 to 3 ([Gemini API: Rate limits](https://ai.google.dev/gemini-api/docs/rate-limits)). There is no free tier for image generation in the API. The AI Studio UI is free ([Gemini API: Pricing](https://ai.google.dev/gemini-api/docs/pricing)). All images carry a SynthID watermark, and the Agent Platform adds C2PA content credentials ([Agent Platform: Nano Banana 2.1](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/nano-banana-2-1)). Safety blocks can arrive after generation as a `FinishReason` such as `IMAGE_SAFETY`, so the pipeline must check finish reasons, not just HTTP status; violence is a filtered category and there is no documented game-art carve-out ([Vertex: Gemini image responsible AI](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/multimodal/gemini-image-responsible-ai)).

## Three rivals output alpha, none output clean alpha

Among general-purpose APIs, transparency at generation time exists in exactly three places. OpenAI's `background: "transparent"` is GA on `gpt-image-2.5-sunburst` and `gpt-image-2.5-flare` and in preview on `gpt-image-2` (announced August 20, 2026); output must be PNG or WebP ([OpenAI API reference, images](https://developers.openai.com/api/reference/cli/resources/images/index.md)). Ideogram has dedicated `ideogram-4-transparent` and `ideogram-3-transparent` endpoints that deliver "PNGs with alpha," plus a `background: transparent` field on Ideogram 4.5 ([Ideogram 4.0 transparent](https://developer.ideogram.ai/v2/api-reference/images/generate/ideogram-4-transparent.md); [Ideogram 4.5 generate](https://developer.ideogram.ai/v2/api-reference/images/generate/ideogram-4-5.md)). Leonardo's `transparency: "foreground_only"` works only with SDXL and SD1.5-era models ([Leonardo docs](https://docs.leonardo.ai/docs/generate-images-using-transparency)). Recraft, Stability, Black Forest Labs (FLUX), Adobe Firefly and Midjourney have none. Recraft and Stability sell a removal call at $0.01 and $0.05 ([Recraft llms-full.txt](https://www.recraft.ai/llms-full.txt); [Stability pricing](https://docs.stability.ai/pricing)).

Native alpha is still dirty alpha. Forum measurements on the gpt-image-2 preview found opaque regions at **alpha 252 to 254 rather than 255**, a thin grey border outside the alpha, white halos on light-coloured subjects, and drop shadows carrying alpha; one user's edit of a transparent input lost transparency in the output ([OpenAI community thread](https://community.openai.com/t/transparent-backgrounds-are-now-available-in-preview-for-gpt-image-2-in-the-api/1391541)). Recraft users report "a visible edge halo/alpha fringe despite prompts requesting no halo" ([Recraft feedback](https://feedback.recraft.ai/bug-reports)). On the keying side, one vendor measured that after keying out `#FF00FF`, about 0.78% of visible pixels still carried magenta across six assets, rising to 2.47% on a thin sword, concentrated in a one-pixel rim (vendor measurement) ([Rangy](https://rangy.ai/blog/ai-game-assets)). The conclusion is the same for every provider: budget one deterministic alpha pass that clips alpha at or above about 250 to 255, un-mixes or erodes a one-pixel rim, and for pixel art thresholds alpha to 0 or 255 (inference from the measurements above and from pixel-art tool guidance at [sprite-ai.art](https://www.sprite-ai.art/tools/sharpen-edges)).

On reference conditioning, Google is competitive or ahead on count. gpt-image edits take up to 16 images, FLUX.2 [pro] up to 8, Ideogram 4.5 up to 5, Recraft style references up to 10, and Google 14 ([OpenAI API reference](https://developers.openai.com/api/reference/cli/resources/images/index.md); [BFL help](https://help.bfl.ai/articles/7424166364-wip-welcome-to-the-forest)). No provider publishes a controlled measurement of identity drift across dozens of generations; the only numbers found ("94.7% accuracy," "98% identity retention" for FLUX Kontext) cite no method and should be ignored ([G2 listing](https://ai.g2.com/marketplace/tools/flux-kontext-2025-10-29)). Two things rivals have that Google lacks: a palette parameter (Ideogram 3.0's `color_palette`) and a fine-tuning path. Hosted LoRA training for FLUX.1 costs **$0.005 per step on fal, about $2.40 per 1,000 steps**, and Replicate's fast trainer finishes "under 2 minutes" for "under $2" ([fal turbo trainer](https://fal.ai/models/fal-ai/turbo-flux-trainer); [Replicate changelog](https://replicate.com/changelog/2025-05-23-faster-flux-trainer)). FLUX.2 [dev] training is far pricier (fal's example is $47.46 for 1,000 steps) and its weights are non-commercial, while FLUX.2 klein-4B is Apache 2.0 and trains for about $9.71 ([fal flux-2-trainer-v2](https://fal.ai/models/fal-ai/flux-2-trainer-v2/edit); [fal klein 4B trainer](https://fal.ai/models/fal-ai/flux-2-klein-4b-base-trainer/edit)). One practitioner ranks consistency as LoRA, then reference images, then re-prompting, calling references "less tight than a fine-tune or LoRA but more stable than re-prompting from text" (vendor) ([AgentBrush](https://agentbrush.dev/blog/2d-game-asset-generation)). Google removed its Imagen subject and style tuning and offers no replacement ([Vertex AI release notes](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/release-notes)).

Background removal without a GPU is cheap and plentiful. Replicate's rembg and BiRefNet listings run **$0.0003 to $0.026 per image** depending on hardware, fal hosts BiRefNet v2 with a Node client (`fal.subscribe("fal-ai/birefnet/v2", ...)`), a July 2026 blog puts Bria RMBG-2.0 on fal at $0.018, and Recraft's `removeBackground` is $0.01 ([ilkerc/rembg](https://replicate.com/ilkerc/rembg); [men1scus/birefnet](https://replicate.com/men1scus/birefnet); [fal BiRefNet v2](https://fal.ai/models/fal-ai/birefnet/v2/llms.txt); [aireiter](https://aireiter.com/blog/best-background-removal-api)). No source tested any of these on pixel art or sub-64-pixel sprites. For sprites that will be downscaled to a grid, matting quality matters less than the deterministic threshold pass afterwards, so a sub-cent rembg endpoint or a plain chroma key in `sharp` is adequate; BiRefNet "Matting" or "Heavy" only earns its cost on painted assets kept at full resolution (inference).

One access note: fal.ai hosts Google's `nano-banana-pro` ($0.15 per image) and `nano-banana-2` alongside gpt-image-2, FLUX.2, Ideogram 4 and BiRefNet behind one key, and Ideogram's own v2 API proxies gpt-image-2/2.5 and Nano Banana 2 / 2.1 / Pro ([fal pricing](https://fal.ai/pricing); [Ideogram v2 docs index](https://developer.ideogram.ai/v2/llms.txt)). So a direct Gemini key is the cheapest route to Google's models, but a single fal or Ideogram key could cover a cross-provider experiment without three separate accounts.

## Pixel-art tools add the grid, the tileset and the skeleton

Two tools output on a true pixel grid and have real HTTP APIs usable from Node. Retro Diffusion (Astropulse LLC) runs on a prepaid USD balance with no subscription: `POST /v2/inferences` with an `X-RD-Token` header, then poll the task until it succeeds ([Retro-Diffusion/api-examples](https://github.com/Retro-Diffusion/api-examples)). Request fields cover most of what a sprite pipeline wants at generation time: `width`/`height` from 12 to 512, `prompt_style` (which also selects the model), `input_image` with `strength` for image-to-image, `reference_images` (up to 9, RD Pro styles only), `input_palette` as a palette image, `remove_bg`, `tile_x`/`tile_y` for seamless output, `frames_duration` and `return_spritesheet` for animations, `upscale_output_factor` (default 1, so output is native pixels), `check_cost` for a free dry run, and `Idempotency-Key`. Prices are flat per image at any size: `rd_fast` $0.03, `rd_plus` and `rd_mini` $0.06, `rd_pro` $0.18, single tiles $0.06, a full tileset $0.10, animations $0.07 (`8_dir_rotation` $0.25, `rotate` $0.10), inpainting and `seam_tiling` $0.18, `background_remover` $0.01, and failed generations are refunded ([Retro-Diffusion/api-examples](https://github.com/Retro-Diffusion/api-examples)). Scenario's documentation of the same models says RD Plus is "trained at native resolutions of 256 x 256 pixels (or below)," RD Tile fixes some styles at 32x32 "classic RPG tiles" and has a "tileset advanced" mode that blends two prompts or references (stone and moss) with "seamless transitions" between materials, and RD Animation makes 4-direction walk cycles that "may be limited to 48x48" with low frame counts, where reference images guide design but are not starting frames ([Scenario help: Retro Diffusion Models](https://help.scenario.com/en/articles/retro-diffusion-models-the-essentials/)). Astropulse states the model was "trained on licensed assets from Astropulse and other pixel artists with their consent" and that outputs "are owned by whoever creates them (you)"; this is the only such provenance claim among the pixel tools and it is a vendor statement without independent audit ([astropulse.itch.io](https://astropulse.itch.io/retrodiffusionai)).

PixelLab is subscription-based ($12 a month for 2,000 generations, $24 with priority and 400x400 output, $50 for 10,000, per a September 2026 third-party table; the official pricing widget did not render) and exposes an OpenAPI-documented REST API plus a remote MCP server at `https://api.pixellab.ai/mcp` ([Cinevva comparison](https://app.cinevva.com/guides/ai-pixel-art-generators); [PixelLab docs](https://www.pixellab.ai/docs/ways-to-use-pixellab)). Its distinctive endpoints are `animate-with-skeleton` (a `reference_image` plus exactly three frames of labelled keypoints, views side / low top-down / high top-down, eight compass directions), `estimate-skeleton` (keypoints from an existing sprite), `rotate` (turn a south-facing sprite to another direction), `inpaint`, and the generators `generate-image-pixflux` (16 to 400 px per side, `no_background`, `color_image` forced palette, `view`, `direction`) and `generate-image-bitforge` (16 to 200 px, `style_image` with `style_strength`, mask inpainting) ([PixelLab OpenAPI](https://api.pixellab.ai/v1/openapi.json)). Cinevva calls it "the only one that treats a sprite as a skeleton you can pose and rotate rather than a picture" (vendor-published comparison). The map and tileset tools appear in the UI but have no fields in the public OpenAPI spec, so tilesets from PixelLab are not scriptable today ([PixelLab docs](https://www.pixellab.ai/docs/ways-to-use-pixellab)).

Independent hands-on reviews of PixelLab or Retro Diffusion output from 2025 to 2026 were essentially absent from search results. The quality evidence is vendor material plus devlogs.

The non-AI alternative for walk cycles deserves a line. The Universal LPC Spritesheet Character Generator composes layered 64x64 character sheets (walk, slash, thrust, spellcast, shoot, hurt, plus run, jump and climb in the expanded set) from JSON layer definitions and PNGs; it runs on Node 22.19+, has no official CLI, but a Rust CLI (`lpcg`) already composites the same sheets headlessly, and a Node script with `sharp.composite()` over the `spritesheets/` directory would reproduce it ([LPC generator](https://github.com/LiberatedPixelCup/Universal-LPC-Spritesheet-Character-Generator); [lpcg crate](https://docs.rs/crate/lpcg/0.3.0)). It is the only route found with guaranteed frame-to-frame consistency and known licensing. The cost is that characters look like LPC characters and that the per-file CC-BY-SA and GPL items impose share-alike on derivatives and require a shipped credits list.

## A no-GPU Node pipeline is nine deterministic steps

Every tool the practitioner reports used is available as a pure-Node package or a CLI that runs on CPU. `sharp` provides resize kernels `nearest`, `lanczos3`, `mitchell` and others, `extract` for integer crops, `trim` with a `threshold` and `lineArt` option that reports `trimOffsetLeft`/`trimOffsetTop`, and `composite` for layering ([sharp resize docs](https://sharp.pixelplumbing.com/api-resize)). `image-q` (MIT, pure JS) provides palette quantizers (NeuQuant, RGBQuant, WuQuant), colour distances including CIEDE2000, and image quantizers from nearest-colour to Floyd-Steinberg and Riemersma ([ibezkrovnyi/image-quantization](https://github.com/ibezkrovnyi/image-quantization)). `free-tex-packer-core` (MIT) packs atlases with MaxRects and Optimal packers and exports JsonHash, Pixi, Phaser3, GodotAtlas, GodotTileset, Spine, Unity and custom Mustache templates, with `padding`, `extrude`, `allowTrim`, `allowRotation`, `powerOfTwo` and `detectIdentical` options ([odrick/free-tex-packer-core](https://github.com/odrick/free-tex-packer-core)). The best-regarded pixelization downscaler, Astropulse's K-Centroid (k-means for the dominant colour in each output cell), is MIT-licensed Lua for Aseprite, with Python ports in PixelOE and ComfyUI; no Node port exists, but the algorithm is small ([K-Centroid on itch](https://astropulse.itch.io/k-centroid); [PixelOE mirror](https://gitee.com/dkori/PixelOE)). Astropulse's `pixeldetector` estimates the scale factor of resized pixel art from horizontal and vertical pixel differences, which is the grid-detection step SpriteCook describes ([Astropulse GitHub](https://github.com/Astropulse/)).

The pipeline order below combines Hoyle's working steps, the sprite-forge write-up's acceptance checks, and the pixel-tool guidance. Steps 5 and 6 are skipped when the generator is grid-native (Retro Diffusion, PixelLab), because those return native pixels and accept a palette at generation time ([Retro-Diffusion/api-examples](https://github.com/Retro-Diffusion/api-examples)).

| Step | What it does | Node tool (no GPU) | Reject rule |
|---|---|---|---|
| 1. Generate | Prompt plus approved reference images; fixed canvas, aspect ratio, key colour and outline instruction | `@google/genai` Interactions API; or `fetch` to Retro Diffusion / PixelLab; Batch API for bulk | Missing image; `FinishReason` is `IMAGE_SAFETY` or similar |
| 2. Remove background | HSV chroma key on `#00FF00` (hue 120 plus or minus 22, S > 0.3, V > 0.3); or hosted rembg / BiRefNet via fal or Replicate; or native alpha from gpt-image / Ideogram | `sharp` raw pixel buffer; `@fal-ai/client` | Any of the four corners has alpha > 0; residual key-colour pixels above a per-asset percentage |
| 3. Normalize alpha | Clip alpha >= 250 to 255; un-mix or erode a 1-px rim; for pixel art threshold alpha at 128 to 0 or 255 | `sharp` raw loop | Any semi-transparent pixel remaining in pixel-art mode |
| 4. Trim and pad | Trim to bounding box, record offsets, pad to the tile multiple with the origin (feet) on a fixed baseline | `sharp.trim()`, `extend` | Bounding box drifts more than 1 px from the base sprite for a variant |
| 5. Detect grid and downscale | Estimate logical pixel size (autocorrelation of edge positions, or assume 16x for a 1024 render of a 64x64 canvas); k-means per cell (K-Centroid port), with `kernel: 'nearest'` as the cheap baseline | Own code on `sharp` buffers | Output dimensions differ from the expected canvas; mixed pixel densities on inspection |
| 6. Quantize | Map to the project's fixed palette, nearest colour, no dither | `image-q` NearestColor against a supplied palette | Colour count exceeds palette size; any colour not in palette |
| 7. Slice | Content-aware slicing by connected non-transparent regions and empty columns, not a uniform grid | Own code | Component count differs from the frames requested |
| 8. Pack | Fixed-grid sheets for animation; MaxRects atlas for props | `free-tex-packer-core` with `padding`/`extrude` 1 to 2 px, `allowRotation: false`, `allowTrim: false` for grid sheets | |
| 9. Record provenance | JSON sidecar per asset: model, prompt, reference ids, acceptance results, human edits | Own code | Missing sidecar blocks the build |

The slicing rule in step 7 is load-bearing. Hoyle found that uniform slicing merged two poses when one row had six sprites and the next had five, and that content-aware slicing found the correct eleven boundaries ([roboticape.com](https://roboticape.com/2026/03/07/generating-game-sprites-with-gemini-image-generation-nano-banana-pro-lessons-learned/)). The acceptance rules in steps 2 and 4 come from the sprite-forge pipeline, which rejected outputs whose four corners were not transparent and variants more than 1 px off the base, and which reported that "each regeneration shifts by a few pixels" and that hand-fixing frames had a "zero percent success rate," so its fixes were regenerations ([dev.to sprite-forge write-up](https://dev.to/quolu/how-i-made-an-ai-that-cant-draw-the-same-character-create-anime-model-sheets-19cn)). Hoyle's full pipeline ran under a minute for 74 sprites, with prompt writing (30 to 60 minutes), per-sheet generation (5 to 10 minutes each with one or two regenerations) and manual QA (30 to 60 minutes) making up a half day ([roboticape.com](https://roboticape.com/2026/03/07/generating-game-sprites-with-gemini-image-generation-nano-banana-pro-lessons-learned/)). Two smaller gotchas from the notes: a collision box that defaults to the full sprite canvas turns transparent padding into solid collision ([Makko blog](https://blog.makko.ai/pixel-art-hitboxes-ai-game-art-week-march-30/)), and TexturePacker-style "reduce border artifacts" fixes colour bleed under semi-transparent border pixels but does not remove them ([CodeAndWeb KB](https://www.codeandweb.com/texturepacker/knowledgebase/reduce-border-artifacts)).

Tilesets need an assembly step no tool provides. The target formats are well defined: Tiled's corner sets are 16 tiles for two terrains, edge sets 16, mixed sets 256, and the 47-tile blob is a reduced mixed set; Godot 4's terrain modes (Match Corners and Sides, Match Corners, Match Sides) map to the same bitmasks, with 47 valid combinations in the 3x3 minimal case because corners only count when both adjacent edges are set ([Tiled manual: Terrain](https://doc.mapeditor.org/en/stable/manual/terrain/); [Godot docs: Using TileSets](https://docs.godotengine.org/en/stable/tutorials/2d/using_tilesets.html)). No tool found emits a labelled blob set from a prompt. The workable path is to generate a seamless interior texture per terrain with `tile_x`/`tile_y`, one transition pair per terrain pair with RD Tile's advanced mode, then cut quadrant pieces and compose the 47 (or 16) variants with `sharp.composite`, writing Godot `.tres` peering bits and a Tiled wangset `.tsx`. This is an inference from the format definitions; no source demonstrates it end to end, and converters such as Blobsmith and TerrainForge exist as GUI tools if the export formats prove fiddly ([Blobsmith](https://blobsmith.itch.io/blobsmith); [TerrainForge](https://deforestpeg.itch.io/terrainforge)).

Buildings are simpler as one image than as tiles. Generating a cottage as a single image at a multiple of the tile size (for example 96x128 for a 3x4-tile footprint at 32 px) with background removal and then slicing keeps the 3/4 perspective consistent within the building; walls-as-tiles only pays off when buildings must be resizable (inference). Seasonal variants are more reliable as palette remaps of one base building than as regenerations, following the practice of standardising palette index order so swaps produce variants without redrawing ([Relish Games](https://relishgames.com/journal/pixel-art-pipelines-best-tools-for-2026/)); damage states need inpainting with the undamaged building as the init image. No source documented a validated season or damage workflow for a generated building.

## Licensing: you own nothing raw, and stores want a disclosure

The Gemini API Additional Terms (effective March 23, 2026) say Google "won't claim ownership" of generated content, that Google "may generate the same or similar content for others," that you are responsible for your use of the content, that paid-tier prompts and responses are not used to improve Google's products, and they contain no indemnification clause ([Gemini API Additional Terms](https://ai.google.dev/gemini-api/terms)). The Google Cloud "Generative AI Indemnified Services" page (modified July 20, 2026) lists the "Gemini Enterprise Agent Platform API (formerly Vertex AI API) used with generally available versions" of Gemini and Imagen as covered by Google's generated-output indemnity; the Gemini API and AI Studio are absent from that list ([Google Cloud indemnified services](https://cloud.google.com/terms/generative-ai-indemnified-services)). So the same `gemini-nano-banana-2.1` call is indemnified through a Cloud project and not through an AI Studio key. The conditions text of that indemnity (for example whether disabled safety filters void it) was not fetched. Uploaded reference images require rights clearance under the Prohibited Use Policy ([Gemini API: Image generation](https://ai.google.dev/gemini-api/docs/image-generation)). For comparison, OpenAI assigns its rights in output to the user and offers Copyright Shield to API customers, but with exclusions for outputs that were modified or combined with non-OpenAI products and for cases where safety features were disabled, which most sprite post-processing arguably triggers ([OpenAI Terms of Use](https://openai.com/policies/terms-of-use/); [Proskauer](https://www.proskauer.com/blog/openais-copyright-shield-broadens-user-ip-indemnities-for-ai-created-content)). Ideogram states "We do not claim ownership of your generated images, and you're free to use them for any purpose, including commercial use" ([Ideogram pricing](http://ideogram.ai/pricing/?pricing_tab=api)). Recraft grants full ownership only on paid plans. Free-plan outputs are public and not licensed for commercial use ([Recraft ownership docs](https://www.recraft.ai/docs/plans-and-billing/commercial-rights-and-ownership.md)). Astropulse says Retro Diffusion outputs belong to whoever creates them ([astropulse.itch.io](https://astropulse.itch.io/retrodiffusionai)). FLUX.2 klein-4B weights are Apache 2.0 while [dev] and klein-9B are non-commercial, which matters only if a LoRA path is chosen ([BFL help](https://help.bfl.ai/articles/7424166364-wip-welcome-to-the-forest)).

Ownership of raw generations is moot in the US because there is little to own. The Copyright Office's Part 2 report (January 29, 2025) holds that "prompts alone do not provide sufficient human control to make users of an AI system the authors of the output," while "the creative selection, coordination, or arrangement of material in the outputs, or creative modifications of the outputs" are protectable, and incorporating AI content into a larger work does not affect protection of the work as a whole ([Part 2 report PDF](https://www.copyright.gov/ai/Copyright-and-Artificial-Intelligence-Part-2-Copyrightability-Report.pdf)). The Supreme Court denied certiorari in Thaler v. Perlmutter on March 2, 2026, leaving the D.C. Circuit's human-authorship requirement in place ([Baker Donelson](https://www.bakerdonelson.com/supreme-court-denies-certiorari-in-thaler-v-perlmutter-ai-cannot-be-an-author-under-the-copyright-act)). Allen v. Perlmutter (the Midjourney image with over 600 prompts) finished summary-judgment briefing in January 2026 with no ruling found ([Law360](https://www.law360.com/technology/articles/2432068)). The practical reading (inference, not legal advice): individual generated sprites are unprotectable, the tileset layout, the curated set, hand-edited pixels and the game are protectable, and grid snapping alone is probably mechanical while hand repainting is not. The provenance sidecar in pipeline step 9 is what makes any later claim or disclosure possible.

Store policy is disclosure, not prohibition. Valve rewrote Steam's rules on January 16, 2026: development tools such as coding assistants need no disclosure, while "AI to generate content for the game" (in-game, store page, marketing) and "AI content generated during gameplay" must be disclosed, and the disclosure appears on the store page; roughly 8,000 titles disclosed in the first half of 2025 ([VGC, Jan 2026](https://www.videogameschronicle.com/news/valve-has-significantly-rewritten-steams-rules-for-how-developers-much-disclose-ai-use); [Steamworks Content Survey](https://partner.steamgames.com/doc/gettingstarted/contentsurvey)). itch.io requires an "AI Disclosure" tag, is "strictly enforcing disclosure for all game asset pages," and untagged asset pages "may result in delisting" ([itch.io quality guidelines](https://itch.io/docs/creators/quality-guidelines)). On mixing with open art: Kenney packs are CC0 and mix freely; LPC art is per-file CC0, CC-BY, CC-BY-SA, OGA-BY or GPL with a required shipped credits list, and CC-BY-SA or GPL items pull derivatives under the same licence ([Kenney Pixel Shmup](https://kenney-assets.itch.io/pixel-shmup); [LPC generator README](https://github.com/LiberatedPixelCup/Universal-LPC-Spritesheet-Character-Generator)). No legal source addresses whether AI output conditioned on a CC-BY-SA reference image is a derivative; treating it as share-alike is the safe assumption (inference).

## What still fails: identity, grids, seams, animation

The failure list is consistent across every independent report. Identity and proportion drift between separate calls: Hoyle's characters varied between sheets, the sprite-forge pipeline saw every regeneration shift by a few pixels, a visual-novel devlog needed "several hours of Photoshop cleanup to match outfits," and another removed its AI sprites because consistency edits "took too long" ([roboticape.com](https://roboticape.com/2026/03/07/generating-game-sprites-with-gemini-image-generation-nano-banana-pro-lessons-learned/); [dev.to](https://dev.to/quolu/how-i-made-an-ai-that-cant-draw-the-same-character-create-anime-model-sheets-19cn); [itch devlog](https://itch.io/devlog/507457/a-productive-week-another-ending-complete-and-some-sprite-work.amp); [itch devlog](https://rizvn.itch.io/deliidol/devlog/635116/removed-ai-cgs-and-sprites-images-that-were-removed-from-game)). No general model holds a pixel grid. Even the vendor selling a pixel-art generator says "AI cannot produce true pixel art" from general models because of irregular grids, anti-aliased edges and too many colours ([Rangy](https://rangy.ai/blog/ai-game-assets)). Tilesets are "the weakest category" with visible seams, and animation frames are "not mechanically consistent" (vendor reports at [Summer Engine](https://www.summerengine.com/blog/ai-2d-game-asset-generator) and [AgentBrush](https://agentbrush.dev/blog/2d-game-asset-generation)). Sprites below about 16x16 "look like downscaled illustration" ([AgentBrush](https://agentbrush.dev/blog/2d-game-asset-generation)). Palette locking by prompt is unreliable everywhere except through an explicit parameter (Ideogram 3.0, Retro Diffusion, PixelLab). Background removal leaves residue (one accepted sprite-forge image still had over 200,000 black residue pixels) and keyed edges leave a rim. No tool emits a labelled autotile set. Safety filters can block a cartoon brigand with a club, and the only mitigation on record is stylised wording and checking finish reasons (inference from [Gemini API: Safety settings](https://ai.google.dev/gemini-api/docs/safety-settings)).

Where the tools are credible, by the same evidence: single props, portraits and concept art at full resolution; short loops of 4 to 8 frames at 32 to 48 px from the pixel-native tools; style consistency across one sheet; palette-remapped variants of an approved base. The developers who shipped AI sprites in 2026 did it by over-generating, filtering with deterministic checks and never hand-fixing frames (inference from the devlogs above). Two evidence gaps are worth naming because they shape the experiments below: no source measured whether 512px output on 3.1 Flash Image gives a cleaner grid than 1K downsampled, and no source tested any background remover on pixel art.

## Conclusion

The research changes the question from "can Google generate my sprites" to "which stage of the pipeline is Google good at." Its models are the cheapest high-reference-count illustrators available and are well suited to concept art, portraits, props and whole-sheet style exploration, where a 1K painted image with a chroma key and a Node cleanup pass is exactly what is wanted. They are poorly suited to the parts of a Stardew-like asset set that must be mechanically consistent: directional walk cycles, autotiles and seamless terrain. Those are precisely what Retro Diffusion and PixelLab were built for, at prices that make running both vendors side by side trivial. The art-style decision therefore drives the tooling decision more than any model benchmark does: if the game commits to 16- or 32-pixel art, the pixel-native tools plus Google for non-grid work is the lower-risk path; if it adopts a painted or "hi-bit" top-down look where no grid snapping is needed, Google's models (or a native-alpha rival) carry more of the load and the pipeline shrinks to key, defringe, trim and pack.

Two implications follow for a project built text-first by a coding agent. First, the deterministic acceptance checks (corner alpha, bounding-box drift, palette membership, component count) are the real product of this work, because every report says the fix for a bad generation is another generation, and an agent can run that loop unattended only if the checks are mechanical. Second, the provenance sidecar is not optional: it is simultaneously the Steam disclosure record, the copyright-registration record for human edits, and the reproducibility record for a pipeline whose models get deprecated every few months (three Google image models changed status in 2026 alone).

## Recommended pipelines

Both candidates share the same Node skeleton (steps 2 to 9 above), the same acceptance checks and the same provenance sidecar. They differ in which generator sits at step 1 for which asset class.

**Pipeline A, pixel-native (recommended if the game commits to pixel art).**

1. Sprites, walk cycles, rotations: Retro Diffusion RD Animation (`four_angle_walking`, `8_dir_rotation`) and PixelLab `rotate` / `animate-with-skeleton`, with `input_palette` or `color_image` set to the project palette and `remove_bg` / `no_background` on. Output is native pixels. Skip downscale and quantize, keep the alpha threshold and the drift check.
2. Terrain and tiles: Retro Diffusion `tile_x`/`tile_y` for interiors, RD Tile "tileset advanced" for two-material transitions, then the Node blob assembler writes 47-tile sets plus Godot `.tres` and Tiled `.tsx`.
3. Buildings and props: Retro Diffusion `rd_plus` at tile-multiple sizes with `remove_bg`; seasons as palette remaps; damage via `inpainting`.
4. Portraits, concept sheets, UI illustrations, store art: `gemini-nano-banana-2.1` at 1K on `#00FF00` with the white-outline instruction, keyed in `sharp`, kept at full resolution.
5. Fallback for walk cycles if generated frames fail the drift check: LPC paper-doll bodies composited in Node, with the CC0 subset filtered through `CREDITS.csv` or the credits screen shipped.

**Pipeline B, generate large and snap (recommended if the style is painted or if pixel art is still undecided and you want one vendor).**

1. Everything from `gemini-nano-banana-2.1` at 1K (Pro for hard compositions and text), one approved reference per character or building passed on every call, fixed canvas and aspect ratio, `#00FF00` plus white outline.
2. Chroma key and defringe in `sharp`; hosted BiRefNet via fal for painted assets where keying leaves a rim.
3. For pixel art: grid detection, K-Centroid downscale, `image-q` quantize to the fixed palette, alpha threshold. For painted: skip, keep full resolution, pack.
4. Tiles: generate 4x4-tile blocks on a 64x64 logical canvas at 1024x1024, snap, test with an offset wrap, expect to hand-select or regenerate seams; or buy terrain from Retro Diffusion anyway, since tiling is where Google is weakest.
5. Use the Batch API for bulk runs (half price) and the online API for iterative edits via `previous_interaction_id`.

Use the Gemini API with an API key for the experiments. Move the same calls to the Agent Platform (Cloud project, `enterprise: true`) only if indemnity or C2PA credentials matter at ship time. The model IDs and SDK calls are the same.

## First experiments once a key is available

Each experiment is small enough to run in an afternoon and produces a number the pipeline can use. The Gemini key must be added as an environment secret first. None is present in the container today. Experiments 5 and 6 need a Retro Diffusion balance (no subscription; `check_cost` is free).

1. **Transparency recipe.** Generate 20 props on `gemini-nano-banana-2.1` at 1K with the `#00FF00` plus white-outline prompt, key them in `sharp`, and measure residual key pixels and corner alpha. Repeat 20 with a dark outline instead of white, and 20 with `#FF00FF`. Record the reject rate per recipe.
2. **Grid snap quality.** Prompt ten 64x64-logical pixel-art props at 1K on 2.1, run grid detection and K-Centroid versus nearest-neighbour, and count colours and mixed-density cells. Run the same ten on `gemini-3.1-flash-image` at 512px to answer the open question of whether the smaller output gives a cleaner grid.
3. **Reference-image drift.** Take one approved character render and request south, north, east and west standing poses in four separate calls with that image as a character reference on 2.1, then the same on Pro with it as a style reference. Measure bounding-box height and width per pose and distinctive-landmark survival (scarf, hat). This answers the 2.1-versus-Pro question from the limit table.
4. **Sheet versus single.** Request one 4x3 sheet of twelve poses versus twelve single-pose calls, same reference. Compare cost, content-aware slice success, and drift. Hoyle's data says the sheet wins on style and loses on grid spacing. Check that here.
5. **Pixel-native baseline.** Run the same character brief through Retro Diffusion `four_angle_walking` at 48x48 and `8_dir_rotation`, and ten props through `rd_plus` with `input_palette`. Compare directly against experiment 3's output at game scale.
6. **Tileset assembly.** Generate grass and dirt interiors with `tile_x`/`tile_y` and one grass-to-dirt transition with RD Tile advanced; write the blob assembler and load the result in Tiled or Godot to confirm the peering bits.
7. **Safety and filter behaviour.** Prompt a cartoon brigand with a club, a butcher with a cleaver and a hunter with a bow on 2.1; log finish reasons. This sets expectations before authoring a town's worth of NPC sprites.
8. **Removal fallback.** Run 20 keyed-but-rimmed outputs from experiment 1 through fal BiRefNet v2 and a sub-cent Replicate rembg endpoint; compare rim pixels after alpha threshold. No published test covers pixel art, so this fills a real gap.

## Open decisions

1. Art style: pixel art at 16 or 32 px, or a painted top-down look. This decides Pipeline A versus B and whether grid snapping exists at all.
2. Walk cycles: generated frames (Retro Diffusion or PixelLab), LPC paper-doll composites, or a hybrid where LPC bodies carry the cycle and generated art covers everything static.
3. Vendor posture: Gemini API key only, or Agent Platform for indemnity and C2PA; and whether a second vendor (Retro Diffusion, fal) is in scope from the start.
4. Palette: a fixed project palette of 16 to 32 colours chosen before generation (required for Pipeline A's palette lock and for quantization), or per-asset palettes with a later unification pass.
5. Tile grid: 16 px (Stardew-like) or 32 px (RD Tile's fixed "classic RPG" styles), and which autotile format (Godot terrain `.tres`, Tiled wangset, or the game's own JSON) the assembler targets.
6. Licensing posture, carried over from the engine research: CC0 only, LPC with share-alike and a credits screen, or generated assets you do not own, and how the provenance sidecar records human edits for disclosure.
7. Whether SynthID or C2PA metadata should be preserved on shipped assets (it almost certainly does not survive a 16x nearest-neighbour downscale, which is untested) or deliberately stripped and replaced by the project's own provenance record.
