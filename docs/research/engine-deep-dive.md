# Render on Canvas 2D, verify in Node

Keep the simulation in TypeScript, as already decided, and draw the first renderer on raw Canvas 2D behind a small backend interface, so the same drawing code runs in the browser and in Node through `@napi-rs/canvas` for pixel-exact snapshot tests. The renderer this game needs is small: layered tiles, one alpha group per inline building for roof hiding, Y-sorting of actors and tall props, interpolation between tile-arrival events, a camera that can follow anything, integer scaling, a few hundred sprites and a little UI. Every JavaScript option can do those things, and none needs shader filters for any of them, so the deciding question for a developer who cannot see the screen is whether the renderer's output can be checked without a browser. Only Canvas 2D passes that test today. In this container, `@napi-rs/canvas` 1.0.13 reproduced exact nearest-neighbour pixels with `imageSmoothingEnabled = false`, while PixiJS 8.22's experimental Canvas backend initialised and completed a render pass in Node but returned a black frame, one missing blit away from working. Phaser 4, Excalibur and every editor engine need a browser or an X server for any pixels at all. Unity would cost a GUI-minted Personal license, a 7.5 GB container image and an editor-in-the-loop content pipeline, and return nothing a 2D town needs over a hand-built page a hundredth the size. A Rust core would buy compiler-checked determinism and `insta`/`proptest`, but at a few hundred entities there is no performance case, the sim design is agreed in TypeScript, and the two-language boundary is a permanent cost; the right move is to shape the sim's public surface (step to a tick and return typed events, export snapshot bytes) so a Rust port stays possible later without touching the viewer. PixiJS v8 is the named fallback if the renderer ever needs WebGL (per-light shading, many thousands of sprites), and a one-week experiment at the start of the renderer step decides between them on evidence rather than taste.

Throughout, sentences with an inline link are backed by a source in the research notes under `docs/research/notes/engine2_*.md`. Sentences marked "Inference" are a reading of that evidence. Two results were produced by running code in this container and are marked as such; the PixiJS script is kept at `docs/research/notes/engine2_pixi_node_smoke.mjs`.

## The seam decides more than the engine: typed events out, nothing back in

Shipped deterministic games converge on one shape. The sim advances in integer ticks on its own cadence, the renderer reads sim output and never writes it, and wall-clock time and unseeded randomness are banned inside the sim. OpenFrontIO states the rules for its TypeScript core in writing: "The core MUST be fully deterministic with no external dependencies", "Any randomness must use seeded random number generators", and "The client does NOT handle game logic" ([OpenFrontIO architecture docs](https://mintlify.wiki/openfrontio/OpenFrontIO/development/architecture)). Its client runs the core in a Web Worker, renders with PixiJS, and receives a `GameUpdate` per turn ([same source](https://mintlify.wiki/openfrontio/OpenFrontIO/development/architecture)). Factorio runs update and render on separate threads and drops render frames rather than slowing the update, about 40 FPS at 60 UPS in the post's example ([FFF-70](https://factorio.com/blog/post/fff-70)). Dwarf Fortress draws one graphical frame per two computational ticks by default ([DF wiki: FPS](https://dwarffortresswiki.org/index.php/FPS)). Caves of Qud is a C# core hosted inside Unity ([Unity interview with Brian Bucklew](https://unity.com/resources/systems-driven-design-in-caves-of-qud)), and Oxygen Not Included keeps its element simulation in a native DLL under a Unity game ([Klei forums, snippet only](https://kleiforums.com/forums/topic/167593-simsimdll-multi-threaded-simulation/)). Inference: the two hosted-core examples show that the seam survives an engine change, which is the one property this project wants from its architecture if the renderer is ever swapped.

A discrete-event core already produces the right output. Each popped event is a typed fact ("actor 7 arrived at tile (12, 4) at tick 50,400"), which is OpenFrontIO's `GameUpdate` at finer granularity. The viewer subscribes to those events and owns all fractional math. Fiedler's fixed-timestep recipe maps directly: the renderer produces scaled real time, the sim consumes it by popping events whose tick is at or below the target, and the renderer interpolates between the previous and current states with the step count per frame capped so a stall "appears to slow under heavy load instead" of spiralling ([Gaffer On Games: Fix Your Timestep](https://gafferongames.com/post/fix_your_timestep/)). Inference: for this sim the per-actor presentation state is `{fromTile, toTile, departTick, arriveTick}` from the last movement event, drawn at `lerp(from, to, (nowTick - departTick) / (arriveTick - departTick))` with a fractional presentation clock, then floored to integer logical pixels. Flooring removes sub-pixel shimmer in every renderer, keeps browser and Node output identical, and leaves the sim integer-only, which protects determinism by construction. Pause, speed and "skip to morning" are then viewer-side choices of how much sim time to consume per real second; RimWorld treats its 1x/3x/6x/15x speeds that way and admits the machine may not keep up ([RimWorld wiki: Ticks](https://rimworldwiki.com/wiki/Ticks)), and OpenFrontIO scales its turn interval by replay speed with a backlog of up to 60 turns ([OpenFrontIO LocalServer.ts](https://github.com/openfrontio/OpenFrontIO/blob/main/src/client/LocalServer.ts)).

The sim does not need a Web Worker on day one, and it should not depend on shared memory at all. `SharedArrayBuffer` requires cross-origin isolation (COOP and COEP headers), without which the constructor is hidden and `postMessage` throws for shared buffers ([MDN: SharedArrayBuffer](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer)); static hosts such as itch.io do not set those headers by default (Inference). OpenFrontIO's single-player mode is the most reusable template: `LocalServer.ts` is a `setInterval` polling every 5 ms that ends a turn when real time passes the turn interval, batches intents into a `Turn`, stores a client hash every 100 turns, and on replay sends `desync` if the archived hash differs ([OpenFrontIO LocalServer.ts](https://github.com/openfrontio/OpenFrontIO/blob/main/src/client/LocalServer.ts)). Inference: run the sim on the main thread first, with its interface shaped as messages (`stepUntil(tick)` returning an event array, `snapshot()` returning bytes), so moving it into a worker later is a transport change and nothing else. Chrome stops `requestAnimationFrame` entirely for hidden tabs and throttles timers to once per second, then once per minute after five minutes hidden ([Chrome Developers: Timer throttling in Chrome 88](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)), so a single-player town should pause on `visibilitychange` rather than attempt a multi-minute catch-up burst (Inference).

Replay is the main test instrument, and the shipped practice is uniform. Factorio ran a mode that "computes a checksum of the whole map every tick, and the replay checks the same thing", then compared the two saves at the first divergent tick, where "the difference is usually tiny" ([FFF-47](https://factorio.com/blog/post/fff-47)). OpenTTD's `-d desync=2` validates caches every tick, replays `commands-out.log`, and triggers `NOT_REACHED` on a checksum mismatch; its periodic checksum is the RNG state and "does not give any indication on when the Desync happened" ([OpenTTD desync.md, jgrpp copy](https://git.blob42.xyz/Archives/OpenTTD-patches/src/branch/jgrpp/docs/desync.md)). All three projects require the same version or commit for replay ([OpenFrontIO README](https://github.com/openfrontio/OpenFrontIO); [Factorio 0.4.1](https://cf-www.factorio.com/blog/post/factorio-0-4-1-released)). General guidance adds per-subsystem hashes so a failure names the subsystem ([bugnet.io: debugging desyncs](https://bugnet.io/blog/how-to-debug-multiplayer-desync-issues-in-games)). Inference: the "golden day" test for this project is `{seed, contentVersion, inputLog}` plus a hash at every tick in tests (size does not matter there), with separate hashes for actors, places, the calendar, the RNG state and the pending event queue itself. Hashing the event queue is the discrete-event analogue of OpenTTD hashing the RNG: it is the cheapest value that changes when anything upstream diverges. Goldens are fixtures for a commit, regenerated on content changes rather than migrated.

## Canvas 2D is the only renderer whose output can be checked without a browser

The renderer requirements come straight from `decisions.md`: a unified exterior grid with inline ground floors and per-building roof hiding, scene swap for detached places, a camera separate from the avatar, pixel art at integer scale, keyboard and click-to-walk, interpolation between tile-arrival events, and a text view that the agent and Playwright can read. All four engines surveyed express roof hiding as "layer alpha = f(indoor)" and Y-sorting as a depth or zIndex key, and none needs filters for either (Inference from the four engines' documented APIs). Click-to-walk is `tile = floor((clientX / scale + camX) / tileSize)` in every option. So the differentiators are elsewhere: whether pixels can be produced in Node, how pixel-art placement is controlled, bundle weight, maintenance health, and how much of the frame loop the library insists on owning.

**Raw Canvas 2D** is the only option where the exact renderer code runs in Node. `@napi-rs/canvas` is a Skia binding with prebuilt N-API binaries and no system dependencies ([Brooooooklyn/canvas](https://github.com/Brooooooklyn/canvas)); its 1.0.0 release cited "about 11 million weekly downloads and a stable API" (vendor claim) ([v1.0.0 release](https://github.com/Brooooooklyn/canvas/releases/tag/v1.0.0)). Verified in this container with 1.0.13 on Node 22.22.0: a 2x2 red/blue checker scaled to 8x8 with `imageSmoothingEnabled = false` gave pixel (3,3) = `[255,0,0,255]`, (4,4) = `[0,0,255,255]` and (3,4) = `[0,0,0,0]`, while smoothing on gave blended values such as `[187,0,66,135]`. `OffscreenCanvas` is not exported (also verified). One caution: release 1.0.12 (2026-10-20) made about 30 changes "mostly aimed at matching Chrome", including font layout, `drawImage` sampling and gradient dithering ([releases](https://github.com/Brooooooklyn/canvas/releases)), so the package must be pinned and a bump is allowed to change baselines. node-canvas (Cairo) is at 3.2.3 with a 4.0 release candidate and needs system libraries ([Automattic/node-canvas releases](https://github.com/Automattic/node-canvas/releases)); it is the fallback, not the first choice. Inference, the renderer sketch: a `RenderBackend` interface over `createCanvas` and `drawImage`, implemented by the browser canvas and by `@napi-rs/canvas`; one offscreen canvas per 16x16-tile chunk per static layer, re-rasterised only when the sim changes a tile; per frame, clear, draw visible chunks at the integer camera offset, draw a Y-sorted array of `{y, draw}` entries for actors and tall props, draw roof chunks with `globalAlpha` per building, then UI. A 100x100-tile town at 16 px is 1600x1600 world pixels, and a 480x270 logical viewport shows about 30x20 tiles, so even without chunk caching the frame is a few hundred `drawImage` calls, far inside a 60 fps budget on any desktop browser (Inference; no external measurement was found). Integer scaling is CSS: canvas width `logicalW * k` with `k = floor(min(innerW / logicalW, innerH / logicalH))` and `image-rendering: pixelated`, the pattern melonJS 20.9.0 ships as `scaleRounding: "integer"` ([melonJS releases](https://github.com/melonjs/melonJS/releases)). The costs are real but bounded: Y-sort, camera, dirty tracking and text layout are yours, and WebGL-grade lighting is off the table.

**PixiJS v8** is the most actively maintained library here, and the developer's doubts about it are justified on exactly one axis, headless verification. It passed 500,000 weekly npm downloads in mid-2026, ships 25 agent skill files inside the package at `node_modules/pixi.js/skills/`, and accepts a renderer preference list such as `['webgl', 'canvas']` ([PixiJS Update, June 2026](https://pixijs.com/blog/june-2026)). The Canvas backend arrived in 8.16.0 as "experimental" and "doesn't cover every feature the GPU renderers support" ([PixiJS 8.16.0](https://pixijs.com/blog/8.16.0)). There is no first-party tilemap; `@pixi/tilemap` 5.0.2 has had no release since 2025-07-14, lists its texture limits as "Temporarily switched off", and shows no named maintainer ([pixijs-userland/tilemap](https://github.com/pixijs-userland/tilemap); [npm registry](https://registry.npmjs.org/@pixi/tilemap)), so a chunked renderer built from `cacheAsTexture()` containers is the safer plan ([Container guide](https://pixijs.com/8.x/guides/components/scene-objects/container)). Container alpha applies per sprite, so overlapping roof tiles would double-blend unless the roof container is cached to a texture first (Inference). Headless is the problem. The official `@pixi/node` repo has 12 commits, 49 stars, empty releases and needs `xvfb-run` on servers ([pixijs/node](https://github.com/pixijs/node)); the v8 `Environments` guide offers a custom `DOMAdapter` stub with placeholder bodies and no Node package ([Environments guide](https://pixijs.com/8.x/guides/concepts/environments)). Verified in this container with pixi.js 8.22.0 and `@napi-rs/canvas`: with an adapter and about 30 lines of DOM stubs, `autoDetectRenderer({ preference: 'canvas', roundPixels: true })` returned a canvas renderer in 9 ms, `renderer.render()` completed, and a 64x48 PNG was written, but every pixel was `[0,0,0,255]` including the background; after rendering, `renderer.canvasContext.activeContext !== rootContext`, so the renderer finished on an internal target and never presented to the root canvas. Pixi's own visual tests run in Electron through `@pixi/jest-electron`, with pixelmatch at threshold 0.2 and up to 100 differing pixels tolerated ([tester.ts](https://raw.githubusercontent.com/pixijs/pixijs/dev/tests/visual/tester.ts); [package.json](https://raw.githubusercontent.com/pixijs/pixijs/dev/package.json)). Inference: Pixi in Node is "possible with an afternoon of adapter work", which is a different thing from "supported", and the WebGL path in Node (`gl` + Xvfb + Mesa) is heavier and less deterministic ([stackgl/headless-gl](https://github.com/stackgl/headless-gl)). If Pixi is chosen, the plan is `Application.init({ antialias: false, resolution: 1, roundPixels: true })`, `scaleMode: 'nearest'` on every texture source, one container per map layer with `cacheAsTexture()` for static layers, a Y-sorted container for actors, and a UI render group.

**Phaser 4** is the heaviest and the most batteries-included. Version 4.0.0 shipped 2026-04-10 with a rebuilt render-node pipeline, a unified Filter system, `TilemapGPULayer` (a whole layer as one quad, orthographic only, one tileset, 4096x4096 max, WebGL only) and `SpriteGPULayer`; the Canvas renderer "should be considered deprecated" and almost all new features are WebGL-only ([Phaser 3 vs Phaser 4](https://phaser.io/news/2026/05/phaser-3-vs-phaser-4); [CHANGELOG v4.0.0](https://raw.githubusercontent.com/phaserjs/phaser/HEAD/changelog/v4/4.0/CHANGELOG-v4.0.0.md)). `pixelArt: true` sets `antialias` false and `roundPixels` true, but `roundPixels` "only applies to axis-aligned, unscaled objects" ([RenderConfig](https://docs.phaser.io/api-documentation/typedef/types-core#renderconfig); [CHANGELOG v4.0.0](https://raw.githubusercontent.com/phaserjs/phaser/HEAD/changelog/v4/4.0/CHANGELOG-v4.0.0.md)), so interpolated actors still need flooring by hand. `Phaser.HEADLESS` "creates neither a Canvas nor a WebGL renderer, yet it still absolutely relies on the DOM being present" and is "meant for unit testing, not for running Phaser on the server" ([Phaser.HEADLESS docs](https://newdocs.phaser.io/docs/3.85.2/focus/Phaser.HEADLESS)); Phaser's own 4.2.1 test helper boots a HEADLESS game and expects the environment to supply a DOM ([tests/helper.js](https://app.unpkg.com/phaser@4.2.1/files/tests/helper.js)). That gives logic-level assertions under jsdom ("roof alpha is 0 when the player is indoors") with zero pixels. The company is funded: Phaser Studio launched in December 2023 with $2M from Open Core Ventures ([OCV announcement](https://opencoreventures.com/blog/2023-12-phaser-studio-launched/)), and Phaser games reach Steam through Electron (Desktop Heroes, October 2025) and NW.js ([phaser.io](https://phaser.io/news/2026/04/desktop-heroes-phaser-electron-steam)). Inference: Phaser owns the loop through `Scene.update(time, delta)`, which puts a second clock between the sim and the screen, and its v3-era tutorials are partly stale, which Phaser itself acknowledges by shipping skill files. It is a viable choice and the worst fit of the serious options for this particular project.

**Excalibur** has the best CI rig to copy and the worst release risk. It is TypeScript-first with a first-party TileMap, Tiled and LDtk plugins, and a `pixelArt: true` preset that uses a sub-pixel sampler shader instead of flooring ([Pixel art docs](https://excaliburjs.com/docs/pixel-art)). Its visual tests run Vitest browser mode with Playwright, Chromium in windowed mode under Xvfb, `--use-gl=swiftshader` and `--force-device-scale-factor=1`, with `--disable-gpu` deliberately left off ([vitest.config.visual.ts](https://raw.githubusercontent.com/excaliburjs/Excalibur/main/src/spec/vitest.config.visual.ts)). Those are working flags for exactly the headless-Linux setup this project would need. But 0.32.0 (2025-12-23) is the last stable; the `next` tag is 0.33.0-alpha.247 after 133 alpha builds in 2026 ([npm registry](https://registry.npmjs.org/excalibur)), the README says "breaking changes **will occur**" ([excaliburjs/Excalibur](https://github.com/excaliburjs/Excalibur)), and "headless server support" sits undated on a roadmap whose last dated events are 2019 to 2022 ([issue #1161](https://github.com/excaliburjs/Excalibur/issues/1161)).

**melonJS** is the surprise of the survey and deserves a half-day spike only if Canvas 2D fails. Version 20.10.1 shipped 2026-10-21, one of 31 releases this year; it runs on WebGPU, WebGL 2 or Canvas2D with automatic fallback, has Tiled support up to 1.12 built in, added `scaleRounding: "integer"` in 20.9.0, and is maintained by AltByte in Singapore ([melonjs/melonJS](https://github.com/melonjs/melonJS); [releases](https://github.com/melonjs/melonJS/releases)). Its own skill file warns that "most published melonJS material predates 20.0 and its bootstrap no longer exists" ([melonJS SKILL.md](https://cdn.jsdelivr.net/npm/melonjs@20.5.0/skills/melonjs/SKILL.md)). Inference: it is the one engine-level path that could plausibly run under `@napi-rs/canvas`, and nothing found says anyone has tried. **Kaplay** is out: its stable line has been frozen since June 2025 and the 4000 alphas break APIs between builds ([kaplay CHANGELOG](https://raw.githubusercontent.com/kaplayjs/kaplay/master/CHANGELOG.md)).

## Editor engines cost the headless loop and return nothing a 2D town needs

The genre shipped mostly on Unity: Graveyard Keeper, Cult of the Lamb, Spiritfarer, Sun Haven and Oxygen Not Included are Unity titles ([Wikipedia: Graveyard Keeper](https://en.wikipedia.org/wiki/Graveyard_Keeper); [LevelUp on Cult of the Lamb](https://www.levelup.com/en/news/cult-of-the-lamb-threatens-to-disappear-due-to-unity); [Wikipedia: Spiritfarer](https://en.wikipedia.org/wiki/Spiritfarer); [Wikipedia: Sun Haven](https://en.wikipedia.org/wiki/Sun_Haven); [Wikipedia: ONI](https://en.wikipedia.org/wiki/Oxygen_Not_Included)), and Stardew itself is C# on XNA, migrated to MonoGame in 2021 ([Wikipedia: Stardew Valley](https://en.wikipedia.org/wiki/Stardew_Valley)). That record is an argument for keeping the sim independent of its host, not an argument for Unity. The engine moves in this genre were all forced by shipping constraints: Stardew's 4 GB mod ceiling on XNA, Vampire Survivors leaving Phaser for Unity in August 2023 for performance and platforms ([GamingOnLinux](http://www.gamingonlinux.com/2023/07/vampire-survivors-switching-to-new-game-engine-on-august-17)), Fields of Mistria leaving GameMaker for an in-house engine in July 2026 because the game "has outgrown its original engine" ([patch notes v0.16.2](https://www.fieldsofmistria.com/post/new-engine-v0-16-2-patch-notes)), and CrossCode reaching consoles only after its publisher built a JavaScript interpreter "in a cage" ([RPG Site](https://www.rpgsite.net/news/9249-deck13-and-radical-fish-games-provide-an-update-on-the-console-versions-of-crosscode)). None of those moves was about rendering features (Inference). Consoles are out of scope for this project, and desktop is cheap from a web stack.

**Unity** fails on the headless loop before it fails on anything else. Personal is free under $200K revenue and the Runtime Fee is dead ([Unity pricing updates](https://unity.com/products/pricing-updates)), but Personal licenses "have no serial number, so the command-line method doesn't apply" ([Managing your Unity license](https://docs.unity3d.com/cn/2023.2/Manual/ManagingYourUnityLicense.html)); the GameCI route is to log in to the Hub on a desktop, copy `Unity_lic.ulf` into a secret, and inject it with email and password ([GameCI activation](https://game.ci/docs/github/activation)), and Unity dropped manual `.alf` activation for Personal in August 2023 ([Unity Discussions](https://discussions.unity.com/t/unity-no-longer-supports-manual-activation-of-personal-licenses/926760)). The agent cannot bootstrap this on its own; a Pro serial at $2,310 per seat per year is the only fully headless activation ([Unity pricing updates](https://unity.com/products/pricing-updates)). The new standalone `unity` CLI (beta, Ubuntu 22.04+, glibc 2.34+) installs editors without the Hub and has `build`, `test`, `run` and `license` commands ([Unity CLI reference](https://docs.unity.com/en-us/unity-cli/unity-cli-reference.md)), and the `ubuntu-6000.3.27f1-webgl-3` GameCI image is 7.56 GB compressed ([Docker Hub API](https://hub.docker.com/v2/repositories/unityci/editor/tags?name=6000.3)). Content authoring is the second wall: the manual says "Avoid generating or editing Unity YAML files directly" ([UnityYAML](https://docs.unity3d.com/Manual/UnityYAML.html)), and Unity's own agent skills "control your open Unity Editor directly rather than editing scene and asset files by hand" ([Unity-Technologies/skills](https://github.com/Unity-Technologies/skills/blob/main/README.md)). The code-only route is C# Editor scripts run with `-batchmode -nographics -executeMethod`, with every referenced asset needing a GUID in a `.meta` file the agent also generates (Inference). `-nographics` "skips graphics device initialization" ([Editor command line arguments](https://docs.unity3d.com/Manual/EditorCommandLineArguments.html)), so no pixels come from the engine itself. The 2D feature set is complete and documented (Pixel Perfect Camera, URP 2D Renderer with a Custom Axis transparency sort for Y-ordering) ([2D Renderer Data](https://docs.unity3d.com/6/Documentation/Manual/urp/2DRendererData-overview.html); [Pixel Perfect Camera](https://docs.unity3d.com/Packages/com.unity.2d.pixel-perfect@5.0/manual/index.html)), and an empty Unity 6 Web build is about 3.3 to 5 MB ([Unity Discussions](https://discussions.unity.com/t/smallest-possible-webgl-build-size/917019)) or about 7.7 MB Brotli for a 2D project per one vendor-adjacent guide ([Cinevva](https://app.cinevva.com/guides/godot-vs-unity-web-games)). Inference: Unity would be the right host if the project needed console reach or Unity-only middleware. It needs neither, and the sim would still have to cross a `.jslib` bridge on web and a socket on desktop to reach it.

**Godot** is the one editor engine with a real editor-less loop, and it still costs the TypeScript toolchain. The editor binary is the CLI: `--headless` is "required on machines without GPU access, such as CI", and `--headless --import` then `--headless --export-release "Web" build/index.html` exports with templates installed for the exact version ([Command line tutorial](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)). `.tscn` and `.tres` are documented text formats an agent can write ([TSCN file format](https://docs.godotengine.org/en/stable/engine_details/file_formats/tscn.html)); a forum user reports Cline editing `.tscn` directly ([Godot forum](https://forum.godotengine.org/t/anyone-else-using-ai-to-create-mini-games-one-shot-prompt/99856)). GUT runs headless and exits 1 on failure with JUnit output ([GUT Command Line](https://gut.readthedocs.io/en/latest/Command-Line.html)); gdUnit4's .NET flavour forced an xvfb workaround "too slow" on GPU-less CI ([gdUnit4Net #350](https://github.com/godot-gdunit-labs/gdUnit4Net/discussions/350)). The documented pixel-art setup (viewport stretch, integer scale mode, `snap_2d_transforms_to_pixel`) and TileMapLayer with per-tile Y-sort origins cover the rendering needs ([Multiple resolutions](https://docs.godotengine.org/en/stable/tutorials/rendering/multiple_resolutions.html); [Using TileMaps](https://docs.godotengine.org/en/stable/tutorials/2d/using_tilemaps.html)). The web constraints are the issue. Web export runs only on the Compatibility (WebGL 2) renderer, "Godot 4 C# projects cannot currently be exported to the web" as of 4.7 ([Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html); [Godot forum, April 2026](https://forum.godotengine.org/t/is-there-an-update-on-exporting-c-projects-to-web/128821)), and godot-rust's wasm support "is still a work-in-progress and is not yet well tested" ([docs.rs godot](https://docs.rs/godot)). So on web the scripting language is GDScript, and a TypeScript sim reaches it through `JavaScriptBridge` in the browser and a different transport on desktop (Inference). An empty 4.6.2 web export is 6.33 MB uncompressed, and the test author says Godot's web loading times are long compared with Unity ([Godot-Web-LoadingTest](https://github.com/JohannesDeml/Godot-Web-LoadingTest)). Inference: Godot buys nothing a TS sim core cannot get from a TS renderer, and it costs the single-language Node test loop that `decisions.md` already assumes.

**Defold** is the only engine whose documented CI story is "no editor ever". `java -jar bob.jar --archive --platform wasm-web resolve build bundle` builds HTML5 without the editor, `--variant headless` builds a GPU-less engine for tests, and `--settings` overlays point CI at a test collection ([Bob manual](https://defold.com/manuals/bob/); [Automated testing manual](https://defold.com/manuals/automated-testing/)). The empty HTML5 build is 1.06 MB as of 1.12.4 ([Defold 1.12.4](https://defold.com/2026/05/04/Defold-1-12-4/)), roughly five times smaller than Godot's. The costs are Lua, a text-protobuf project format where each component's protobuf is escaped inside the parent's `data` string with no published spec ([Defold forum](https://forum.defold.com/t/whats-the-text-format-used-to-serialize-collections/72707/5)), native extensions built on `build.defold.com` by default ([Bob manual](https://defold.com/manuals/bob/)), and a small community. Its own testing manual says multimodal evaluation of screenshots "is a supplementary signal, not a replacement for deterministic checks" ([Automated testing manual](https://defold.com/manuals/automated-testing/)), which matches the conclusion of this report. Inference: if the project ever wanted an engine with an editor for a human collaborator, Defold is the one whose pipeline would not punish the agent. For this project it is a lateral move away from TypeScript.

**GameMaker** is the weakest fit on Linux: the manual documents the Igor CLI only for Windows and macOS hosts, licences come from an IDE login or access key, the only headless "test" mode passes if the runner survives a wait time ([Building via Command Line](https://raw.githubusercontent.com/YoYoGames/GameMaker-Manual/develop/Manual/contents/Settings/Building_via_Command_Line.htm)), and the Linux IDE is a 2021 beta with no newer news ([GamingOnLinux 2021](https://gamingonlinux.com/2021/09/gamemaker-studio-2-update-released-to-bring-forth-the-ubuntu-linux-editor-beta)). **Unreal** is disqualified by container cost alone (about 20 GB download and 60 GB installed for the prebuilt Linux editor) and by Paper2D being maintenance-only ([GamingOnLinux 2022](https://www.gamingonlinux.com/2022/07/unreal-engine-5-editor-quietly-gets-a-proper-linux-version/); [Unreal forums](https://forums.unrealengine.com/t/paper2d-dead/121200)).

## A Rust core buys compiler-checked determinism; the scale does not need it

Bevy as a whole-game engine is the wrong shape for this sim. It ships a new 0.x every four to five months (0.18 on 2026-01-13, 0.19 on 2026-06-19, 0.20 on 2026-10-08) ([Bevy news index](https://bevy.org/news/)), and the 0.19 to 0.20 migration guide has roughly 75 sections, including a sprite backend rebuilt on `Mesh2d` where draw order for sprites sharing a Z may change ([0.19 to 0.20 migration guide](https://bevy.org/learn/migration-guides/0-19-to-0-20/)). Bevy is a schedule of systems over archetype storage; nothing in 0.18 to 0.20 adds an event-queue runner, and 0.20's switch to weak ordering plus a `shuffle_seed` debug feature that randomises schedule order "to surface hidden ordering bugs" ([Bevy 0.20](https://bevy.org/news/bevy-0-20/)) is the project acknowledging the problem LogLog Games described when it left Rust gamedev: Bevy's scheduling "doesn't maintain consistent ordering even across frames", so ordering constraints have to be added anyway ([LogLog Games](https://loglog.games/blog/leaving-rust-gamedev/)). Inference: a deterministic DES should never live inside Bevy systems; at most Bevy would be a viewer reading snapshots, which is the same split as a wasm sim plus a TypeScript viewer with a heavier renderer. The pixel-art path is well-trodden (the first-party `pixel_grid_snap` example renders at 160x90 to a texture and upscales by an integer factor) ([pixel_grid_snap.rs](https://raw.githubusercontent.com/bevyengine/bevy/main/examples/2d/pixel_grid_snap.rs)) and `bevy_ecs_tilemap` tracks every release ([bevy_ecs_tilemap](https://github.com/StarArawn/bevy_ecs_tilemap)), but the only published wasm sizes are from July 2022 for a 3D project: 13.0 MB without `wasm-opt`, 4.8 MB with it ([examples README](https://raw.githubusercontent.com/bevyengine/bevy/main/examples/README.md)). The Foundation's August 2026 post says it is "drastically underfunded for our ambitions", that paid developers are about 54% below the intended baseline salary, and that the editor "has not landed upstream" ([Bevy's Sixth Birthday](https://bevy.org/news/bevys-sixth-birthday/)). Comfy, a Rust 2D engine from a maintainer with shipped games, was archived on 2025-11-24 after its author cited frequent breaking changes in wgpu, winit and egui ([darthdeus/comfy](https://github.com/darthdeus/comfy)). Macroquad is light and alive (0.4.16 on 2026-07-30) but wants to own the canvas through its own `mq_js_bundle.js` loader ([macroquad](https://github.com/not-fl3/macroquad); [crates.io](https://crates.io/api/v1/crates/macroquad/versions)), so it does not compose with a TypeScript viewer.

The split that is worth taking seriously is a Rust sim compiled to wasm under a TypeScript Canvas viewer. The toolchain is stable and maintained: wasm-bindgen 0.2.129 shipped 2026-09-25, and since 0.2.128 "the library and CLI versions must match", so both get pinned together ([wasm-bindgen releases](https://github.com/rustwasm/wasm-bindgen/releases)); wasm-pack lives under the wasm-bindgen org and is maintained by drager ([wasm-bindgen/wasm-pack](https://github.com/wasm-bindgen/wasm-pack)). `serde-wasm-bindgen` is the preferred bridge, with defaults that bite a TypeScript consumer (`HashMap` becomes a JS `Map`, `u64` beyond the safe-integer range fails, `None` becomes `undefined`) unless `Serializer::json_compatible()` is used ([serde-wasm-bindgen](https://github.com/RReverser/serde-wasm-bindgen)); `ts-rs` 12 generates `bindings/*.ts` from the same serde-annotated structs during `cargo test` ([ts-rs](https://github.com/Aleph-Alpha/ts-rs)). Small projects do exactly this: sandspiel builds its Rust sim with `wasm-pack` and glues it to a JavaScript renderer ([sandspiel](https://github.com/MaxBittker/sandspiel)); caputchin-replay-rs ships a freestanding wasm sim with no bindgen glue that "the renderer drives" live and a server replays identically ([caputchin-replay-rs](https://docs.rs/caputchin-replay-rs)). Inference: an event-stream API (`step_until(tick) -> Vec<SimEvent>`) is strictly better than a snapshot for a DES, because the event log is the replay file and the viewer's interpolation needs only deltas; a snapshot export remains for save/load and `insta` fixtures. With `u32` tick counters the `bigint` friction disappears.

What a Rust core actually buys is enforcement. Rust's `HashMap` randomises iteration order per `RandomState` by design ([std hash/random.rs](https://doc.rust-lang.org/stable/src/std/hash/random.rs.html)); the `rand` book marks `SmallRng` and `StdRng` as non-portable and warns that float distributions "may not be portable" across platforms ([rand reproducibility](https://rust-random.github.io/book/crate-reprod.html)); `insta` gives a reviewable YAML snapshot per scenario in one macro and `proptest` shrinks a failing event sequence to a minimal case ([insta.rs](https://insta.rs/); [proptest](https://proptest-rs.github.io/proptest/intro.html)). The traps are compile-visible or lintable, and integer-only sim math is natural with `i32` tiles and `u64` ticks. TypeScript has fewer traps and fewer guard rails: `Map` iteration is insertion-ordered by spec, every number is an IEEE double in every engine, vitest has file snapshots, and a seeded PRNG is ten lines, but nothing in the type system stops a `number` carrying a fraction into tile math or a stray `Date.now()` entering the sim (Inference). The anguis project's note applies to both languages: "Calling rand::thread_rng() will silently break the determinism check" ([anguis](https://zff.dev/ARKye03/anguis)). Wasm itself is deterministic except for NaN bit patterns and relaxed SIMD ([webassembly.org nondeterminism](https://www.webassembly.org/docs/nondeterminism/)), which integer-only state sidesteps entirely.

The agent-productivity evidence is mixed and not decisive for this project. SWE-bench Multilingual had Rust as the best-resolved language for SWE-agent plus Claude 3.7 Sonnet at 58% (25 of 43) with JavaScript and TypeScript combined near the bottom at 35% ([swebench.com/multilingual](https://swebench.com/multilingual)); Multi-SWE-bench had every non-Python language in the single digits to mid-teens, Rust topping at 15.9% and TypeScript at 11.6%, and states "TS and JS consistently yield the lowest resolved rates" ([Multi-SWE-bench](https://arxiv.org/html/2504.02605)). Both are Claude 3.5/3.7-era numbers; 2026 aggregate scores are two to three times higher with no per-language split ([llmrun](https://llmrun.dev/benchmark/swe-bench-multilingual?show=all)). Bun's 535,496-line Zig to Rust port by 64 Claude agents in 11 days is the strongest "compiler as reviewer" datapoint, and its criticism as "unreviewed slop" by Zig's creator is the strongest counterpoint ([Pragmatic Engineer](https://blog.pragmaticengineer.com/the-pulse-what-can-we-learn-from-buns-rapid-rust-rewrite-with-ai/); [devclass](https://www.devclass.com/ai-ml/2026/07/15/zig-creator-calls-buns-claude-rust-rewrite-unreviewed-slop/5271749)). Inference: the structural point outweighs the benchmarks. A sim crate with no graphics dependencies is the easy end of Rust (owned data, integers, no async), and the hard end (wgpu, winit, async) is the renderer, which this architecture leaves in TypeScript either way. Compile time is the cost that would matter to the agent's loop, and no measurement of a mid-size sim crate's `cargo check` or `wasm-pack build` time was found; LogLog's "8 seconds to compile 1,600 lines" of a serde-heavy module is the cautionary number ([LogLog Games](https://loglog.games/blog/leaving-rust-gamedev/)).

The other compiled stacks do not change the answer. Ebitengine 2.10 (2026-09-08) is the strongest non-Rust option: one-command wasm builds, pure-Go desktop builds, and a new host/guest "virtualization" mode "for automated testing by programs and AI agents", but "the host still needs a graphics environment" and "there is no software renderer for CI environments without a GPU" ([Ebitengine 2.10 notes](https://ebitengine.org/en/documents/2.10.html)). MonoGame "doesn't officially support web builds", with the feature request closed as not planned; the KNI fork adds a Blazor WebAssembly target of unquantified size ([Wavedash: MonoGame](https://docs.wavedash.com/engines/monogame.md); [Wavedash: KNI](https://docs.wavedash.com/engines/kni.md)). HaxeFlixel 6.x is active and HTML5-native but Haxe is a thin slice of any model's training data (Inference). Zig's Mach lists web as "soon" ([machengine.org](https://machengine.org/)), and Nim's main raylib wrapper was archived on 2026-08-07 ([planetis-m/naylib](https://github.com/planetis-m/naylib)).

Verdict on Rust: not now, and keep the door open. The sim design is agreed in TypeScript, the first four steps of the build order are text-only and unblocked, and the two-language cost (a second toolchain, generated types, opaque `RuntimeError: unreachable` panics without `console_error_panic_hook`) is permanent while the benefit at a few hundred entities is enforcement rather than speed. The door stays open if the sim package's public surface is exactly what a wasm module would export: `stepUntil(tick): SimEvent[]`, `snapshot(): Uint8Array`, `hash(): string`, with no DOM, no wall clock and no renderer types inside. Inference: the triggers that would justify a port are a native Steam build that cannot carry a browser, a server-side sim where Rust's guarantees matter more, or a run of determinism bugs in TypeScript that lint rules fail to catch.

## The agent sees text first, Skia second, Chromium third

Order the feedback channels by reliability, and spend the test budget in that order. First is a structured scene dump from the viewer, which is deterministic, diffable as text and needs no GPU. Second is a Node-side Canvas 2D render through Skia compared with a golden PNG at pixelmatch threshold 0, which is deterministic on one platform and needs no browser. Third is a Playwright screenshot of the real page, which catches integration bugs but is sensitive to the headless build, fonts, GPU path and animation timing. Fourth is the agent reading a PNG, useful for sanity and useless for regression. This ordering is an inference from the sources below, and it matches what agent-built projects report: a community skill for Claude Code web games tells the agent to expose a `render_game_to_text` state alongside screenshots and to rerun in headed mode if a headless WebGL capture looks wrong ([playbooks: develop-web-game, snippet only](https://playbooks.com/skills/davila7/claude-code-templates/develop-web-game)), and a Godot toolkit submitted in June 2026 opens with the claim that AI assistants "are blind in game engines" and ships an HTTP server that dumps the node hierarchy and captures the running game ([Godot Asset Library: A.I. Essentials Toolkit](https://www.godotengine.org/asset-library/asset/5264)). `decisions.md` already commits to text views from the sim; the viewer needs its own dump too, because "sprite didn't move" bugs live in the viewer. Inference: the viewer dump should carry the tick and presentation clock, the camera rect, every visible actor with id, tile, interpolated pixel position, facing, animation and frame, each layer's alpha (so "roof alpha is 0 when the followed actor is indoors" is one assertion), the UI widgets and their text, and a fixed-size ASCII window of the visible tiles with actor glyphs, exposed as `window.__scene()` in the browser and dumped beside the diff PNG on any failure.

Playwright is a workable third channel if its traps are planned for. Playwright 1.49 moved default headless runs to a separate `chromium-headless-shell` build and documented that "Screenshots are different" from the new headless mode, with the recommendation to update all screenshot expectations ([microsoft/playwright#33566](https://github.com/microsoft/playwright/issues/33566)); baselines "differ between browsers and platforms due to different rendering, fonts and more", and must be generated in the same environment as the comparison ([Playwright: Visual comparisons](https://playwright.dev/docs/test-snapshots)). `toHaveScreenshot` defaults to `threshold` 0.2 with `maxDiffPixels` unset, and `animations` disabled ([Playwright: PageAssertions](https://playwright.dev/docs/api/class-pageassertions)). For WebGL renderers the traps multiply. Chromium has deprecated automatic SwiftShader fallback; WebGL context creation now fails unless the browser is launched with `--enable-unsafe-swiftshader` ([Chromium SwiftShader docs](https://chromium.googlesource.com/chromium/src/+/main/docs/gpu/swiftshader.md)), one project reports `--disable-gpu` "breaks WebGL on Chrome 130+" (community, unverified) ([chrome-use commit](https://gitea.oimcloud.myaddr.tools/oimwiodev/chrome-use/src/commit/486e1b341fbe1e1a6bbf9bfc885ec0e2d34eb45c/cli)), and without a display "WebGL silently degrades to a flat 2D fallback: the screenshot still succeeds... and the output is wrong but plausible" ([Microlink: faster WebGL screenshots](https://microlink.io/blog/faster-webgl-screenshots)). WebGPU in headless browsers "fails silently: the page loads, the screenshot command succeeds, and the canvas is black" without setup ([agent-browser WebGPU guide](https://agent-browser.dev/webgpu)). A WebGL canvas read back after compositing is empty unless the context was created with `preserveDrawingBuffer: true` or the capture happens inside the render loop ([webgl2fundamentals: WebGL tips](https://webgl2fundamentals.org/webgl/lessons/webgl-tips.html)), and the test should wait on an application-level ready flag rather than a load event ([createit: headless Chrome WebGL](https://www.createit.com/?p=3319)). Inference: a Canvas 2D renderer avoids every item in this paragraph except the headless-shell note; that is the single strongest practical argument for it in a container without a GPU. The Playwright recipe either way: `deviceScaleFactor: 1`, a viewport that is an integer multiple of the logical size, a bitmap font loaded before the ready marker, `page.evaluate(() => window.__render(stateJSON))` to draw one deterministic frame with the ticker stopped, assert the active renderer before capture, `canvas.screenshot()` compared with `maxDiffPixels: 0` for Canvas 2D (Pixi's own suite tolerates 100 pixels for WebGL), and baselines generated only inside the CI container image. Fonts are the main cross-renderer drift, implied by 1.0.12's "follow Blink" changes to text layout ([@napi-rs/canvas releases](https://github.com/Brooooooklyn/canvas/releases)), so UI text is a bitmap font drawn with `drawImage`, or masked out of pixel comparisons.

Desktop packaging does not depend on the renderer and should not drive the choice. Electron and NW.js bundle Chromium; CrossCode shipped on Steam in NW.js and Vampire Survivors reached Steam 1.0 on Phaser ([summerengine.com](https://www.summerengine.com/make-great-games/threejs-game-on-steam)). `steamworks.js` is MIT, supports Electron and NW.js, covers achievements, cloud saves and Workshop, and must run in the main process ([steamworks.js on npm](https://www.npmjs.com/package/steamworks.js)). Tauri 2 produces binaries "as small as 3 to 10 megabytes" but uses the system webview, which means WebView2, WKWebView and webkit2gtk are three rendering engines to test ([summerengine.com](https://www.summerengine.com/make-great-games/threejs-game-on-steam)), a three.js user reports Tauri "has had issues not supporting WebGL2 on some platforms" ([three.js discourse](https://discourse.threejs.org/t/best-solution-for-running-three-js-in-a-desktop-app/47485)), and no Steamworks binding for Tauri was found ([narrat forum, undated](https://narrat.discourse.group/t/ditching-electron-in-favour-of-more-modern-tools-like-tauri/259)). Inference: Electron is the low-risk wrapper because it is the same Chromium the Playwright tests run against, and a Canvas 2D renderer is the least sensitive to the webview spread if Tauri is tried later for size. The Steam bridge runs in Electron's main process over IPC, the same shape as the sim/viewer seam, so it can reuse the message conventions.

## Recommendation: Canvas 2D now, confirmed by a one-week experiment, PixiJS as the fallback

Build the first renderer on raw Canvas 2D behind a `RenderBackend` interface, in the `web` package, with the Node implementation over `@napi-rs/canvas` living in `tools` beside the existing text views. Keep the sim in TypeScript with the public surface described above. Treat the experiment below as the gate on the renderer step (step 5 of the suggested order in `design/what-remains.md`), and name PixiJS v8 as the fallback so a failed gate has a destination rather than a reopened debate. Do not pick Phaser 4 (heaviest, no headless pixels, owns the loop), Excalibur (no stable release in 2026 and headless on an undated roadmap), Unity (license, image size, editor-in-the-loop content), Godot (loses TypeScript on web) or a Rust core (no scale case yet). melonJS is the only alternate worth a half-day spike, and only if the Canvas 2D gate fails on performance.

The decisive experiment takes one week, before any art pipeline work. Build a fixture from the sim: three buildings and a square from step 3, twelve villagers at 14:00 with one indoors so roof fading is exercised, and the camera following a villager mid-walk so interpolation is exercised. Implement the reference scene once in Canvas 2D. The gate has five criteria, each measurable without a screen.

| Criterion | Pass condition | What a failure means |
|---|---|---|
| Node determinism | Two Node renders of the fixture are byte-identical PNGs | Pin or fix `@napi-rs/canvas`; this should not fail |
| Browser parity | Playwright `canvas.screenshot()` matches the Node PNG at `maxDiffPixels: 0` with UI text masked | Text or sampling drift; move to a bitmap font or widen the mask before blaming the renderer |
| Scene dump | `window.__scene()` matches the sim's "where is everyone" table and reports roof alpha 0 for the occupied building | Viewer state bug; fix before measuring anything else |
| Frame budget | Mean frame time under 8 ms at 480x270 logical, 3x scale, 300 sprites, measured with `performance.now()` in the page under Playwright, and no chunk re-rasterisation during a pan | Switch to PixiJS behind the same `RenderBackend` interface; keep the fixture and the dump |
| Size | Renderer under about 800 lines excluding tests, zero runtime dependencies | Reconsider whether the hand-rolled path is paying for itself |

Inference: the frame budget is the only criterion with a realistic chance of failing, and the draw-call arithmetic above says it will not at this scale. If it fails, PixiJS is the fallback because it is the most maintained library, ships its own agent skills, and its headless gap is one blit away from closed; the project would then accept Playwright with `--enable-unsafe-swiftshader`, `preserveDrawingBuffer` in test builds and 100-pixel tolerances as the cost of WebGL.

What each option commits the project to, if chosen:

| Option | Commits the project to | Gives up |
|---|---|---|
| Canvas 2D (recommended) | Owning Y-sort, camera, chunk cache and bitmap text (~a few hundred lines); pinning `@napi-rs/canvas`; bitmap fonts or masked text in pixel tests | Shader lighting and per-light shading; very large sprite counts |
| PixiJS v8 (fallback) | WebGL in CI with SwiftShader flags and tolerances; a chunked tilemap of your own; Electron for desktop to keep one Chromium | Pixel-exact Node tests until the canvas backend's present step is fixed |
| Phaser 4 | A 356 KB framework that owns the loop; jsdom for logic tests; Playwright for all pixels; Tiled JSON as the map format | A thin seam between sim and screen; Canvas fallback (deprecated) |
| Excalibur 0.32 | Pinning a 0.x engine with a nine-month alpha line; its Playwright+Xvfb rig | A Node path; any 2026 stable |
| melonJS 20 | An API with stale training data; an unverified Node path | Community depth |
| Godot 4.7 | GDScript on web; `.tscn` text without editor validation; a `JavaScriptBridge` seam; a 6 MB base download | TypeScript on the render side; the Node test loop for the viewer |
| Unity 6 | A human-minted `.ulf`; a 7.5 GB image; Editor scripts as the content pipeline; `.jslib` on web | The headless loop; a small web build |
| Defold 1.13 | Lua; text protobuf; cloud-built native extensions | TypeScript; community depth |
| Rust sim + TS viewer | A second toolchain pinned together; `ts-rs` bindings regenerated before `tsc`; a permanent boundary to debug across | Nothing at the viewer; the single-language repo |
| Bevy end to end | A ~75-section migration every five months; 5 to 13 MB wasm; a sim kept outside the ECS anyway | Sharing code with the developer's TypeScript work |
| Ebitengine | Go; a GPU on the test host for its virtualization harness | Software-rendered pixels in CI |

Open decisions, in the order they come due:

| Decision | Options | Due |
|---|---|---|
| Logical resolution and tile size | 320x180 or 480x270 at 16 px tiles; fixes the integer-scale ladder and the UI's pixel budget | Before the experiment fixture |
| UI in the canvas or in the DOM | Bitmap-font UI inside the canvas (pixel-testable, one surface) versus a DOM overlay (readable by Playwright as an accessibility tree, excluded from pixel tests) | Before the experiment |
| Pixel-test strictness policy | Text dumps only; plus Node PNG goldens at threshold 0; plus Playwright smoke at tolerance. Recommended: all three, with Playwright limited to a handful of whole-scene captures | At the gate |
| Worker now or later | Main thread first; the message-shaped interface makes a worker a transport change | When frame time or catch-up stalls justify it |
| Lighting and day-night | A multiply overlay is cheap on Canvas 2D; per-light shading argues for PixiJS. Decide before the art pipeline so tiles are authored for one or the other | Before generated art |
| Desktop wrapper | Electron with `steamworks.js` (overlay-safe, same Chromium as tests) versus Tauri (small, three webviews, no Steamworks binding found) | When Steam becomes concrete |
| Rust port trigger | Write down the conditions (native build without a browser, server-side sim, determinism bugs lint cannot catch) so the question is not reopened by taste | Now, in `decisions.md` |
| Version pinning and baseline policy | Pin `@napi-rs/canvas` and Playwright; regenerate baselines on bump in a dedicated commit | At repo setup |

## Conclusion

The research moves the engine question from "which library" to "which seam", and once the seam is an event stream with no back-channel the renderer becomes the least consequential part of the stack. It can be a few hundred lines, it can be replaced behind one interface, and the only property that differentiates the candidates for a developer who cannot see is whether the same code can produce pixels in Node. That property is why Canvas 2D wins here despite being the least featured option, and why the developer's unease about PixiJS turns out to be well placed on the headless axis and misplaced on maturity.

The second shift is about Rust. The case for a Rust core in this project is enforcement, not performance, and enforcement can be bought more cheaply in TypeScript with a sim package that has no browser imports, a lint against `Math.random` and `Date.now`, integer-only tile math, and replay hashes at every tick. Shaping the sim's public surface as exactly what a wasm module would export keeps the port available at the cost of a few naming decisions today, and turns a language debate into a trigger written in the decisions log.
