# Sim/viewer architecture and the sightless-agent dev loop (researched 2026-10-23)

Scope: the seams between a deterministic discrete-event simulation core and its renderer, how shipped games present discrete simulation smoothly, how replay is used as a test instrument, how an agent with no screen gets feedback, and what web-first vs desktop-first costs. Engine feature comparisons are out of scope (other notes cover them). Everything below is tied to a source; items I could not source are listed under Gaps.

A note on source quality: several primary pages (Playbooks skill page, RustConf abstract, Klei forums, Medium) returned 403/404 to fetches, so for those the only material is the search-result snippet. Those are marked "(snippet only)". The OpenFrontIO repo could not be listed through the GitHub API from this session, but one source file and the README were fetched raw.

## 1. Sim/viewer separation patterns and their trade-offs

### Takeaway
Shipped deterministic-simulation games converge on one shape: the sim advances in integer ticks on its own cadence, the renderer reads sim state (or a per-tick update message) and never writes it, and determinism is protected by forbidding wall-clock time and unseeded randomness inside the sim. The most directly relevant open-source precedent for a TypeScript project is OpenFrontIO, which runs the deterministic core in a Web Worker, sends `GameUpdate` messages to a PixiJS client, and treats every game as an archived intent log with periodic hashes that are re-checked on replay. "Headless server plus thin client" for single-player exists in practice (Screeps, OpenFrontIO's `LocalServer`, DFHack's RPC server) and is the pattern that gives a sightless agent the most leverage, since the same sim can be driven from Node with no browser at all.

### Cited Findings

**OpenFrontIO (TypeScript, AGPL; deterministic core in a Web Worker, PixiJS client)**
- The project is split into a client, a deterministic core, a relay server and a closed-source API. The client "handles rendering with PixiJS, UI input, the WebSocket connection, and runs a Web Worker that executes the core simulation." — [OpenFrontIO architecture docs (mirror)](https://mintlify.wiki/openfrontio/OpenFrontIO/development/architecture)
- Rules the docs state for the core: "The core MUST be fully deterministic with no external dependencies." "Any randomness must use seeded random number generators." "The client does NOT handle game logic. All game state modifications happen in the core component." Determinism "Allows game replays by re-running intents." — [OpenFrontIO architecture docs (mirror)](https://mintlify.wiki/openfrontio/OpenFrontIO/development/architecture)
- Data flow: a player action becomes an `Intent` sent to the server; the server bundles all intents for a tick into a `Turn` and relays it to all clients; each client forwards the Turn to the core worker; the worker creates `Executions` (stateful objects that modify game state over multiple ticks) and sends a `GameUpdate` "with changes" back to the client, which displays it. The mirror does not say whether `GameUpdate` is a full snapshot or a delta, nor how postMessage/transferables are used. — [OpenFrontIO architecture docs (mirror)](https://mintlify.wiki/openfrontio/OpenFrontIO/development/architecture); the search summary of other mirror pages described "a main thread for UI, rendering, and user input, with a worker thread for core simulation, communicating via postMessage with transferable buffers" and said the core "is meant to avoid Math.random() (use seeded RNG) and Date.now() (use tick counters)" — [OpenFrontIO technical overview (mirror)](https://www.mintlify.com/openfrontio/OpenFrontIO/technical/overview) (snippet only)
- The current README describes the packages as `@openfront/engine` ("Deterministic game simulation"), `engine-api` ("The engine's contract: types, schemas, game updates and the worker protocol"), `engine-lib`, `/packages/shared` ("wire schemas"), a "Compact binary wire format for zod schemas" package, `/src/client` and `/src/server`. Replay of a production game requires being "on the same commit that the game you want to replay was executed on" (the commit is stored in the game's `gitCommit` field) and "Unfinished games cannot be replayed on localhost." Node v24.15.0+ required. — [OpenFrontIO README](https://github.com/openfrontio/OpenFrontIO)
- Single-player is literally a headless server inside the client: `src/client/LocalServer.ts` runs a `setInterval` that polls every 5 ms and ends a turn once `Date.now() > this.turnStartTime + turnIntervalMs` (scaled by replay speed); intents are batched into a `Turn` and sent to the client as a `turn` message; a pause intent ends the turn immediately and while paused non-pause intents are dropped; at the fastest replay speed up to 60 turns of backlog may queue. In singleplayer the client hash is stored only every 100 turns (`clientMsg.turnNumber % 100 === 0`) to keep the record small; on replay `if (archivedHash !== clientMsg.hash)` the server logs an error and sends a `desync` message. Finished games are gzip-compressed and POSTed to `/archive_singleplayer_game`; games resumed from a snapshot are never archived "because their turns start mid-game and can't be replayed." — [OpenFrontIO src/client/LocalServer.ts](https://github.com/openfrontio/OpenFrontIO/blob/main/src/client/LocalServer.ts)

**Factorio (C++; update and render on separate threads, no interpolation)**
- FFF #70 "The smooth FPS" (Kovarex, 2015-01-23): the old loop skipped a frame if all work ran over 16.666 ms; the current loop runs update and render on separate threads. If rendering takes too long the frame misses vsync and is skipped while "the update still runs, so the game isn't slowed" (the post cites roughly 40 FPS at 60 UPS). If update takes too long (huge factories) UPS falls below 60 and the whole game slows. The remaining problem was spikes, addressed by splitting large calculations across ticks. The post does not describe interpolation. — [Factorio FFF-70](https://factorio.com/blog/post/fff-70)
- Forum discussion (2018-2019) proposed computing tick N on one core while rendering tick N-1 on another, at the cost of "about one tick of delay to the visual output"; a Factorio staff member replied that breaking the connection between update and render would remove a core part of how the game works. One player measured render at about 1.5 ms and update at about 3.0 ms on a large factory. — [Factorio forums, "Parallel processing in games & applications"](https://forums.factorio.com/viewtopic.php?p=479355)
- A Factorio staff member defines determinism as the same result of the update function for all players given the same state and inputs, written as S_{t+1} = Update(S_t, I_t). — [Factorio forums](https://forums.factorio.com/viewtopic.php?p=574958)

**Dwarf Fortress (C++; one codebase, graphics layer swaps glyphs; external viewers over RPC)**
- Tarn Adams on the Steam version (interview published 2023-03-14): "There aren't really two codebases at all, haha." The Classic/graphical mode switch "is just swapping out some glyphs"; the shared grid "leads to some restrictions, but this has made it really easy to maintain the free version." The new UI was built "mostly Zach and I and to some extent also Mike and Meph"; Putnam is introduced as "the new programmer" whose additions sometimes need tweaks because of "baked-in assumptions" in the codebase. The interview does not discuss SDL/OpenGL or graphical FPS. — [Game Developer: How Tarn Adams upgraded and optimized Dwarf Fortress for Steam](https://www.gamedeveloper.com/programming/how-tarn-adams-upgraded-and-optimized-dwarf-fortress-for-its-official-steam-release)
- DF wiki: "FPS" is the number of computational ticks per second; "graphical frame rate" is the display refresh and is "typically slower than the computational frame rate"; with default settings "one graphical frame occurs every two computational frames"; FPS_CAP defaults to 100 and Alt-= / Alt-- change it in game. — [Dwarf Fortress wiki: FPS](https://dwarffortresswiki.org/index.php/FPS). Older wiki: G_FPS "controls how often Dwarf Fortress redraws the screen" and "how often the game checks for keyboard or mouse input"; "reducing G_FPS can speed up the rest of the game." — [DF wiki v0.34: Maximizing framerate](https://dwarffortresswiki.org/index.php/v0.34:Maximizing_framerate)
- Community claim (2022 Steam thread, not an official statement): "the entire game is single-threaded." — [Steam discussions](https://steamcommunity.com/app/975370/discussions/0/3709306945126390003)
- DFHack's remote interface: external tools talk to DFHack over a TCP socket using Google protobuf messages (handshake, request/response, quit); core and plugins expose "RPC methods"; `allow_remote` defaults to false (local only), port defaults to 5000; `RemoteFortressReader` is a plugin exposing RPC methods; Stonesense and Armok Vision (external 3D viewers) use the RPC API; client libraries exist for C#, Go, JavaScript, C++ (Qt), Python, Java and Rust. The page does not mention Dwarf Therapist. — [DFHack docs: Remote access interface](https://docs.dfhack.org/en/stable/docs/dev/Remote.html)

**Screeps (Node.js server, closed client; the purest "headless sim + thin client")**
- Server tick is two stages: "1. Player scripts calculation. 2. Commands processing." Run-time servers pull tasks, load needed DB data, run each player's script, collect commands; then commands are processed per room. "One room and one player are processed synchronously by one core which rules out various race conditions." All game data lives in MongoDB ("each game object is a separate database document"); tick coordination and task queues are Redis-based; DB writes are applied in bulk after both stages; run-time servers work from RAM and player code "does not make any hard drive or database requests." The page does not describe how the client receives world state. — [Screeps server-side architecture](https://docs.screeps.com/architecture.html)
- The open-source server has six modules (launcher, storage, backend, engine, driver, common); the engine module is shared between the official and standalone servers; the driver "connects the engine to its hosting environment, so it can be swapped out." — [screeps/screeps on GitHub](https://github.com/screeps/screeps). Player code runs in `isolated-vm` sandboxes with separate heaps (256 MB ceiling) since 2018-03-05. — [Screeps changelog 2018-03-05](https://blog.screeps.com/2018/03/changelog-2018-03-05/)
- The frontend is not open source; a community comment says it is NW.js plus Angular (unconfirmed). — [r/screeps mirror](https://lr.us.psf.lt/r/screeps/comments/1ekq1rr/how_is_this_game_made)

**Caves of Qud (C# roguelike core hosted inside Unity)**
- Brian Bucklew (Unity interview, 2025-06-18): "Caves of Qud at the time was a C# project"; he describes putting the game inside Unity "as a host" after shipping Sproggiwood on PC and mobile with Unity, because "I was really impressed with Unity's ability to go cross-platform" and wanted to see if Qud could reach mobile as easily. Objects are "a set of properties that are composed together," which he says maps to Unity's component model. — [Unity: Systems-driven design in Caves of Qud](https://unity.com/resources/systems-driven-design-in-caves-of-qud)
- Secondhand quote attributed to Bucklew that the game "was not originally developed on Unity and only use Unity for the UI." — [GOG forum thread](https://gog.com/forum/general/so_what_then_if_not_unity/page2) (community quote, not verified against the original)
- In 2023, after Unity's runtime-fee announcement, Bucklew live-tweeted porting the game to Godot and reported about 16 hours to get it booting; no confirmation found that a full Godot port shipped. — [FullCleared](https://fullcleared.com/news/caves-of-qud-developer-live-tweets-porting-game-to-godot)

**Oxygen Not Included (Unity C# game + native sim DLL)**
- The engine is Unity. — [Wikipedia: Oxygen Not Included](https://en.wikipedia.org/wiki/Oxygen_Not_Included). A Klei-forum mod project "SimDLLPlus" is described as "replacing origin SimDLL" with a C++ component plus a C# layer that "links SimDLLPlus and the main program," built with the VS2022 v143 toolset, confirming the shipped game's element simulation lives in a native DLL separate from the C# game. One user reported about 33% FPS loss on a 600x600 map at 30x speed attributed to single-thread limits and thread waits. — [Klei forums: SimDLLPlus multi-threaded simulation](https://kleiforums.com/forums/topic/167593-simsimdll-multi-threaded-simulation/) (snippet only; fetch returned 403)

**Stardew Valley (single-loop XNA/MonoGame)**
- "Originally programmed in C# using the Microsoft XNA framework and later migrated to MonoGame in 2021"; Barone said the migration made the game "futureproof," enabling mods to use more than 4 GB of RAM. — [Wikipedia: Stardew Valley](https://en.wikipedia.org/wiki/Stardew_Valley). (Stardew's Update/Draw loop is the XNA `Game` class pattern; I found no Barone statement describing it, see Gaps.)

**Shared memory on the web (constraints)**
- `SharedArrayBuffer` requires a secure context and cross-origin isolation (COOP + COEP headers); without the headers the constructor is hidden and `postMessage` throws for SAB objects. Shared memory was disabled at the start of 2018 (Spectre) and re-enabled via isolation in 2020. "The requirements listed above for sharing a SharedArrayBuffer between workers also apply to sharing a WebAssembly.Memory"; `WebAssembly.Memory` created with `shared: true` is backed by a SAB. — [MDN: SharedArrayBuffer](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer)

### Inferences
- Pattern comparison, grounded in the examples above:
  - Snapshot-per-frame (viewer reads whole state): what Factorio and DF do in-process (same memory, separate threads or a single thread). Zero sync cost, perfect determinism isolation if the renderer is read-only, but it forces same-process, same-language, and in Factorio's case the staff explicitly refused to decouple it for latency reasons.
  - Event stream / deltas (viewer applies `GameUpdate`s): OpenFrontIO. Works across the worker boundary with serialization; the client keeps its own presentation copy. Cost is a wire schema (OpenFrontIO built a zod binary format for it) and the risk that the client-side copy drifts; OpenFrontIO mitigates by making the client stateless about rules ("does NOT handle game logic") and hashing every 100 turns.
  - Command/observer with typed events: this is the discrete-event core's natural output (each popped event is already a typed fact). The viewer subscribing to "ActorArrived(tile, tick)" and owning its own tween state is the same thing as OpenFrontIO's `GameUpdate` with smaller granularity.
  - Shared memory (SAB / wasm linear memory): viable only with COOP/COEP; itch.io and most static hosts do not set those headers by default, which matters for the web-first constraint. Nothing in the surveyed 2D games uses it.
  - Process separation (worker, or native process over WebSocket): OpenFrontIO (worker), Screeps (server), DFHack RPC (sidecar). This is the only pattern that lets the same sim run under Node for tests and under the browser for play without a rendering dependency.
- OpenFrontIO's `LocalServer` is the most reusable template for this project: the single-player "server" is a tiny turn-producer, the archive is the input log, and replay verification is "re-run and compare hashes at checkpoints." Its decision to hash only every 100 turns is a size trade-off that a test harness need not make.
- Caves of Qud and ONI are the two shipped examples of "sim in one runtime, renderer in another language/runtime" (C# core hosted by Unity; C++ sim DLL under a Unity game). Both show the seam is survivable but neither published the interface.

## 2. Rendering a discrete-event sim smoothly (interpolation, time scale, catch-up)

### Takeaway
Every shipped example separates "simulation rate" from "display rate" and lets them diverge in both directions: DF renders one graphical frame per two sim ticks by default; Factorio keeps 60 UPS and drops render frames; RimWorld multiplies the tick rate (60/180/360/900 ticks per second) and admits the machine may not keep up. The canonical smoothing recipe is Gaffer's fixed-timestep accumulator with interpolation between the previous and current sim states, clamped to avoid the spiral of death; for a discrete-event core the equivalent is interpolating presentation between the last applied event and the next scheduled one. On the web, background tabs stop `requestAnimationFrame` entirely and throttle timers, so "catch-up on tab return" must be an explicit, capped loop.

### Cited Findings
- Fix Your Timestep (Glenn Fiedler): measure frame time, clamp it (the article uses 0.25 s) "to limit the spiral of death," add to an accumulator, step the simulation by fixed dt while the accumulator holds a step (saving previous state), then "alpha = accumulator / dt" and "perform a linear interpolation" between previous and current states for rendering. Fixed timesteps give "exact reproducibility from one run to the next given the same inputs," which is why deterministic lockstep uses them. Capping steps per frame makes the simulation "appear to slow under heavy load instead." — [gafferongames.com: Fix Your Timestep](https://gafferongames.com/post/fix_your_timestep/)
- Factorio: render and update are separate threads; a late render frame is skipped at vsync while update continues (about 40 FPS at 60 UPS); a late update slows the whole game; spikes are smoothed by splitting big calculations across ticks. — [Factorio FFF-70](https://factorio.com/blog/post/fff-70)
- Dwarf Fortress: computational ticks (FPS, cap default 100) and graphical refresh are separate; default is one graphical frame per two ticks; lowering G_FPS speeds up the sim because redraw and input polling happen at G_FPS. — [DF wiki: FPS](https://dwarffortresswiki.org/index.php/FPS); [DF wiki v0.34: Maximizing framerate](https://dwarffortresswiki.org/index.php/v0.34:Maximizing_framerate)
- RimWorld: 60 ticks per real second at normal speed; "there are always 2,500 ticks to one in-game hour" (60,000 per day); speed settings are multipliers of 3, 6 and 15 (ultrafast is dev-mode only); modders use a 250-tick "rare tick" and a 2,000-tick "long tick"; the game "may not reach the target speed depending on the player's hardware" and then runs "as close to the target as possible." The page says nothing about rendering vs ticks. — [RimWorld wiki: Ticks](https://rimworldwiki.com/wiki/Ticks)
- OpenFrontIO's local server scales the turn interval by replay speed and allows a backlog of up to 60 turns at the fastest replay speed; pausing is an intent that ends the current turn immediately and suppresses further intents. — [OpenFrontIO LocalServer.ts](https://github.com/openfrontio/OpenFrontIO/blob/main/src/client/LocalServer.ts)
- Chrome background-tab behavior (Chrome 88+): `requestAnimationFrame` "will wait for the page to be visible" (no CPU while hidden). Timers are throttled to once per second ("standard throttling") when hidden, and to once per minute ("intensive throttling") once the page has been hidden more than 5 minutes, the timer chain count is 5 or more, the page has been silent 30 s and WebRTC is not in use. — [Chrome Developers: Timer throttling in Chrome 88](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)

### Inferences
- For a priority-queue sim, the accumulator loop maps directly: the renderer "produces" real time scaled by the speed multiplier, the sim "consumes" it by popping events whose tick <= target tick. Interpolation between discrete events means the viewer stores, per actor, (fromTile, toTile, departTick, arriveTick) from the last movement event and draws position = lerp(from, to, (nowTick - departTick)/(arriveTick - departTick)), where nowTick is a fractional presentation clock. This keeps the sim integer-only and leaves all fractional math in the viewer, which preserves determinism by construction.
- Pause and speed changes are viewer-side concerns (how much sim time to consume per real second), and OpenFrontIO and RimWorld both treat them that way. "Skip to morning" is just "consume N ticks with rendering suppressed," which is the same path a test harness uses to run to a tick; rendering during fast-forward can sample every k-th tick (DF's 2:1 default is the simplest form).
- Tab inactivity: because rAF stops, the sim should not be driven from rAF alone if the world is meant to keep running; but a single-player town game can simply pause on `visibilitychange` and resume, which also avoids a multi-minute catch-up burst. If catch-up is wanted, clamp it (Gaffer's 0.25 s rule generalized to "at most N ticks per frame") and run the remainder in the worker where it cannot stall rendering.
- Factorio's refusal to put render one tick behind update is about input latency for a real-time game; for a town sim where the player's actions are already queued intents, a one-tick (or one-turn) presentation lag is invisible and buys a clean worker boundary.

### Gaps
- No source found describing how RimWorld, ONI or Prison Architect interpolate (or don't) between ticks at high speed, or how they throttle rendering during fast-forward.
- No shipped-game source found for "catch up after tab inactivity"; the Chrome throttling rules are the only hard data.

## 3. Deterministic replay as a testing instrument

### Takeaway
The shipped practice is uniform: record the input stream plus seed and build version, re-simulate, and compare per-tick (or periodic) state hashes to find the first divergent tick. Factorio ran a mode that checksums the whole map every tick (2014), OpenTTD validates caches every tick in `-d desync=2` and replays `commands-out.log` with `NOT_REACHED` on checksum mismatch, and OpenFrontIO (TypeScript) archives every game as compressed turns with a hash every 100 turns and emits `desync` on replay mismatch. Replays are only valid on the same version/mods/commit in all three.

### Cited Findings
- Factorio FFF #47 "CRC fun" (2014): the developers ran the game in a mode "that computes a checksum of the whole map every tick, and the replay checks the same thing"; when checksums diverge they compare the two saves from that tick, "the first tick of desynchronization, and the difference is usually tiny." This fixed reproducible local determinism bugs; user-reported multiplayer desyncs were harder. — [Factorio FFF-47](https://factorio.com/blog/post/fff-47)
- Factorio 0.4.1 (2013): the game "was (almost) fully deterministic, which enabled replays. Replays only worked for games played on the same version with the same mods." — [Factorio 0.4.1 release post](https://cf-www.factorio.com/blog/post/factorio-0-4-1-released). FFF #270 notes the replay system would not work if you ever saved, exited and resumed without it. — [Factorio FFF-270](https://cf-www.factorio.com/blog/post/fff-270)
- FFF #149 (2016-07-29): a joining client receives the player input "saved for later," downloads the map in the background and "updates as fast as it can to reach the server's state"; messages carry per-communication sequence numbers so high-latency players can batch more actions per message. — [Factorio FFF-149](https://factorio.com/blog/post/fff-149)
- OpenTTD: start with `-d desync=2` to "enable validation of caches every tick" (cached values recomputed and compared, differences logged to `commands-out.log`); level 1 dumps commands, level 2 adds vehicle cache checks, level 3 adds monthly autosaves; the periodic server checksum "is the state of the random number generator of the game logic" and "is only an ultimate failure detection. It does not give any indication on when the Desync happened"; to replay, use the same version, enable `DEBUG_DUMP_COMMANDS`, rename the log to `commands.log`, run `openttd -D -d desync=3 -g startsavegame.sav`, and a checksum mismatch "will trigger a NOT_REACHED"; desync saves are named `dmp_cmds_<seed hex>_<date hex>.sav`. — [OpenTTD docs/desync.md (jgrpp copy)](https://git.blob42.xyz/Archives/OpenTTD-patches/src/branch/jgrpp/docs/desync.md); current official page: [OpenTTD docs/debugging_desyncs.md](https://github.com/OpenTTD/OpenTTD/blob/master/docs/debugging_desyncs.md) (confirms the `dmp_cmds_XXXXXXXX_YYYYYYYY.sav` naming and the three debug levels; does not itself state the "every tick" wording)
- OpenFrontIO (TypeScript): replays are archived turn lists; replay requires the same git commit; singleplayer stores a client hash every 100 turns; on replay a hash mismatch logs an error and sends `desync`. — [OpenFrontIO LocalServer.ts](https://github.com/openfrontio/OpenFrontIO/blob/main/src/client/LocalServer.ts); [OpenFrontIO README](https://github.com/openfrontio/OpenFrontIO)
- General guidance (secondary): hash game state each tick and compare across runs to find the first divergent frame; hash per entity or subsystem to narrow which value diverged; the "test of truth" is that re-simulating the recorded inputs from the recorded starting state yields an identical run; pin RNG seed, input-stream hash and build/content version; common nondeterminism sources are floating-point order dependence, wall-clock time in gameplay code, per-frame rather than per-tick RNG, and unordered iteration; a CI check can replay the same log at several frame rates and require identical final hashes. — [bugnet.io: How to debug multiplayer desync issues](https://bugnet.io/blog/how-to-debug-multiplayer-desync-issues-in-games); [bugnet.io: test replay determinism across frame rates](https://bugnet.io/blog/how-to-test-network-replay-determinism-across-frame-rates)

### Inferences
- A "golden day" test for this project is the OpenTTD/OpenFrontIO recipe in miniature: `{seed, contentVersion, inputLog}` plus a stored hash at every N ticks (N can be 1 in tests since size does not matter there). Store per-subsystem hashes (actors, inventory, schedule queue, RNG state) so a failure names the subsystem, as the bugnet guidance suggests and as OpenTTD effectively does by validating specific caches.
- Hashing the pending event queue itself (not only world state) is the discrete-event analogue of OpenTTD hashing the RNG state: it is the cheapest value that changes when anything upstream diverges.
- "Replay to tick T and screenshot" is sound only if the renderer is a pure function of (sim state, presentation clock); the OpenFrontIO rule that the client holds no logic is what makes that true.
- Factorio's and OpenTTD's "same version only" rule means replay logs are a test fixture for a given commit, not a long-lived asset; regenerate goldens on content changes rather than trying to migrate them.

### Gaps
- No TypeScript project besides OpenFrontIO was found that uses input-log replay in automated tests, and OpenFrontIO's use is runtime desync detection rather than a CI test (no CI test for it was found in this pass).
- No source found on JavaScript-specific floating-point determinism across engines (V8 vs JSC) for game sims; the general advice (integer ticks, integer math in sim) sidesteps it.

## 4. Feedback for a sightless agent (screenshots, text dumps, pixel diffs)

### Takeaway
As of late 2026 the working pattern reported by agent-built game projects is: expose a text/structured dump of the scene and a deterministic "advance N ticks" hook, drive the game with Playwright, capture screenshots as a secondary check, and compare with a pixel-diff library using a threshold. Chromium specifics matter: Playwright 1.49 (2024-11) moved to `chromium-headless-shell` for headless runs with a documented warning that "Screenshots are different" from new headless, Chromium has deprecated automatic SwiftShader fallback for WebGL (opt in with `--enable-unsafe-swiftshader`), and a WebGL canvas read back without `preserveDrawingBuffer: true` can be blank. A Canvas2D/Skia path in Node (`@napi-rs/canvas`) avoids the browser entirely for pixel-exact renders of a 2D pixel-art scene.

### Cited Findings

**Browser screenshots (Playwright/Chromium)**
- Playwright issue "Changes in Chromium headless in Playwright v1.49" (opened and closed 2024-11-13): Chromium removed the old headless mode; Playwright ships a separate `chromium-headless-shell` build for default headless runs; differences in new headless include "PDF documents are now rendered in the page," "Screenshots are different" (recommendation: update all screenshot expectations), "New headless is slightly slower on average," and "GPU/WebGL: Availability, features, and performance may vary." Opt into new headless with `channel: 'chromium'`; skip the shell download with `npx playwright install --no-shell`. — [microsoft/playwright#33566](https://github.com/microsoft/playwright/issues/33566)
- `toHaveScreenshot` options: `animations` defaults to `"disabled"`; `caret` defaults to `"hide"`; `threshold` (per-pixel perceived color difference, 0 strict to 1 lax) defaults to `0.2`; `maxDiffPixels` and `maxDiffPixelRatio` are unset by default (configurable in `TestConfig.expect`); `scale` defaults to `"css"` ("device" gives one pixel per device pixel); `mask` and `stylePath` available. — [Playwright: PageAssertions](https://playwright.dev/docs/api/class-pageassertions). Snapshot files are named `<name>-<browser>-<platform>.png`; "Screenshots differ between browsers and platforms due to different rendering, fonts and more"; the docs name pixelmatch as the comparison library and warn to "run tests in the same environment where the baseline screenshots were generated" (host OS, version, settings, hardware, power source, headless mode all affect rendering). — [Playwright: Visual comparisons](https://playwright.dev/docs/test-snapshots)
- Chromium SwiftShader doc: "Allowing automatic fallback to WebGL backed by SwiftShader has been deprecated"; WebGL context creation will fail rather than fall back unless the browser is launched with `--enable-unsafe-swiftshader` (which "opts in to lower security guarantees"); the unsafe path is also listed as `--use-gl=angle --use-angle=swiftshader-webgl`; SwiftShader "remains useful for web developers testing sites on headless systems or machines without a supported GPU" but is "not intended for running untrusted content." No Chrome version number is given on the page. — [Chromium docs/gpu/swiftshader.md](https://chromium.googlesource.com/chromium/src/+/main/docs/gpu/swiftshader.md)
- A community commit note reports switching from `--disable-gpu` to `--enable-unsafe-swiftshader` "for Playwright parity," saying `--disable-gpu` "breaks WebGL on Chrome 130+." — [chrome-use CLI commit (community, unverified)](https://gitea.oimcloud.myaddr.tools/oimwiodev/chrome-use/src/commit/486e1b341fbe1e1a6bbf9bfc885ec0e2d34eb45c/cli). Microlink reports `--use-angle=gl` is faster than SwiftShader but "has to bind a GL surface, which needs an X display, even headless," otherwise WebGL can silently degrade. — [Microlink: faster WebGL screenshots](https://microlink.io/blog/faster-webgl-screenshots)
- WebGL readback: by default the browser clears the WebGL drawing buffer after compositing, so a later `toDataURL()` reads an empty buffer; the fix is `preserveDrawingBuffer: true` at context creation (which "prevents certain possible optimizations") or exporting inside the render loop right after drawing. — [webgl2fundamentals: WebGL tips](https://webgl2fundamentals.org/webgl/lessons/webgl-tips.html)
- Guidance for WebGL screenshots: have the app expose a readiness flag and wait on it before `page.screenshot()` rather than waiting on load events. — [createit.com: Headless Chrome, testing WebGL using Playwright](https://www.createit.com/?p=3319)

**Node-side rendering without a browser**
- `@napi-rs/canvas` is a "High performance Skia canvas implementation. Zero system dependencies," a Skia binding for Node via Node-API; supports Linux arm64 (Cortex-A57+), armv7, glibc 2.18+, Apple M-series; encodes PNG, JPEG, AVIF, WebP (and GIF); includes Path2D with PathKit boolean ops and Skottie; the README does not mention WebGL and only mentions node-canvas (cairo) as "hard to install" and used for compatibility tests; no benchmarks given. — [Brooooooklyn/canvas (@napi-rs/canvas)](https://github.com/Brooooooklyn/canvas)

**Pixel-diff libraries**
- pixelmatch: threshold 0 to 1, default 0.1 (smaller is more sensitive); antialiasing detection on by default (`includeAA: true` disables ignoring AA pixels); uses YIQ perceptual color difference and a published antialiasing-detection method. — [pixelmatch package overview](https://socket.dev/npm/package/pixelmatch/overview/^4.0.0)
- odiff: threshold 0 to 1 (lower is more precise), `antialiasing` option keeps AA pixels out of the count, YIQ NTSC color difference, cross-format comparison, ignore regions; speed is its main selling point. — [odiff-bin on npm](https://www.npmjs.com/package/odiff-bin)
- looks-same: antialiasing ignored by default (`ignoreAntialiasing: false` to turn off), `antialiasingTolerance` for browser rendering quirks with maintainers advising not to exceed 10; uses tolerance-style options rather than a 0 to 1 threshold. — [looks-same package page](https://classic.yarnpkg.com/en/package/looks-same)

### Inferences
- Order of reliability for a sightless agent, from the sources: (1) structured scene dump from the sim/viewer (deterministic, diffable as text, no GPU), (2) Node-side Canvas2D render via Skia with pixelmatch against a golden (deterministic on one platform, no browser), (3) Playwright screenshot of the real page (catches integration bugs but is sensitive to headless build, fonts, GPU path and animation timing), (4) the agent "looking" at a PNG (useful for sanity, not for regression).
- What the text dump should contain, synthesized from the develop-web-game guidance and the Godot toolkit: the current tick and presentation clock, camera rect, every visible actor with id, tile, interpolated pixel position, facing, animation name and frame, the active UI widgets and their text (an accessibility-tree analogue), and a fixed-size ASCII map of the visible tile window with actor glyphs. If the dump is produced by the viewer (not the sim), it also verifies the viewer's own state, which is where "sprite didn't move" bugs live.
- For a 2D pixel-art game rendering into a Canvas2D with `imageSmoothingEnabled = false` and integer scaling, a Skia render in Node and a Chromium screenshot should match the same sprite placements; fonts are the main source of cross-renderer drift, so text should be bitmap-font sprites or masked out of comparisons (Playwright's `mask`/`stylePath`).
- If WebGL is chosen (PixiJS), budget for `--enable-unsafe-swiftshader` in CI, a `preserveDrawingBuffer` toggle for test builds, and a readiness flag the test waits on; baseline images must be regenerated when Playwright changes its headless build (as 1.49 did).

- No report found of an agent project using input-log replay plus screenshot-at-tick as a CI gate; this appears to be unexplored in public write-ups.

## 5. What Stardew-likes and living-world games shipped on, and why

### Takeaway
The genre is overwhelmingly Unity (Graveyard Keeper, Moonlighter, Cult of the Lamb, Spiritfarer, Sea of Stars, Sun Haven, Roots of Pacha, ONI, Caves of Qud as host) with Unreal 4 for the 3D entry (Coral Island), XNA then MonoGame for Stardew, and a visible trend of successful indies leaving their first engine once scale or platforms demanded it: Stardew (XNA to MonoGame, 2021), Vampire Survivors (Phaser/HTML5 to Unity, 2023-08-17), Fields of Mistria (GameMaker to an in-house engine, v0.16.2, 2026-07), CrossCode (Impact.js/NW.js, console port required an interpreter "in a cage"). The stated reasons are consistently performance, cross-platform/console reach, and mod/memory ceilings, not features.

### Cited Findings
- Stardew Valley: C# on XNA, migrated to MonoGame in 2021 to be "futureproof" and let mods use more than 4 GB RAM; Switch port by Sickhead Games (2017-10-05); iOS/Android with The Secret Police; Barone donated $125,000 plus an ongoing monthly commitment to MonoGame. — [Wikipedia: Stardew Valley](https://en.wikipedia.org/wiki/Stardew_Valley); [80.lv on the MonoGame donation](https://80.lv/articles/stardew-valley-creator-donated-usd125-000-to-monogame-c-framework-which-holds-his-game-together/). A Steam forum post relays Barone's 2016 AMA remark that one of his big regrets was "going with XNA (totally outdated now)." — [Steam discussions (secondhand)](https://steamcommunity.com/app/413150/discussions/0/365163686043643821/)
- Graveyard Keeper (Lazy Bear Games): Unity. — [Wikipedia: Graveyard Keeper](https://en.wikipedia.org/wiki/Graveyard_Keeper)
- Moonlighter: Unity (database listing). — [Dexerto game DB](https://www.dexerto.com/gaming/db/game/moonlighter/)
- Cult of the Lamb (Massive Monster): Unity; the studio said "Our team specializes in Unity games" during the 2023 runtime-fee dispute. — [LevelUp](https://www.levelup.com/en/news/cult-of-the-lamb-threatens-to-disappear-due-to-unity)

### Inferences
- The engine moves above were all forced by shipping constraints the first engine could not meet: console JIT bans (CrossCode), a 4 GB/mod ceiling (Stardew on XNA), performance and co-op (Vampire Survivors), crashes and Steam Deck/Linux support (Mistria). None were about rendering features. For a sim-first game the practical lesson is that the sim core should not depend on the first renderer or host so that a host swap (NW.js to Unity, GameMaker to custom) does not force a rules rewrite; Caves of Qud's C#-core-hosted-in-Unity is the shipped proof that this works.
- CrossCode is the clearest datapoint on web-first to console: it shipped on PC via NW.js fine (2018) and reached consoles only via a publisher-built JS interpreter (2020), with performance as the binding constraint. For "web first, desktop second," desktop is cheap (NW.js/Electron) and consoles are the expensive step, which matches the project's stated priorities.

### Gaps
- Dinkum: no source found naming its engine in this pass (commonly reported as Unity, unverified here).
- Sea of Stars: Unity is implied by Unity's own roundup, not stated outright in the material fetched.
- Fields of Mistria: the Rust/"maybe" details come only from the RustConf abstract snippet; the official patch notes do not name the language.
- No postmortem found explaining why Graveyard Keeper, Moonlighter or Sun Haven chose Unity beyond "team specializes in Unity" style statements.

## 6. Web vs desktop: what web-first gives up and how it is recovered

### Takeaway
Web-first with a TypeScript/wasm sim costs: no SharedArrayBuffer without COOP/COEP headers, background-tab throttling, no file-system access or Steam features, and a WebGL path that is fragile in CI. The recovery path used in practice is a Chromium wrapper (Electron or NW.js) plus steamworks.js (MIT, supports Electron and NW.js, achievements/cloud/Workshop/overlay helper) or the older Greenworks; Tauri gives much smaller binaries but uses the OS webview with reported WebGL2 gaps. Measured web-build size for an empty engine export: Godot 4.6.2 about 6.33 MB (release, WebGL2, uncompressed per the test repo), Unity 6 empty 2D about 7.7 MB Brotli per one 2026 guide; hand-rolled Canvas2D/PixiJS pages are far below either, which is a concrete argument for not adopting a full engine for a web-first 2D town game.

### Cited Findings
- steamworks.js: "a modern Steamworks SDK implementation for HTML, JavaScript and Node applications," MIT, "Electron and NW.js support," covers achievements, local player, cloud saves, Workshop; it is a native module that "cannot be used by default in the renderer process" (BrowserWindow settings must change); includes an overlay helper to call at the end of main.js; Steam must be installed and running during development. — [steamworks.js on npm](https://www.npmjs.com/package/steamworks.js)
- A GDevelop forum thread (date unclear) claims "the Steam Overlay does not fully work with electron based on the issues listed on the repository" and that steamworks.js "does not currently support the Steam leaderboard API." — [GDevelop forum](https://forum.gdevelop.io/t/steam-overlay-and-leaderboards/60725) (possibly dated)
- Greenworks is the older alternative; one developer shipped an Electron HTML5 game on Steam with overlay and achievements via Greenworks (Electron v16.0.2, Greenworks v16.0.0-alpha.1, Steamworks 1.5), Windows x64 only since that covers over 95% of Steam players. — [itch.io devlog: Adding Steam achievements to an Electron game](https://smjn.itch.io/hivepvs/devlog/364303/adding-steam-achievements-to-an-electron-game)
- Tauri vs Electron: Electron bundles Chromium (WebGL via ANGLE like desktop Chrome); Tauri uses the OS webview (WebView2 on Windows, WebKit on macOS, WebKitGTK on Linux); a three.js forum user reports Tauri "has had issues not supporting WebGL2 on some platforms"; Tauri installers under about 10 MB vs 80 to 150 MB for Electron and roughly 30 to 50 MB idle memory vs 100 to 300 MB (secondary sources); an itch.io developer preferred Tauri for smaller downloads while noting Electron is what enables Steam publishing of browser games. — [three.js discourse](https://discourse.threejs.org/t/best-solution-for-running-three-js-in-a-desktop-app/47485); [itch.io devlog: offline desktop app built with Tauri](https://itch.io/devlog/799708/add-offline-desktop-mac-app-built-with-tauri.amp); [JSLegendDev: The struggle of packaging a JavaScript game for PC](https://jslegenddev.substack.com/p/the-struggle-of-wrapping-a-javascript)
- Godot web export sizes from a load-test repo (WebGL2 template, uncompressed as listed): 4.6.2 release 6.33 MB, 4.5.2 6.22 MB, 4.4.1 6.14 MB, 4.3.0 5.34 MB ("+0.8MB / +15%" from 4.3 to 4.4); the author says "Loading times are really long for godot (compared to unity)" and that Godot export "is finished in a second" vs "10+ minutes" for Unity; no load-time numbers given. — [JohannesDeml/Godot-Web-LoadingTest](https://github.com/JohannesDeml/Godot-Web-LoadingTest)
- A 2026 comparison guide puts an empty Godot web build at about 5 MB Brotli / 9 MB gzip (the template carries the whole engine because it cannot tell which features are used) and measured Unity 6 empty builds at about 7.7 MB (2D) and 10.7 MB (3D URP) with Brotli; qualitative claim that Unity load times trail web-native engines. — [Cinevva: Godot vs Unity for web games (2026)](https://app.cinevva.com/guides/godot-vs-unity-web-games) (vendor-adjacent, not independently benchmarked)
- Web platform constraints relevant to a worker/SAB sim: SAB needs COOP/COEP (section 1); background tabs stop rAF and throttle timers to 1/s then 1/min (section 2). — [MDN: SharedArrayBuffer](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer); [Chrome: Timer throttling](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)
- CrossCode's path (web engine, NW.js desktop, interpreter-based console port) and Vampire Survivors' path (Phaser web, Unity for performance and platforms) are the two web-first precedents (section 5). — [RPG Site](https://www.rpgsite.net/news/9249-deck13-and-radical-fish-games-provide-an-update-on-the-console-versions-of-crosscode); [GamingOnLinux](http://www.gamingonlinux.com/2023/07/vampire-survivors-switching-to-new-game-engine-on-august-17)

### Inferences
- For "web first, desktop second," the architecture that keeps both cheap is: sim in a worker speaking postMessage (no SAB dependency, so it runs on any static host), renderer on Canvas2D or PixiJS, and a desktop wrapper added later (Electron for Steam-overlay safety, Tauri if size matters more than overlay). steamworks.js's requirement to run in the main process means the Steam bridge is an IPC seam, which is the same shape as the sim/viewer seam and can reuse its message conventions.
- Choosing Unity or Godot now "to keep Steam open" buys nothing for this genre that Electron+steamworks.js does not also provide for a 2D game, while it costs the headless loop: Godot headless works from the CLI (Brandon Wu's report) but screenshots then need either the running-game HTTP toolkit or an X server; Unity needs more headless setup. The quantified web cost (5 to 8 MB empty builds, slow Godot startup) is also higher than a hand-built page.
- Console reach is the one thing a web-first stack genuinely gives up (CrossCode's interpreter workaround took a publisher), and the task statement puts consoles out of scope.

### Gaps
- No rigorous, independent 2025 to 2026 benchmark of load times for Unity vs Godot vs PixiJS web builds was found; only sizes and qualitative claims.
- No current (2025 to 2026) authoritative statement on Steam overlay reliability under Electron with steamworks.js; the forum claims may be stale.
- No source quantifying Tauri WebGL2 support status per platform in 2026.
