# JavaScript/TypeScript renderers for a 2D top-down pixel-art town game (researched 2026-10-23)

Scope: the renderer only. The simulation is a separate deterministic discrete-event TypeScript package; the renderer draws layered tile maps, hides roofs indoors, Y-sorts actors and tall props, interpolates between tile-arrival events, follows a camera target, draws crisp pixel art at integer scale, handles a few hundred sprites, shows UI, and must be developable by an agent that cannot see a screen and works in a headless Linux container. Web first, Tauri/Electron second.

## PixiJS v8 (8.22.0 as of 2026-10-01)

### Takeaway
Pixi is the most actively developed option (a release roughly monthly, 500k weekly downloads, WebGL + WebGPU + an experimental Canvas backend, 25 agent skills shipped inside the npm package). It has no first-party tilemap; `@pixi/tilemap` 5.0.2 works with v8 but has had no release since July 2025 and lists its texture limits as "temporarily switched off", so a chunked tile renderer built from `cacheAsTexture` containers or meshes is the safer plan. Headless in Node is not supported out of the box: `@pixi/node` is a 12-commit, 49-star v7-era repo that needs `xvfb`; v8's `DOMAdapter` lets you plug in `@napi-rs/canvas`, and in a local test the Canvas renderer initialised and ran a full render pass in Node 22, but the frame came back black (see Gaps). Pixi's own visual tests run in Electron via `@pixi/jest-electron`, not in Node.

### Cited Findings
- v8.20.0 was a WebGPU-focused point release: WGSL shader overrides, depth-stencil formats, partial buffer updates, render bundles, depth-only targets, Safari WGSL fallback, and a "WebGPU-first render-target attachment architecture"; migration risk: `StructsAndGroups.isUniform` replaced by `accessMode` and old code reading it silently gets `undefined` — [GameDev.net repost of the 8.20.0 release](https://gamedev.net/news/5221-pixijs-v8200-released/)
- June 12, 2026 update (v8.18/8.19): PixiJS passed 500,000 weekly npm downloads; "the 25 official agent skills ship inside the package at `node_modules/pixi.js/skills/`"; renderer `preference` now accepts an array such as `['webgl', 'canvas']`; v8.19 added an experimental `pixi.js/html-source` subpath that renders live DOM elements into textures (Chrome behind a flag only); v8.18 added `graphicsContextToSvg()` and sprite mask `channel: 'alpha'`; AI tooling at pixijs.com/llms with install instructions for 40+ agents — [PixiJS Update - June 2026](https://pixijs.com/blog/june-2026)
- The Canvas renderer arrived in v8.16.0, described as experimental: a 2D Canvas renderer for environments without WebGL or WebGPU, smaller build, automatic fallback, forced with `preference: 'canvas'` in `app.init()`; handles sprites, graphics, text and basic filters but "doesn't cover every feature the GPU renderers support" — [PixiJS Update - v8.16.0](https://pixijs.com/blog/8.16.0)
- `Application.init` options: `resolution` (default 1), `autoDensity` (adjusts canvas CSS size from `resolution`, HTMLCanvasElement only), `antialias`, `preference: 'webgl' | 'webgpu'` (default webgl), `resizeTo`, `sharedTicker` (default false), `autoStart` (default true); the guide page does not list `roundPixels` — [Application guide](https://pixijs.com/8.x/guides/components/application)

- The v8 `Graphics` constructor accepts a `roundPixels` option that rounds final on-screen x/y, "producing crisper lines for pixel-art styles at the cost of smooth sub-pixel movement" — [pixijs-scene-graphics skill page (community mirror of the official skill)](https://claudeskills.info/skills/pixijs/pixijs-skills/pixijs-scene-graphics/)

- `@pixi/node` (pixijs/node): "run PixiJS in Node.js environments, no browser required"; uses the `gl` package for WebGL and `canvas` (node-canvas, which may build from source: `brew install pkg-config cairo pango libpng jpeg giflib librsvg` on macOS); headless servers/CI need `xvfb` (`xvfb-run node ./src/index.js`) to avoid "unable to auto-detect a suitable renderer"; repo has 12 commits, 49 stars, 13 open issues, empty Releases; it does not state which Pixi version it targets — [pixijs/node](https://github.com/pixijs/node). A search result notes the repo's last push was March 2024 and that it is "likely v7-era" — [search summary](https://awesome.ecosyste.ms/projects/github.com%2Fpixijs-userland%2Fnode)
- headless-gl (`gl`): "aspires to fully conform to the WebGL 1.0.3 specification"; WebGL 2 is experimental via `createWebGL2Context: true`; built on ANGLE; Node 20+ tested, prebuilt binaries for LTS 20/22/24; Linux build needs `build-essential libxi-dev libglu1-mesa-dev libglew-dev pkg-config`; headless servers need Xvfb + Mesa (`xvfb-run -s "-ac -screen 0 1280x1024x24" node ...`); `<image>`/`<video>` not implemented (upload via `texImage2D`); readback via `gl.readPixels` into a `Uint8Array` — [stackgl/headless-gl](https://github.com/stackgl/headless-gl)
- `@pixi/tilemap`: PixiJS v8.x pairs with Tilemap Kit v5.x; a `Tilemap` renders a fixed set of tile textures in one pass and `CompositeTilemap` layers several to get past that limit; `tilemap.tile('grass.png', x, y)`; ~16k tiles per tilemap unless `settings.use32bitIndex = true`; `TEXTURES_PER_TILEMAP` and `TEXTILE_UNITS` are "Temporarily switched off"; canvas fallback "about 5x slower than vanilla RPG Maker"; 352 commits, 50 open issues, no named maintainer, empty Releases and Contributors sections on the repo page — [pixijs-userland/tilemap](https://github.com/pixijs-userland/tilemap); npm: 5.0.2 published 2025-07-14, nothing in 2026 — [npm registry](https://registry.npmjs.org/@pixi/tilemap)
- Pixi's own visual regression harness (`tests/visual/tester.ts`): tests four `RenderType`s (`webgpu`, `webgl2`, `webgl1`, `canvas`), creates renderers with `autoDetectRenderer` (`preference: 'webgl'` + `preferWebGLVersion` 1 or 2), captures with `renderer.extract.canvas(...)` then `getImageData`, compares with `pixelmatch` at `threshold: 0.2`, fails when differing pixel count exceeds `pixelMatch` (default 100), baseline path `./tests/visual/snapshots/${id}-${rendererType}.png`, writes the baseline automatically if missing, and saves an Expected/Actual/Diff image to `.pr_uploads/visual/` on failure; it uses `document.createElement('canvas')` so it needs a DOM — [tester.ts](https://raw.githubusercontent.com/pixijs/pixijs/dev/tests/visual/tester.ts). The runner is Jest 26 with `@pixi/jest-electron` ^26.1.0 plus `pixelmatch` ^5.3.0 and `pngjs`; vitest, playwright and puppeteer are not in devDependencies — [pixijs package.json (8.22.0)](https://raw.githubusercontent.com/pixijs/pixijs/dev/package.json)
- Verified locally (script kept at `/home/user/game-world/docs/research/notes/engine2_pixi_node_smoke.mjs`, Node v22.22.0, pixi.js 8.22.0, @napi-rs/canvas 1.0.13): with a `DOMAdapter` wrapping `createCanvas` plus ~30 lines of stubs (`document.createElement`, `addEventListener` on document/window/canvas, `element.style`, `element.remove`, `requestAnimationFrame`), `autoDetectRenderer({ preference: 'canvas', roundPixels: true })` returned `renderer.name === 'canvas'` in 9 ms and `renderer.render({ container })` completed and wrote a 64x48 PNG via `canvas.toBuffer('image/png')`. `Texture.from(napiCanvas)` throws `Could not find a source type for resource: [object HTMLCanvasElement]` (instanceof sniffing), but `new Texture({ source: new CanvasSource({ resource, scaleMode: 'nearest' }) })` works. The decoded PNG was entirely `[0,0,0,255]` including where the `background: 0x202020` should be; after render `renderer.canvasContext.activeContext !== rootContext` while `rootContext.canvas === renderer.canvas`, i.e. the renderer finished on an internal target and never blitted to the root canvas. The Ticker's rAF stub kept the process alive, so `process.exit` was needed. (Local experiment; no external source.)

### Inferences
- For this project the practical Pixi plan is: `Application.init({ antialias: false, resolution: 1, roundPixels: true })`, `TextureSource.defaultOptions.scaleMode = 'nearest'` (or set per texture source), one `Container` per map layer with `cacheAsTexture()` for static ground/detail layers (re-cached only on chunk changes), a Y-sorted `Container` with `sortableChildren = true` for actors and tall props (a few hundred children is well under the "large numbers" the guide warns about), and a UI render group. Integer scale by setting the canvas CSS size to `logicalSize * k` with `image-rendering: pixelated` rather than through `resolution`.
- `@pixi/tilemap` is usable but effectively unmaintained in 2026 (no release in 15 months, limits switched off, no named maintainer). A chunked renderer (one `Mesh`/`Graphics`-textured quad per 16x16-tile chunk, or `cacheAsTexture` per chunk) is a few hundred lines and avoids the dependency.
- Roof fade is trivial in Pixi: the roof layer is a `Container` whose `alpha` the renderer tweens to 0 when the sim says the followed actor is inside; no filter is needed. Alpha on a container applies per-sprite (overlapping roof tiles would double-blend), so either cache the roof container as a texture first or keep roof tiles non-overlapping.
- Headless Pixi in Node is "possible with adapter work" rather than "supported". The canvas backend got within one blit of working in an hour; finishing it means reading `CanvasRenderer`'s present step and probably shimming `HTMLCanvasElement`/`ImageBitmap` instanceof checks. The WebGL backend in Node means `gl` + Xvfb + Mesa, which is heavier and less deterministic. Playwright + Chromium is the supported path and is how Pixi's own maintainers do visual tests (via Electron, which is the same Chromium).

### Gaps
- Whether `roundPixels` is a renderer/Application-level option in 8.22 is not confirmed from an official page (my local call `autoDetectRenderer({ roundPixels: true })` was accepted without error, which suggests it is, but I did not confirm it affects sprite placement).
- No official or community project was found that snapshot-tests Pixi v8 scenes in plain Node; every found setup (Pixi's own, Excalibur's, the forum reports) uses a browser or Electron.
- No measured bundle or performance numbers for a tilemap of town size in Pixi v8 were found.
- `@pixi/tilemap` maintainer identity and whether it is tested against 8.2x were not found.

## Phaser 4 (4.2.1 as of 2026-07-09)

### Takeaway
Phaser 4.0 shipped 2026-04-10 with a rebuilt render-node WebGL pipeline, a unified Filter system, GPU tilemap layers, Canvas renderer deprecated, and a `pixelArt` flag that now means `antialias:false` + `roundPixels:true` (with `roundPixels` defaulting to false). Tiled JSON loading is unchanged. `Phaser.HEADLESS` exists in 4.x and Phaser's own unit-test helper boots a HEADLESS game, but it "absolutely relies on the DOM being present", so Node use means jsdom and no pixels; there is no screenshot path without a browser. The company is Phaser Studio Inc. (founded Dec 2023, $2M from Open Core Ventures, Richard Davey CTO). It is the heaviest bundle (356 KB gzip) and the most batteries-included.

### Inferences
- For pixel art in Phaser 4: `render: { pixelArt: true }` plus a camera `zoom` of an integer and `Scale.FIT` with a logical size; because `roundPixels` only applies to axis-aligned unscaled objects, interpolated actors should be positioned at integer logical coordinates by the renderer each frame (floor the interpolated position) rather than relying on the flag.
- Y-sorting in Phaser is `setDepth(y)` per actor each frame or `Tilemap.createFromObjects(..., { sortByY })` for static props; a Container with `depth` sorting handles it. Roof hiding is a `TilemapLayer` whose `alpha` is tweened; with `TilemapGPULayer` the layer is one quad so alpha works uniformly.
- Phaser HEADLESS under jsdom gives logic-level tests (scene objects, positions, depth, visibility) with zero pixels. That is still useful for an agent: a test can assert "roof layer alpha is 0 when player is indoors" without rendering. Screenshots require Playwright.
- Phaser's engine owns the loop (Scene `update(time, delta)`), so the sim-event interpolation lives inside a Scene's update, which is fine but means Phaser's clock and the sim clock are two clocks to reconcile; Pixi/raw canvas give the same shape with less framework in the way.
- Migration pain is irrelevant for a greenfield project, but the API churn means much community material (Phaser 3 tutorials, LLM training data) is partly stale, which Phaser itself acknowledges by shipping skills files.

## Excalibur (0.32.0 stable, 0.33.0-alpha.247 as of 2026-09-21)

### Takeaway
Excalibur is a TypeScript-first engine with a first-party TileMap, Tiled and LDtk plugins, a `pixelArt: true` preset (sub-pixel pixel-art sampler shader, v0.29.0), and a serious visual test suite (Vitest browser mode with Playwright, Chromium under Xvfb with `--use-gl=swiftshader`). It is still 0.x with "breaking changes will occur", had no stable release in 2026 (0.32.0 was 2025-12-23; 133 alphas since), and "headless server support" sits on the roadmap under v0.31.0 with no date.

### Cited Findings
- v0.32.0 (23 Dec): DX and performance; actors can set a default graphic/material in the constructor; faster debug draw via a browser extension; performance work on offscreen culling, tilemaps and realistic collisions. v0.31.0 (26 Sep): TileMap culling fixed with parallax, meshes update on transform change, `Query` filters. v0.30.0: `pointerenter`/`pointerleave` on TileMap tiles, `Screen.worldToPagePixelRatio` exposed as CSS var `--ex-pixel-ratio` for scaling HTML UI, GPU particles, NineSlice. v0.29.0: `pixelArt: true`, detailed `antialiasing` config, `uvPadding` for atlases to reduce bleed, TileMap `meshingLookBehind` and `getOnScreenTiles()` — [Excalibur releases](https://github.com/excaliburjs/Excalibur/releases); npm dates: 0.32.0 2025-12-23, `next` 0.33.0-alpha.247 2026-09-21 — [npm registry](https://registry.npmjs.org/excalibur)

## Raw Canvas 2D, with @napi-rs/canvas or node-canvas for Node

### Takeaway
A few-hundred-line Canvas 2D renderer is realistic for this game, and it is the only option where the exact same renderer code runs in Node for pixel-exact tests: `@napi-rs/canvas` 1.0.13 (Skia, prebuilt N-API binaries, releases every 1-3 weeks, 1.0.12 in Oct 2026 explicitly re-aligned fonts/text/drawImage/ImageData with Chrome/Blink) honours `imageSmoothingEnabled = false` with exact nearest-neighbour output (verified locally). node-canvas (Cairo) is at 3.2.3 with a 4.0 RC and needs system libs. The trade is that you write Y-sorting, camera, dirty tracking and text layout yourself, and WebGL-grade effects (lighting) are off the table.

### Cited Findings
- `@napi-rs/canvas`: Skia binding via Node-API; Linux arm64 needs cortex-a57+, glibc 2.18+; `GlobalFonts.registerFromPath(path, family)` and `GlobalFonts.families`; `toBuffer(mime, opts)` / `encode(format, opts)` with PNG/JPEG/AVIF/WebP, `encode` runs in the libuv thread pool; maintainer Brooooooklyn, asks for sponsorship for full-time OSS — [Brooooooklyn/canvas](https://github.com/Brooooooklyn/canvas)
- v1.0.0 (04 May): "about 11 million weekly downloads and a stable API" as the reason; "There are no breaking changes; it's safe for everyone to upgrade" — [v1.0.0 release](https://github.com/Brooooooklyn/canvas/releases/tag/v1.0.0)
- 1.0.8 (24 Aug): `drawImage` snapshots the canvas source; 1.0.9: typeface cache invalidated on font registration; 1.0.10 (01 Oct): use-after-free fix for `CanvasPattern`; 1.0.11: `Path2D.addPath` subpath fix, SBOMs; 1.0.12 (20 Oct): ~30 changes "mostly aimed at matching Chrome": fractional global alpha preserved, pattern snapshots honour image sampling quality, gradient dithering, Skia built with Chrome's CPU raster defines, image sources drawn from Chrome's decode-cache levels, "font parsing, layout, and measurement follow Blink", text rasterized with CoreText and Fontations, paths/clips/`roundRect`/`setTransform` changed, ImageData and Float16 storage, CSS Color 4/5, WebIDL conversion/arity/exception changes, Chrome m157; 1.0.13 (21 Oct): native-method wrapping fix — [releases](https://github.com/Brooooooklyn/canvas/releases); npm: 1.0.13 published 2026-10-21, 25 releases in 2026 — [npm registry](https://registry.npmjs.org/@napi-rs/canvas)
- Verified locally with @napi-rs/canvas 1.0.13 on Node 22.22.0 (script in scratchpad; test drew a 2x2 red/blue checker scaled to 8x8): with `ctx.imageSmoothingEnabled = false`, pixel (3,3) = `[255,0,0,255]`, (4,4) = `[0,0,255,255]`, (3,4) = `[0,0,0,0]` (exact); with smoothing on, (3,3) = `[187,0,66,135]` and (4,4) = `[66,0,187,135]` (blended). The getter reflects the set value. `OffscreenCanvas` is not exported by the package. (Local experiment.)
- node-canvas: 3.0.0 (23 Dec) moved to N-API, dropped Node 16 and below, switched from node-pre-gyp to prebuild-install, and reverted a Linux font-matching change that "doesn't work when fonts are installed"; 3.1.1 (19 Jun) added arm64 Linux prebuilds; 3.2.0 added `ctx.lang`; 3.2.1 (10 Jan) fixed `roundRect()` with large radii and `loadImage` null `src`, GCC 15 build; 3.2.2 (21 Mar) security fixes for untrusted `getImageData`/`putImageData` inputs, `ctx.direction` save/restore; 3.2.3 (31 Mar) GCC build fix — [Automattic/node-canvas releases](https://github.com/Automattic/node-canvas/releases); npm: 3.2.3 2026-03-31, 4.0.0-rc1 2026-07-20, rc3 2026-08-15 — [npm registry](https://registry.npmjs.org/canvas); the 4.0.0-rc1 tag page has no release notes ("17 Jul", by chearon) — [v4.0.0-rc1](https://github.com/Automattic/node-canvas/releases/tag/v4.0.0-rc1); Debian packages 3.2.0/3.2.1 depend on libcairo2 >= 1.15.8 — [Debian NEW queue](https://ftp-master.debian.org/new/node-canvas_3.2.0+dfsg-1.html)
- A 2026 comparison guide says @napi-rs/canvas ships prebuilt binaries via N-API with no compile step, node-canvas is "the original server-side canvas, using the Cairo graphics library" and requires system libraries; its download figures (~800K/week node-canvas, ~500K @napi-rs/canvas) are unverified and conflict with the 11M/week figure in the 1.0.0 notes — [pkgpulse guide](https://www.pkgpulse.com/guides/node-canvas-vs-napi-rs-canvas-vs-skia-canvas-server-2026)
- A plain-canvas pixel-art tutorial recommends integer scales (1x, 2x, 3x, 4x) and rounding positions "since sub-pixel positions cause blur" — [cinevva pixel-art rendering tutorial](https://app.cinevva.com/tutorials/pixel-art-rendering)
- melonJS (which has Canvas2D as a first-class backend) added `scaleRounding: "integer"` in 20.9.0, which "constrains the automatic scale to a whole number of device pixels per source pixel, with letterboxing for the remainder" (only for `scaleMethod: "fit"`), showing the pattern as implemented in a shipping engine — [melonJS releases](https://github.com/melonjs/melonJS/releases)

### Inferences
- Renderer sketch that fits in a few hundred lines: a `RenderBackend` interface over `{ createCanvas(w,h), drawImage, ... }` implemented by the browser canvas and by `@napi-rs/canvas`; one offscreen canvas per static layer chunk (e.g. 16x16 tiles), re-rasterised only when the sim changes a tile; per frame: clear, `drawImage` visible chunks of ground/detail layers at the integer camera offset, draw a Y-sorted array of `{y, draw}` entries for actors and tall props (sort of a few hundred entries per frame is microseconds), then roof chunks with `ctx.globalAlpha = roofAlpha`, then UI. With `imageSmoothingEnabled = false` on every context and all positions floored, output is pixel-exact in both environments.
- Snapshot tests: render the same sim state through the Node backend, `encode('png')`, compare with `pixelmatch` at threshold 0 (expect byte-identical across runs on the same @napi-rs/canvas version). Pin the package version: the 1.0.12 release changed font layout, drawImage sampling and gradient dithering, so a bump can legitimately change baselines. Text is the main cross-environment difference (browser vs Skia-in-Node), so render UI text with a bitmap font drawn via `drawImage`, or exclude UI from pixel-exact assertions.
- Performance: a 100x100-tile town at 16 px tiles is 1600x1600 world px; at a 320x180 or 480x270 logical viewport only ~30x20 tiles are on screen, so even without chunk caching a few hundred `drawImage` calls per frame is far below the 60 fps budget on any desktop browser. Chunk caching mostly saves work on the multiple layers. Dirty rects are unnecessary at these sizes.
- OffscreenCanvas in a worker is possible in browsers for this renderer but adds little; the sim is already separate and deterministic, and the renderer is not the bottleneck.
- Integer-scale letterboxing in CSS: `canvas.style.width = logicalW * k + 'px'` with `k = floor(min(innerW/logicalW, innerH/logicalH))`, `image-rendering: pixelated`, centred in a flex container. No library needed.

### Gaps
- No shipped Steam pixel-art game built on plain Canvas 2D (no engine) with a post-mortem was found in this search; the search returned only hobby projects and engine-based titles.
- `OffscreenCanvas` and `imageSmoothingQuality` support in @napi-rs/canvas was not found in docs; `OffscreenCanvas` is not exported (verified). node-canvas 4.0 release notes could not be read.
- No measured 60 fps numbers for a canvas tile renderer at town scale from an external source; the performance claim above is an inference from draw-call counts.

## Common concerns: roof fade, interpolation, integer scaling, input, WebGPU, Playwright determinism, agent-visible debugging

### Takeaway
Every engine here can do roof fade as layer alpha and Y-sort as a depth/zIndex key; none needs filters for it. Playwright screenshot determinism is an environment problem, not an engine problem: Playwright's own docs say baselines must be generated in the same environment, Excalibur's CI pins `--use-gl=swiftshader` + Xvfb + `--force-device-scale-factor=1`, and multiple sources warn that headless Chromium can silently fall back to a black or 2D canvas without WebGL. WebGPU is production in Pixi and melonJS, absent in Phaser 4 and Excalibur (post-1.0 roadmap). The only engine-independent way to let a blind agent "see" is a text dump of the scene (positions, layer alphas, sort keys) alongside pixel snapshots, which is simplest with a hand-rolled renderer and still possible with Pixi's container tree.

### Cited Findings
- Playwright `toHaveScreenshot`: `threshold` is per-pixel perceived colour difference 0-1, default 0.2; `maxDiffPixels` unset by default; `stylePath` for a capture stylesheet; snapshots are named `<test>-<n>-<browser>-<platform>.png` and "Screenshots differ between browsers and platforms due to different rendering, fonts and more"; "For consistent screenshots, run tests in the same environment where the baseline screenshots were generated"; rendering varies by "host OS, version, settings, hardware, power source, and headless mode" — [playwright.dev test-snapshots](https://playwright.dev/docs/test-snapshots)
- Chromium flag distinction: SwiftShader as the GLES driver (`--use-gl=angle --use-angle=swiftshader`) vs the explicit WebGL fallback (`--use-angle=swiftshader-webgl` plus `--enable-unsafe-swiftshader`, "for trusted test content"); `--disable-gpu` is not a fix — [microlink: WebGL without a GPU](https://microlink.io/blog/webgl-without-a-gpu)
- "Without a display, WebGL silently degrades to a flat 2D fallback: the screenshot still succeeds, the request still returns 200, and the output is wrong but plausible"; their fix was Xvfb + software Mesa on the `--use-angle=gl` path — [microlink: faster WebGL screenshots](https://microlink.io/blog/faster-webgl-screenshots)
- WebGPU in headless browsers "fails silently: the page loads, the screenshot command succeeds, and the canvas is black" without setup — [agent-browser WebGPU guide](https://agent-browser.dev/webgpu)
- Alpine Chromium: "Swiftshader errors will appear in the console in headless mode and WebGL stopped working properly" — [Alpine aports issue 13272](https://gitlab.alpinelinux.org/alpine/aports/-/issues/13272)
- Visual-test guidance: control "time, RNG, async loading, network, animations, fonts, GPU" first; wait on an application-level ready marker, not a fixed delay; screenshot the canvas element with `elementHandle.screenshot()` to exclude DOM overlays; assert the active renderer in the test — [momentic guide](https://momentic.ai/resources/the-definitive-guide-to-webgl-and-canvas-test-automation-from-pixels-to-pipelines)
- A Windows-based writeup found headless Chromium with `--use-angle=angle` gave ~8 fps (no acceleration) and `--use-angle=gl` ~60 fps; verification was manual via `chrome://gpu` — [createit.com](https://www.createit.com/?p=3319)
- Excalibur's working CI flags (copied above): `headless: false` under Xvfb, `--use-gl=swiftshader`, `--force-device-scale-factor=1`, `--window-size=1920,1080`, `--disable-gpu` deliberately left off; it ignores Playwright's default `--disable-remote-fonts` and `--font-render-hinting` — [vitest.config.visual.ts](https://raw.githubusercontent.com/excaliburjs/Excalibur/main/src/spec/vitest.config.visual.ts)
- Pixi's harness tolerates up to 100 differing pixels at pixelmatch threshold 0.2 and tests webgl1/webgl2/webgpu/canvas separately with per-renderer baselines — [tester.ts](https://raw.githubusercontent.com/pixijs/pixijs/dev/tests/visual/tester.ts)
- WebGPU status by engine: Pixi v8 ships WebGPU and keeps investing (8.20.0 render bundles etc.) — [GameDev.net](https://gamedev.net/news/5221-pixijs-v8200-released/); melonJS tries WebGPU first by default — [melonJS README](https://cdn.jsdelivr.net/npm/melonjs@20.5.0/README.md); Phaser 4 is WebGL (WebGL2-compatible canvases, no WebGPU mentioned) — [CHANGELOG v4.0.0](https://raw.githubusercontent.com/phaserjs/phaser/HEAD/changelog/v4/4.0/CHANGELOG-v4.0.0.md); Excalibur lists "WebGPU renderer (pending browser support)" post-1.0 — [issue #1161](https://github.com/excaliburjs/Excalibur/issues/1161)
- Phaser 4 filters can target any game object or camera; internal filters run before the camera transform, external after — [v4-new-features SKILL.md](https://cdn.jsdelivr.net/npm/phaser@4.2.0/skills/v4-new-features/SKILL.md); Pixi filters are objects with `glProgram` and typed `resources` — [migration guide](https://pixijs.com/8.x/guides/migrations/v8)
- Phaser 4 `roundPixels` "only applies to axis-aligned, unscaled objects, which prevents flicker on transforming objects" — [CHANGELOG v4.0.0](https://raw.githubusercontent.com/phaserjs/phaser/HEAD/changelog/v4/4.0/CHANGELOG-v4.0.0.md); Excalibur's `pixelArtSampler` exists precisely to get "smooth subpixel rendering of pixel art without shimmer/fat-pixel artifacts" — [Excalibur 0.29.0 notes via NuGet mirror](https://www.nuget.org/packages/Excalibur/0.29.0)

### Inferences
- Event-driven interpolation is engine-neutral: keep `{from, to, t0, t1}` per actor from the sim's tile-arrival events; each rAF compute `p = lerp(from, to, clamp((now - t0)/(t1 - t0)))`, then floor to integer logical pixels before drawing. Flooring removes the sub-pixel shimmer that `roundPixels` flags only partially address, and keeps browser and Node output identical. Excalibur's pixel-art sampler is the one engine that tries to render sub-pixel motion nicely instead; whether that looks better than flooring is taste.
- Roof occlusion: all four engines express it as "roof layer alpha = f(indoor)"; a per-building roof container (not one global roof layer) lets the renderer fade only the building the followed actor is in. With a cached-texture container (Pixi `cacheAsTexture`, Phaser `TilemapGPULayer`, raw offscreen canvas) the alpha applies to the composite so overlapping roof tiles do not double-blend.
- Playwright recipe for this project, synthesised from the above: Chromium with `--use-gl=angle --use-angle=swiftshader` (or Excalibur's Xvfb variant if the first fails), `deviceScaleFactor: 1`, a fixed viewport that is an integer multiple of the logical size, a bundled bitmap or web font loaded before the ready marker, `page.evaluate(() => window.__render(stateJSON))` to draw a deterministic frame with the ticker stopped, assert `renderer.type` (or `gl.getParameter(RENDERER)` contains SwiftShader) before capture, `canvas.screenshot()` compared with `maxDiffPixels: 0` for Canvas2D and a small `maxDiffPixels` for WebGL (Pixi uses 100). Baselines generated only inside the CI container image.
- Agent-visible debugging: expose `window.__scene()` returning JSON (camera, visible chunks, each actor's interpolated position and sort key, each layer's alpha, UI state) and dump it in test failures beside the diff PNG. Pixi's container tree and Phaser's display list can be walked for this; a hand-rolled renderer has it for free because the draw list is a plain array.
- Input: click-to-walk hit testing is `tile = floor((clientX/scale + camX)/tileSize)` in all cases; Pixi/Phaser/Excalibur event systems add nothing for tiles (Excalibur does have per-tile pointer events since 0.29.2). Keyboard is `keydown`/`keyup` on window in every option.

### Gaps
- No source documents a flag set that makes WebGL screenshots bit-identical across two different machines; the consistent advice is "same container image for baselines and tests".
- No source was found on Playwright + SwiftShader determinism specific to Pixi or Phaser output.
- Font rendering differences between Chromium (browser tests) and @napi-rs/canvas (Node tests) are implied by 1.0.12's "follow Blink" changes but not measured.

## Desktop packaging (Tauri 2, Electron) and Steam

### Takeaway
Electron (or NW.js) is the proven path to Steam for JS games (Vampire Survivors on Phaser, CrossCode on NW.js, Desktop Heroes on Phaser+Electron in Oct 2025); Phaser ships both Electron and Tauri templates. Tauri 2 gives 3-10 MB binaries but uses the system webview (WebView2/WKWebView/webkit2gtk), so WebGL/WebGPU behaviour must be tested on three engines, and no shipped Tauri Steam game or Steamworks binding for Tauri was found. The renderer choice does not change the packaging choice; all options are plain web pages.

- Phaser has released a template for Tauri, "an Electron alternative built on Rust" — [Phaser World newsletter (search result)](https://phaserworld.beehiiv.com/p/phaser-world-issue-235)
- Phaser 4.2.1 removed inline `Phaser` namespace access for ESM-build compatibility — [CHANGELOG v4.2.x (search summary)](https://raw.githubusercontent.com/phaserjs/phaser/HEAD/changelog/v4/4.2/CHANGELOG-v4.2.0.md)

### Inferences
- For a Canvas2D or WebGL renderer, Electron is the lowest-risk desktop wrapper because it is the same Chromium the Playwright tests run against; Tauri adds webkit2gtk on Linux and WKWebView on macOS as untested renderers. A Canvas2D renderer is the least sensitive to that spread, Pixi WebGPU the most.
- If Steam is a real goal, plan on Electron + steamworks.js; Tauri can be a later size optimisation once a Steamworks binding exists.

### Gaps
- No Tauri 2 game found on Steam; the Steamworks-for-Tauri claim is from an undated forum post.
