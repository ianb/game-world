# Shipping a Rust-wasm + TypeScript pixel-art game to web and mobile (researched 2026-10-23)

Scope: packaging paths from a web build to iOS/Android, renderer compatibility inside WKWebView and Android WebView, wasm execution limits, what a headless-Linux-only agent can build and test, store policy, and how the renderer-library choice changes under mobile constraints. The Rust simulation design and the Rust/TS boundary are out of scope.

Source quality note: official docs (Apple, WebKit, Capacitor, Tauri, Google Play, Playwright, vendor pricing pages) were fetched directly where possible. Several claims below rest on vendor blogs or single forum reports and are flagged as such.

## Q1. Packaging paths from a web build to mobile: PWA, Capacitor, Cordova, Tauri 2, React Native/Expo, native wasm shells

### Takeaway
Capacitor is the only path that is both mature for games and fully buildable for Android from Linux; iOS always needs a macOS toolchain somewhere (cloud). Tauri 2 mobile is real but documented for app UIs, not games, and also needs macOS for iOS. Cordova still ships releases but is in decline. React Native/Expo adds nothing for a canvas/WebGL game (it ends up as a WebView or a partial-WebGL2 GLView). Native wasm shells on iOS (wasmer Swift SDK) are experimental and themselves run inside a hidden WKWebView.

### Cited Findings

**Capacitor (current: 8.x)**
- Capacitor 8 announced 8 December 2025; makes Swift Package Manager the default iOS dependency manager (CocoaPods still works); adds Android edge-to-edge handling through an internal `SystemBars` plugin and public `SystemBars` API; ~930k weekly npm downloads in mid-Nov 2025. — [Ionic blog: Announcing Capacitor 8](https://ionic.io/blog/announcing-capacitor-8)
- Capacitor 8 iOS: "iOS 15+ is supported", requires Xcode 26.0+, uses WKWebView. — [Capacitor iOS docs](https://capacitorjs.com/docs/ios)
- Capacitor 8 Android: API 24+ (Android 7), "requires an Android WebView with Chrome version 60 or later"; on Android 7-9 Chrome provides the WebView, on Android 10+ Android System WebView. — [Capacitor Android docs](https://capacitorjs.com/docs/android)
- Capacitor 8.5 (July 2026) targeted iOS 27 scene adoption (third-party summary). — [PlushCap summary of Ionic blog](https://www.plushcap.com/companies/ionic/blog/summaries/2026/07)
- How Capacitor serves the web bundle: iOS uses a custom scheme, default `capacitor://localhost` (`server.iosScheme`, cannot be http/https); Android uses `https://localhost` (`server.androidScheme`; non-standard schemes "can break routing on Webview 117 and later"). `server.hostname` defaults to `localhost`, recommended because it keeps a secure context for APIs that need it. `server.url` (remote URL) is for live reload, "not for production". Options relevant to a game: `zoomEnabled` (default false), `backgroundColor`, `preferredContentMode` (iOS), `limitsNavigationsToAppBoundDomains` (iOS). No header-related options are documented. — [Capacitor config docs](https://capacitorjs.com/docs/config)
- Capacitor's own games page is thin: "broad WebGL and canvas rendering support", names Phaser as the one engine, links the Phaser tutorial. — [Capacitor games guide](https://capacitorjs.com/docs/guides/games)
- Phaser's official Capacitor tutorial: `npx cap init/add/copy/open`; uses `viewport-fit=cover` plus `padding-top: max(env(safe-area-inset-top))` for notch/Dynamic Island; sizes the game to `innerWidth/innerHeight * devicePixelRatio` with `Scale.FIT`; uses `pointerup` to start and `drag` to move; recommends testing on a physical device. Does not cover orientation lock, status bar, audio or performance. — [Phaser tutorial: Bring your Phaser game to iOS and Android with Capacitor](https://phaser.io/tutorials/bring-your-phaser-game-to-ios-and-android-with-capacitor)
- Plugin ecosystem: Capawesome ships keep-awake (Android/iOS/web), screen-orientation lock (portrait/landscape), and haptics plugins; Capgo keep-awake uses Screen Wake Lock API on web. No dedicated safe-area plugin surfaced in results (CSS `env()` is the usual route). — [Capawesome keep-awake](https://capawesome.io/docs/sdks/capacitor/keep-awake/); [Capawesome screen-orientation](https://capawesome.io/docs/sdks/capacitor/screen-orientation/); [Capawesome haptics](https://capawesome.io/docs/sdks/capacitor/haptics/); [Capgo keep-awake](https://capgo.app/plugins/capacitor-keep-awake)
- Apple requires the iOS 26 SDK / Xcode 26 for all App Store Connect uploads (new apps and updates) from 28 April 2026; this is about the build SDK, not the deployment target. — [Capgo: Xcode 26 requirement for Capacitor apps](https://capgo.app/blog/xcode-26-requirement-for-capacitor-apps/); [Capawesome blog](https://capawesome.io/blog/xcode-26-requirement-for-capacitor-apps/); [Apple forum thread asking for clarification](https://developer.apple.com/forums/thread/806141)
- App size: a 2018-era Capacitor issue reported ~122 MB local release .ipa vs ~3 MB .apk for a stock app; the maintainer said the local .ipa does not reflect App Store download size (App Thinning). A forum report puts a signed Android Capacitor build at ~2.7-5 MB. No current measured empty-project numbers found. — [Lightrun mirror of ionic-team/capacitor "iOS app bundle size"](https://lightrun.com/answers/ionic-team-capacitor-ios-app-bundle-size); [Ionic forum: Huge app size with Capacitor compared to Cordova](https://forum.ionicframework.com/t/huge-app-size-with-capacitor-compared-to-cordova/171705)

**Cordova**
- Capgo (a Capacitor vendor) lists cordova-android 15.1.0 and cordova-ios 8.1.1 releases in July 2026, i.e. still maintained; not confirmed against an Apache source. — [Capgo Cordova alternatives page](https://capgo.app/alternatives/cordova/)
- Statista-derived survey figures: developers using Cordova fell from 29% (2019) to 10% (2023); App Center's 2021 Cordova retirement notice triggered a drop in Cordova CLI downloads. — [MobiDev Cordova alternatives guide](https://mobidev.biz/blog/apache-cordova-alternatives-cross-platform-mobile-app-development)
- Capacitor docs: "only a few Cordova plugins are incompatible" when migrating; VS Code extension flags deprecated Cordova plugins. — [Capacitor: Migrate from Cordova](https://capacitorjs.com/docs/vscode/cordova)

**Tauri 2 mobile**
- Tauri 2 went stable October 2024; latest stable listed as v2.10.1 (4 March 2026). — [Wikipedia: Tauri](https://en.wikipedia.org/wiki/Tauri_(software_framework))
- Prerequisites: Android needs Android Studio SDK/NDK, `ANDROID_HOME`/`NDK_HOME`, Rust targets `aarch64-linux-android` etc. (works on Linux). iOS: "iOS development requires Xcode and is only available on macOS"; full Xcode, CocoaPods; Rust targets `aarch64-apple-ios`, `aarch64-apple-ios-sim`. — [Tauri v2 prerequisites](https://v2.tauri.app/start/prerequisites/)
- WebView engines: Android uses the device's system Android WebView (Chromium-based, not bundled; feature support depends on the installed provider); macOS/iOS use WKWebView; Linux WebKitGTK; Windows WebView2. The page gives no iOS-specific minimum. — [Tauri webview versions reference](https://v2.tauri.app/reference/webview-versions/)
- Android minSdkVersion is configurable in `bundle.android` (a user issue shows `minSdkVersion: 23`); iOS has `iOS.minimumSystemVersion` config. Defaults were not confirmed in the fetched sources. — [tauri-apps/tauri #10632](https://github.com/tauri-apps/tauri/issues/10632); [tauri-cli 2.0.0-rc.3 release notes](https://v2.tauri.app/es/release/tauri-cli/v2.0.0-rc.3)
- Open issue (Dec 2025, still updated Sept 2026): "iOS Debug build fails when running on iPhone device". — [tauri-apps/tauri #14675](https://github.com/tauri-apps/tauri/issues/14675)

**React Native / Expo**
- A 2026 write-up argues there is no mature RN game engine: react-native-game-engine mounts a View per entity and struggles at ~50 active entities on mid-range Android; Phaser 4 in a WebView is "the web's engine running in a sandbox inside your app"; expo-gl is the other option. — [DEV: The React Native game engine gap in 2026](https://dev.to/grzott/the-react-native-game-engine-gap-in-2026-rnge-skia-phaser-in-webview-expo-gl-55hp)
- expo-gl `GLView` exposes a context "implementing WebGL 2.0 specification"; a PlayCanvas forum thread reports it is faster than a WebView but "has many unsupported WebGL2 methods". — [expo-gl on jsDelivr](https://www.jsdelivr.com/package/npm/expo-gl); [PlayCanvas forum: React Native with PlayCanvas](https://forum.playcanvas.com/t/react-native-with-playcanvas/15288)

**Native wasm shells**
- Wasmtime uses Cranelift (JIT) on x86_64/aarch64 and the Pulley interpreter elsewhere; Pulley was "not feature complete" at Wasmtime 26.0. No official Wasmtime iOS/Android support statement found. — [Wasmtime: Using Pulley](https://docs.wasmtime.dev/examples-pulley.html); [Wasmtime 26.0 release](https://bytecodealliance.org/articles/wasmtime-26.0)
- Wasmer Swift SDK (released 23 September, year inferred 2026): runs WASIX in a hidden WKWebView using WebKit's own wasm engine (JIT + JSPI); requires iOS 27+, experimental, demos were simulator screenshots. Single secondary source. — [RuntimeWire: Wasmer Swift SDK](https://runtimewire.com/article/wasmer-swift-sdk-ios-macos)
- Rust-viewer comparison points: Bevy's mobile example builds iOS via `xcodebuild`/`xcrun simctl` (Makefile targets `x86_64-apple-ios` sim and `aarch64-apple-ios` device) and carries an `.xcodeproj`; Bevy's example-runner dashboard lists iOS and Android as supported while WebGL2/WebGPU/DX12 are in progress. — [Bevy examples/mobile Makefile](https://raw.githubusercontent.com/bevyengine/bevy/main/examples/mobile/Makefile); [Bevy example tester](https://example-runs.bevy.org/about.html)
- macroquad: iOS build is hand-rolled (folder `MyGame.app` + Info.plist + cargo binary), needs macOS 10.15+/Xcode 11+, `xcrun simctl`, `codesign`, `ios-deploy`, a provisioning profile; Developer Mode toggle on iOS 16+ only appears after connecting to a Mac with Xcode. Android: documented one-command deploy; author warns the stack "isn't well tested on a wide enough variety of mobile phones yet". — [macroquad iOS article](https://macroquad.rs/articles/ios/); [macroquad Android article](https://macroquad.rs/articles/android/); [Rust forum: Zemeroth](https://users.rust-lang.org/t/zemeroth-a-2d-turn-based-strategy-game/28311/10)

### Inferences
- For this project, the realistic mobile path is: PWA for web and Android-first, Capacitor for stores, with iOS builds outsourced to a macOS cloud runner. Tauri 2 is a plausible alternative only if the team wants Rust in the shell; it buys nothing for a game that is already wasm-in-JS and gives up Capacitor's game-specific tutorials and plugin coverage.
- Because Capacitor serves from `capacitor://localhost` (iOS) / `https://localhost` (Android), the web build is the same artifact as the PWA; service workers and manifest can be left in, with the caveat about header control noted in Q2.
- Nothing here changes the Rust side: the wasm module runs in WebKit/Chromium's engine in every path except a hypothetical Rust-native viewer.

### Gaps
- No official Capacitor 8 minimum-version table for Android Studio/Java was fetched.
- No measured 2025-2026 empty-app size for Capacitor on iOS (store download size).
- Tauri default Android minSdk and iOS minimum not confirmed from the docs.

## Q2. Canvas 2D / WebGL2 / WebGPU and wasm execution inside WKWebView and Android WebView (2026)

### Takeaway
WebGL2 is the safe renderer target on both platforms; WebGPU shipped in Safari 26 / iOS 26 (Sept 2025) and is on by default in WKWebView from iOS 26 but has isolated crash reports, and on Android it is still gated by Chrome version and GPU vendor with WebView status unconfirmed. Wasm runs with full JIT in WKWebView; the hard constraints are WebGL context loss on backgrounding, an opaque WebContent memory ceiling, and that cross-origin isolation (SharedArrayBuffer/threads) is hard to obtain in Capacitor's local-serving setup.

### Cited Findings

**WebGPU**
- Safari 26.0 ships WebGPU on macOS, iOS, iPadOS, visionOS; compute shaders; WGSL; WebKit "recommends WebGPU over WebGL for new sites"; Babylon.js, Three.js, Unity, PlayCanvas work. Same release: WebAssembly gets a new in-place interpreter so "large modules launch faster and use less memory" with same peak throughput after warm-up. — [WebKit: features in Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)
- WKWebView: Safari feature flags "only impact Safari and not WebKit generally. For WKWebView, the feature will work when it's enabled by default... Can you please try on the iOS 26 beta? WebGPU is enabled by default there." (June 2025 reply; the original Dec 2024 report was that WKWebView had no GPU access on iOS 18.2 even with the Safari flag.) — [Apple Developer Forums thread 770862](https://developer.apple.com/forums/thread/770862)
- A later Apple forum report describes a WebContent/GPU process crash with WebGPU on iPhone 15 running iOS 26.4 while iPad on 26.4 works (single unverified report). — [Apple forums Safari and Web topic](https://developer.apple.com/forums/topics/safari-and-web-topic)
- Chrome: WebGPU in Chrome 113 (ChromeOS/Windows/macOS); Android in Chrome 121 "on devices running Android 12 and greater powered by Qualcomm and ARM GPUs"; Linux "coming soon"; page last updated 11 Aug 2025. — [Chrome WebGPU overview](https://developer.chrome.com/docs/web-platform/webgpu/overview)
- WebGPU Compatibility mode (subset running on OpenGL ES 3.1 / D3D11) intent-to-ship says it is "immediately available on Android, Android WebView, ChromeOS, Mac, and Windows, where hardware support is available"; a Khronos SIGGRAPH 2026 deck dates Compatibility Mode on older Android to 2026-02. — [blink-dev: Intent to Ship WebGPU Compatibility mode](https://groups.google.com/a/chromium.org/g/blink-dev/c/N3RlLGCOTJ4/m/loneRTlPBwAJ); [Khronos WebGL and WebGPU SIGGRAPH 2026](https://www.khronos.org/developers/linkto/webgl-and-webgpu-sigg26)
- PixiJS open issues: WebGPU in Safari TP 201 rendered transparent pixels as opaque black (#10864, open); fallback from WebGPU to WebGL "doesn't occur in some instances" (#10906, open, updated Dec 2025). — [pixijs #10864](https://github.com/pixijs/pixijs/issues/10864); [pixijs #10906](https://github.com/pixijs/pixijs/issues/10906)

**WebGL and context loss in WKWebView**
- iOS 17 regression: "WebGL: context lost" after backgrounding Safari viewing a WebGL app; reproduced with Babylon, Three and vanilla WebGL. — [WebKit bug 261331](https://bugs.webkit.org/show_bug.cgi?id=261331); [three.js forum thread](https://discourse.threejs.org/t/context-lost-when-backgrounding-safari-on-ios-17-developer-beta-8/55772)
- PlayCanvas report: works in Safari but "on WKWebView from 16.x.x to 17.2 bug still appears", thread ends without a fix. — [PlayCanvas forum: WebGL context lost in iOS 17 (WKWebView)](https://forum.playcanvas.com/t/webgl-context-lost-in-ios-17-wkwebview/34247)
- iOS 18.3.x: WebGL2 context lost on buffer upload; root cause a `flat` varying in a vertex shader crashing above ~30k vertices; fixed via `WEBGL_provoking_vertex` first-vertex convention or removing `flat`; duplicate of bug 286297 (fixed). Reproduced in Safari and in a Flutter InAppWebView. — [WebKit bug 289601](https://bugs.webkit.org/show_bug.cgi?id=289601)
- Phaser 4's renderer "supports context restoration out of the box"; if the context is lost "when a tab is switched or a mobile app goes to the background, it recovers automatically". — [Phaser 4 renderer article, 23 April 2026](https://phaser.io/news/2026/04/phaser-4-renderer-faster-cleaner-and-built-for-modern-games)
- PixiJS: a maintainer said v5 "can recover from lost context... For v4 we can't guarantee that at all" (2021). Current open v8 issues: "blank scene after WebGL context loss during shader compilation" (#12281, Oct 2026) and "After a period of inactivity, WebGL will be reclaimed, resulting in a blank interface" (#11731, v8.13.2, no maintainer answer). — [html5gamedevs: iOS 14 beta and pixi 5 lost context](https://www.html5gamedevs.com/topic/46121-ios-14-beta-and-pixi-5-webgl-lost-context); [pixijs #12281](https://github.com/pixijs/pixijs/issues/12281); [pixijs #11731](https://github.com/pixijs/pixijs/issues/11731)
- Generic handling: listen for `webglcontextlost`, call `preventDefault()`, rebuild on `webglcontextrestored`, and/or recreate on foreground. — [Textastic feedback thread](https://feedback.textasticapp.com/communities/1/topics/4001-webgl2-graphics-context-is-sometimes-lost-in-the-built-in-html-viewer-after-backgrounding-the-app)

**Memory limits**
- Apple forum reply: the WKWebView memory limit "cannot be increased" and "is not a fixed number", depending on device RAM and load; large WebGL scenes trigger `webViewWebContentProcessDidTerminate`. — [Apple forums thread 133449](https://developer.apple.com/forums/thread/133449)
- 2026 report: WebContent process killed by jetsam at a 2048 MB ActiveHard limit on iPhone 17 Pro (12 GB RAM), not on iPads (single user). — [Apple forums thread 823061](https://developer.apple.com/forums/thread/823061)
- Common mitigation: implement the termination delegate and reload. — [Apple forums thread 771787](https://developer.apple.com/forums/thread/771787)

**Wasm, JIT, SharedArrayBuffer**
- WKWebView runs out-of-process and gets JavaScriptCore's JIT (in-process JSContext does not); Apple reserves JIT for its own apps and embedded web views. — [Lucidchart tech blog](https://www.lucidchart.com/techblog/?p=5908); [Replay blog](https://replay.js.org/blog)
- Large wasm (Unity, >15 MB) in WKWebView showed low framerate and heat for the first minutes while the optimizing OMG JIT tier worked; no way found to pin to BBQ tier. — [Apple forums thread 721315](https://developer.apple.com/forums/thread/721315)
- SharedArrayBuffer requires cross-origin isolation (COOP `same-origin` + COEP `require-corp`); Safari added COOP/COEP in 15.2. — [WebKit: Safari 15.2](https://webkit.org/blog/12140/new-webkit-features-in-safari-15-2/); [Wasmer JS SDK troubleshooting](https://docs.wasmer.io/javascript-sdk/explainers/troubleshooting)
- Capacitor issue #6182 (iOS 15.2, Capacitor 4.6.1): headers set in `WebViewAssetHandler` were lost on an internal WebView reload at startup; reporter reproduced it in a plain `WKURLSchemeHandler` project (WebKit behaviour, not Capacitor); workaround was the old `cordova-plugin-ionic-webview` local HTTP server adding COOP/COEP; reporter also stated Android WebView "does not currently support the COOP header". Closed by reporter Jan 2023, no maintainer fix. — [ionic-team/capacitor #6182](https://github.com/ionic-team/capacitor/issues/6182)
- A third-party SDK states "Android WebView is not supported because the Web SDK requires SharedArrayBuffer and cross-origin isolation". — [Shen.ai web troubleshooting](https://developer.shen.ai/getting-started/web-troubleshooting)

**Canvas 2D**
- Only old data: 2014 Nexus 5 Chrome test by Construct's author: WebGL ~17,500 objects at 30 FPS vs ~360 for Canvas 2D (advocacy context). — [WHATWG archive, Ashley Gullen](https://lists.w3.org/Archives/Public/public-whatwg-archive/2014Aug/0038.html)
- PixiJS v8.16.0 added an experimental Canvas renderer for environments without WebGL/WebGPU. — [PixiJS blog tags](https://pixijs.com/blog/tags/tagged-text)

### Inferences
- Target WebGL2 with a WebGL1-compatible asset path; treat WebGPU as an opt-in experiment behind a flag until Android WebView status and iOS 26.x stability are confirmed. For a few hundred sprites at integer scale, WebGPU brings no measurable benefit.
- Plan for single-threaded wasm on mobile. Capacitor cannot reliably set COOP/COEP on iOS and Android WebView lacks COOP, so SharedArrayBuffer/wasm-threads should be treated as unavailable in the wrapped app. A web worker with message passing (postMessage/transferable ArrayBuffer) is the portable alternative.
- Context loss on backgrounding is a certainty on iOS; whatever renderer is chosen must either recover automatically (Phaser 4 claims this) or the viewer must own a "rebuild all GPU resources from the atlas" path. The Rust sim is unaffected since it holds no GPU state.
- Keep the WebContent process well under ~1 GB: a few hundred sprites and a tile atlas fit easily, but texture-heavy interiors or many RenderTextures are the risk.

### Gaps
- No primary source on WebGPU availability in Android System WebView (as opposed to Chrome).
- No 2024-2026 benchmark of Canvas 2D vs WebGL for sprites on phones.
- No confirmed WKWebView WebGPU test on shipping iOS 26.x beyond the beta statement and one crash report.

## Q3. What headless Linux means for building and testing iOS and Android

### Takeaway
Android is fully buildable and testable from Linux (SDK, emulator with KVM on x86_64 CI, or Redroid in Docker). iOS cannot be built, signed, simulated or debugged without macOS; cloud macOS (GitHub Actions $0.062/min, Codemagic $0.095/min with 500 free M2 minutes, EAS $2 per iOS build) closes the build gap, and device clouds (Firebase Test Lab $5/physical-device-hour, AWS Device Farm $0.17/min, BrowserStack from $175/mo) close the on-device test gap. Playwright's WebKit on Linux is useful for layout and logic but is not iOS Safari.

### Cited Findings

**Playwright WebKit fidelity**
- Playwright WebKit is "derived from the latest WebKit main branch sources", often ahead of Safari; it does not run branded Safari; "for the closest-to-Safari experience you should run WebKit on mac"; media codecs vary substantially between Linux, macOS and Windows. — [Playwright: Browsers](https://playwright.dev/docs/browsers)
- Device emulation sets viewport, `deviceScaleFactor`, `isMobile` ("whether the meta viewport tag is taken into account and touch events are enabled"), `hasTouch`, user agent. — [Playwright: Emulation](https://playwright.dev/docs/emulation)
- Vendor and personal reports: emulation misses iOS-specific rendering, virtual keyboard, notch/safe-area handling, memory pressure, backgrounding; form widgets render differently. — [Hyperping mobile emulation guide](https://hyperping.com/learn/playwright/playwright-mobile-emulation); [BrowserStack Playwright iOS guide](https://www.browserstack.com/guide/playwright-ios-automation); [Soledad Penades: using simulators to test Safari](https://soledadpenades.com/posts/2024/using-simulators-to-test-in-safari)

**Android emulator in CI/containers**
- `ubuntu-latest` x86_64 GitHub runners expose `/dev/kvm`; a udev rule granting access is needed; Ubuntu runners are "2-3 times faster than the macOS ones". `reactivecircus/android-emulator-runner@v2` is the standard action. — [ReactiveCircus/android-emulator-runner](https://github.com/ReactiveCircus/android-emulator-runner)
- GitHub ARM runners (`ubuntu-24.04-arm`) do not expose `/dev/kvm`. Options without KVM: Redroid (`redroid/redroid` images Android 8.1-16, `--privileged`, needs `binder_linux`/`ashmem_linux` kernel modules, near-native speed, `redroid_gpu_mode=guest` for headless; project largely inactive since mid-2025) or the SDK emulator with `-no-accel -no-window -gpu swiftshader_indirect` ("much slower"). Android Emulator 36.6.x (June 2026) enforces 4 GB RAM minimum for API 37 AVDs. — [Codersera: Android emulator in Docker without KVM (June 2026)](https://codersera.com/blog/android-emulator-docker-without-kvm/)

**Cloud macOS build pricing (fetched Oct 2026)**
- GitHub Actions: macOS 3/4-core (M1 or Intel) $0.062/min vs Linux 2-core $0.006/min; free minutes 2,000 (Free) / 3,000 (Pro, Team) / 50,000 (Enterprise) per month; standard runners free in public repos, larger runners always charged. — [GitHub: About billing for GitHub Actions](https://docs.github.com/en/billing/managing-billing-for-your-products/about-billing-for-github-actions)
- Codemagic: 500 free Mac mini M2 minutes/month, then $0.095/min (M2), $0.114/min (M4), $0.045/min Linux/Windows; fixed plans $3,990/yr (M2, unlimited minutes), $5,400/yr (M4), $9,000/yr (M4 Max); 1 concurrency on free/PAYG (+$49/mo each up to 3); 120-minute build timeout. — [Codemagic pricing](https://codemagic.io/pricing/)
- Codemagic documents building and publishing iOS from Linux/Windows with App Store Connect API-key signing, but "you will still need a Mac if you need to do any debugging of your app on a iOS Simulator or real device". — [Codemagic: build iOS without a Mac (Flutter)](https://blog.codemagic.io/how-to-build-and-distribute-ios-apps-without-mac-with-flutter-codemagic/); [Codemagic: automatic code signing without a Mac](https://blog.codemagic.io/automatic-code-signing-for-ios-that-doesnt-require-a-mac/)
- EAS Build: Free plan "up to 15 Android and 15 iOS builds", 45-minute timeout, 1 macOS concurrency; Starter $19/mo with $45 credit; Production $199/mo with $225 credit; usage pricing Android $1 (medium)/$2 (large), iOS $2/$4 per build. — [Expo pricing](https://expo.dev/pricing)
- Bitrise: Pro from $218/mo ($200 annual), ~250 builds/month (Codemagic-authored benchmark, competitor source). — [Codemagic build-speed benchmark](https://blog.codemagic.io/build-speed-benchmark-comparison/)
- Xcode Cloud: 25 compute hours/month included with Apple Developer Program (third-party summary). — [Expo blog: best CI/CD for mobile apps](https://expo.dev/blog/best-ci-cd-for-mobile-apps)
- Capawesome Cloud offers Capacitor iOS builds with managed signing "from Windows, Linux, or a Chromebook" (vendor). — [Capawesome build without Mac](https://capawesome.io/solutions/build-without-mac/)

**Device clouds**
- Firebase Test Lab is deprecated, shutting down 30 September 2027 (migrate to Developer Device Platform on Google Cloud). Spark: 15 runs/day (10 virtual, 5 physical). Blaze: 30 physical + 60 virtual free minutes/day, then $5/hour physical, $1/hour virtual, rounded to the minute. iOS covered under the same quota. — [Firebase Test Lab usage, quotas, pricing](https://firebase.google.com/docs/test-lab/usage-quotas-pricing)
- AWS Device Farm: $0.17 per device-minute, 1,000-minute one-time trial; unmetered $250 per device slot per month. — [Quash: Firebase Test Lab alternatives](https://quashbugs.com/blog/best-firebase-test-lab-alternatives); [G2: AWS Device Farm pricing](https://www.g2.com/products/aws-device-farm/pricing)
- BrowserStack Automate (web): Desktop & Mobile $175/mo, Desktop & Mobile Pro $225/mo (annual, 1 parallel); App Automate quoted by third parties at $199/mo for 1 parallel, ~$995/mo for 5. — [BrowserStack pricing](https://www.browserstack.com/pricing?product=app-automate); [devicelab.dev App Automate pricing 2025](https://devicelab.dev/blog/browserstack-app-automate-pricing-2025)

### Inferences
- An agent in a Linux container can own the whole Android loop end to end (Gradle build, emulator or Redroid, adb screenshots/logcat, Playwright against the dev server). For iOS the agent's loop is: push, trigger a macOS cloud job, read logs/artifacts, run on a device cloud, read screenshots and console logs. Every iOS iteration is minutes and cents rather than seconds; design the viewer so that almost all bugs reproduce in Playwright-WebKit or Android first.
- Cheapest defensible iOS setup today: Codemagic free 500 M2 minutes/month for builds plus Firebase Test Lab Blaze free 30 physical minutes/day (until 2027) or AWS Device Farm pay-per-minute for on-device smoke runs.
- Playwright `webkit` with `devices['iPhone 15']` on Linux is good for layout, DPR math, Pointer Events and touch-target logic; it says nothing about WKWebView memory, context loss, audio unlock or safe-area rendering.

## Q4. Store policy: Apple 4.7 / 2.5.2 / 4.2, EU DMA distribution, Google Play WebView rules

### Takeaway
A Capacitor game that bundles its HTML/JS/wasm in the binary is governed by 2.5.2 (self-contained, no downloaded code) and 4.2 (minimum functionality), not by 4.7; 4.7 governs host apps that serve HTML5 mini-games they did not embed, and was tightened in late 2025. Google Play's "Webviews and Affiliate Spam" rule targets apps that wrap someone else's website; a self-contained game is not what it describes.

### Cited Findings
- Apple 4.7 (current text): "Apps may offer certain software that is not embedded in the binary, specifically HTML5 and JavaScript mini apps and mini games, streaming games, chatbots, and plug-ins... You are responsible for all such software offered in your app." 4.7.1 requires privacy rules, filtering/reporting/blocking, and 3.1 for digital goods; 4.7.2 "may not extend or expose native platform APIs or technologies to the software without prior permission from Apple"; 4.7.3 no data/permission sharing without per-instance consent; 4.7.4 index of software with universal links; 4.7.5 age-rating identification and age-restriction mechanism. — [App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)
- Apple 2.5.2: "Apps should be self-contained in their bundles, and may not read or write data outside the designated container area, nor may they download, install, or execute code which introduces or changes features or functionality of the app." — [App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)
- Apple 4.2: "Your app should include features, content, and UI that elevate it beyond a repackaged website... If your App doesn't provide some sort of lasting entertainment value or adequate utility, it may not be accepted." 4.2.2: apps "shouldn't primarily be marketing materials, advertisements, web clippings, content aggregators, or a collection of links." — [App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)
- November 2025 change (third-party account): mini apps/mini games "must comply with the same guidelines as native applications"; only WebKit and JavaScriptCore allowed as engines for that non-embedded software; host apps need age gating and a content manifest. The article addresses mini-app platforms, not standalone wrappers. — [DEV: Apple's Guideline 4.7 update](https://dev.to/arshtechpro/apples-guideline-47-update-what-every-developer-hosting-html5-mini-apps-must-know-90)
- Mini Apps Partner Program (19 Nov 2025): 85% revenue share for qualifying hosts using Advanced Commerce API and Declared Age Range API under 4.7 (secondary report). — [Outlook Respawn](https://respawn.outlookindia.com/amp/story/pop-culture/pop-culture-news/apple-launches-mini-apps-partner-program-with-reduced-commission)
- April 2024 revision allowed retro emulators to download games and specified mini apps/games must be HTML5. — [MacStories](https://www.macstories.net/news/apple-amends-app-review-guidelines-to-permit-game-emulators-and-make-other-changes/)
- EU DMA (announced 18 Aug 2026): Core Technology Fee replaced by a 5% Core Technology Commission on digital transactions for apps via alternative marketplaces or web distribution; App Store IAP 26%, alternative payments 20%, link-out 15%; small marketplaces under EUR 10M/yr can have the 5% waived; notarization still required; sources disagree whether effective 1 Oct 2026 or 1 Jan 2026; Commission has not closed its case; Epic calls them "junk fees". — [mjtsai digest of new EU terms](https://mjtsai.com/blog/2026/08/18/new-eu-app-store-terms-to-comply-with-dma/); [Galaxus report](https://www.galaxus.de/en/page/apple-and-the-eu-settle-long-standing-dispute-43522); [FunnelFox fee summary](https://blog.funnelfox.com/apple-app-store-fees-2026-eu-dma/)
- Google Play "Webviews and Affiliate Spam": "We don't allow apps whose primary purpose is to drive affiliate traffic to a website or provide a webview of a website without permission from the website owner or administrator." Example: "Ted's Shopping Deals... simply provides a webview of Google Shopping." — [Google Play policy: Spam](https://support.google.com/googleplay/android-developer/answer/9899034)
- Google Play "Minimum functionality" intro: "Apps should provide users with a basic degree of adequate functionality and content for an engaging user experience. Apps that crash, exhibit other behavior that is not consistent with a functional user experience" are not allowed. 2020 Google post: webview-of-existing-website submissions are "webview spam". — [Google Play policy topic 9876964](https://support.google.com/googleplay/android-developer/topic/9876964); [Android Developers Blog 2020](https://android-developers.googleblog.com/2020/10/developer-tips-and-guides-common-policy.html)
- Enforcement example: a Wix-based webview app suspended under the webviews and affiliate spam policy. — [B4X forum](https://b4x.com/android/forum/threads/app-google-play-uploading-issue.89429)
- Shipped Phaser-on-Android example: Fuel Field (Phaser 3, Capacitor, Google Play, iOS, itch.io); dev says "Google Play's testing requirements" (closed-testing requirement for new personal accounts) caught him off guard. Pixel Exile (Phaser) ships on Android, web, itch.io; no Capacitor/iOS confirmation. — [Phaser: Fuel Field interview (July 2026)](https://phaser.io/news/2026/07/fuel-field-phaser-roguelite-interview); [Phaser: Pixel Exile (Dec 2025)](https://phaser.io/news/2025/12/pixel-exile)
- Size limits: Google Play base module 500 MB compressed, >200 MB triggers a non-blocking mobile-data warning, APK publishing capped at 100 MB. — [Google Play app size limits](https://support.google.com/googleplay/android-developer/answer/9859372)
- iOS cellular downloads: since iOS 13 the 200 MB cap became a user setting (always allow / ask if over 200 MB / always ask), default is the over-200 MB prompt. — [TechCrunch 2019](https://techcrunch.com/2019/06/03/ios-13-will-let-you-bypass-the-app-store-download-cap-when-on-a-cellular-connection); [iDownloadBlog](https://www.idownloadblog.com/2019/10/25/about-app-store-cellular-download-limit/)

### Inferences
- Ship all code (JS and wasm) inside the bundle. Do not load the game from a remote URL (`server.url`) in production: that is both unsupported by Capacitor and the behaviour 2.5.2 and 4.7 exist to police. Live-update services (Capgo etc.) for JS are a grey area; wasm hot-updates are a bigger one.
- A living-town game with saved state and lasting play clears 4.2's "repackaged website" bar on its face; review risk is lower than for utility wrappers. The practical Apple-side risks are the Xcode 26 SDK requirement and iOS 15 deployment floor, not policy.
- Google Play: not a WebView-spam case (own content, no affiliate purpose), but new personal developer accounts face the closed-testing gate before production.
- Keep the whole install under 200 MB on both stores to avoid the cellular prompt/warning; a pixel-art game with a wasm sim should sit far below that.

## Q5. PWA on iOS in 2026: installability, storage, audio, fullscreen, background, push; is PWA alone viable for a game?

### Takeaway
iOS 26 made every site installable as a Home Screen web app without a manifest, push and badging exist since 16.4, and storage quotas are generous (same as Safari), but there is still no install prompt, no orientation lock, no true fullscreen on iPhone, and an open iOS 26 bug where Web Audio dies after the first run of a Home Screen web app. PWA is a fine primary channel for web/Android and a secondary one on iOS; store presence still needs Capacitor.

### Cited Findings
- iOS/iPadOS 26: "Every site can run as a web app. Adding a site to the Home Screen opens it as a web app by default"; users can toggle "Open as Web App" off; a manifest is no longer required (icons still used if present). WKWebView gained local/session storage restoration APIs and `obscuredContentInsets`. — [WebKit: features in Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)
- Web Push for Home Screen web apps and the Badging API (`navigator.setAppBadge`) arrived in iOS/iPadOS 16.4; third-party browsers can offer Add to Home Screen since 16.4. — [WebKit: Web Push for Web Apps on iOS and iPadOS](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados); [WebKit: Badging for Home Screen Web Apps](https://webkit.org/blog/14112/badging-for-home-screen-web-apps/)
- Storage (Safari 17 / iOS 17+): origin quota up to 60% of disk for browser apps and 15% for other apps (WKWebView), overall 80% / 20%; Home Screen web apps get the same quota as in Safari; eviction is LRU per origin under quota/system pressure or long inactivity (ITP); no user prompt; persistence granted heuristically, e.g. when opened as a Home Screen web app. — [WebKit: Updates to Storage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/)
- The 7-day ITP data cap applies to Safari, not Home Screen web apps, which have their own days-of-use counter (Apple's John Wilander via OSNews); a 2022 bug report nonetheless describes cookies cleared after 7 days on iOS 15.3. — [OSNews on WebKit clarification](https://www.osnews.com/?p=131566); [WebKit bug 237350](https://bugs.webkit.org/show_bug.cgi?id=237350)
- Audio: Safari blocks Web Audio until a user gesture (`audioCtx.resume()` in touch/click handlers); it also suspends the AudioContext when the page is hidden, requiring `resume()` on `visibilitychange` with a tap fallback. WebKit bug 291892 (open): on iOS 26, Home Screen web apps "will only work with Web Audio on the first run, and AudioContext.resume() never returns from the suspended state". Older note: ringer on vibrate silenced Web Audio in Safari iOS (2019). — [bugnet.io: fix HTML5 game audio cut off on iOS background](https://bugnet.io/blog/fix-html5-game-audio-cut-off-on-ios-background); [WebKit bug 291892](https://bugs.webkit.org/show_bug.cgi?id=291892); [Matt Montag: unlock Web Audio](https://www.mattmontag.com/web/unlock-web-audio-in-safari-for-ios-and-macos)
- Orientation lock: caniuse marks `ScreenOrientation.lock` not supported in Safari on iOS through 26.4/26.5 (the parent Screen Orientation API is supported from 16.4); WebKit bug 257695: "iPhone doesn't support html fullscreen api, so screen locking won't work as it needs fullscreen api." — [caniuse: ScreenOrientation lock](https://caniuse.com/mdn-api_screenorientation_lock); [caniuse: Screen Orientation](https://caniuse.com/screen-orientation); [WebKit bug 257695](https://bugs.webkit.org/show_bug.cgi?id=257695)
- Install friction (developer reports): no install prompt in Safari; some developers saw a page snapshot used as icon and OAuth callbacks fail; service-worker caching behaves differently from Android. — [Ionic forum: My experience with PWA](https://forum.ionicframework.com/t/my-experience-with-pwa/132356)
- Legacy baseline (2018, iOS 11.3): `display: fullscreen` falls back to standalone, status bar stays, no orientation lock, no splash, ~50 MB cap and deletion after weeks of non-use (superseded by the 2023 storage policy above). — [firt.dev: PWAs on iOS](https://www.firt.dev/ios-pwa)
- EU: Apple announced then reversed (March 2024) removing Home Screen web apps in the EU; Apple's note said it would "continue to offer the existing Home Screen web apps capability in the EU". — [Engadget](https://www.engadget.com/apple-backtracks-on-plans-to-get-rid-of-web-apps-on-iphones-in-the-eu-195232177.html)
- Interactive-fiction community view: for a free game a PWA beats app-store distribution; what players get is an icon, hidden URL bar and offline play. — [intfiction.org: Releasing a game as a PWA?](https://intfiction.org/t/releasing-a-game-as-a-pwa/47624)

### Inferences
- iOS PWA is now installable enough to be a legitimate "play on your phone" channel, and storage is no longer the blocker. The blockers are discoverability (no prompt, no store), the inability to lock landscape, and the iOS 26 Web Audio bug, which for a game with ambient town audio is serious until fixed. Design the game to be playable in portrait and in landscape rather than relying on a lock.
- The same service worker and manifest work unchanged inside Capacitor (Capacitor routes service-worker requests through its bridge on Android by default), so PWA-first costs nothing extra later.

### Gaps
- No 2025-2026 game-developer postmortem specifically on iOS PWA distribution was found; evidence is forum-level.
- Status of WebKit bug 291892 (Web Audio in Home Screen web apps on iOS 26) as of Oct 2026 not confirmed.

## Q6. Renderer choice under mobile constraints: PixiJS, Phaser 4, Excalibur, melonJS, raw Canvas

### Takeaway
On mobile the differentiators are not raw sprite throughput (a few hundred sprites is trivial for any WebGL batcher) but context-loss recovery, DPR/integer-scaling control, Pointer Events handling and bundle weight. Phaser 4 (GA April 2026) documents automatic context restoration and has a pixel-art guide; PixiJS v8 has the most flexible renderer selection (WebGL default, WebGPU experimental, Canvas coming) but context-loss handling is an open-issue area; Excalibur has clean Pointer Events and `pixelArt` options but thin mobile documentation; melonJS shows little recent activity.

### Cited Findings
- Phaser 4 launched April 2026, replacing the Phaser 3 WebGL pipeline; built on WebGL1 with full WebGL2 support; automatic context restoration; sprite quads use 4 vertices instead of 6; shader system no longer requests max texture units ("helps on mobile"); `roundPixels` now defaults to false; per-object `vertexRoundMode`; `SpriteGPULayer` draws static data in one call at 168 bytes per member. RC4 (May 2025) claimed up to 16x gains for filters/masks on phones. No WebGPU renderer. — [Phaser 4 renderer article](https://phaser.io/news/2026/04/phaser-4-renderer-faster-cleaner-and-built-for-modern-games); [Phaser 3 vs Phaser 4](https://phaser.io/news/2026/05/phaser-3-vs-phaser-4); [Phaser 4 RC4](https://phaser.io/news/2025/05/phaser-v4-release-candidate-4); [SpriteGPULayer performance](https://phaser.io/news/2026/05/phaser4-spritegpulayer-performance)
- Phaser 4 Pixel Art Guide: `pixelArt: true` = antialias off + roundPixels on, for 1:1 display, "avoid scaling, rotating, and zooming"; `smoothPixelArt` for scaled-up pixels (batch-wide, set globally); "Non-integer scale produces non-integer pixel positions, which causes blurring"; keep positions and camera scroll integer when rounding manually. — [Phaser 4 Pixel Art Guide (phaser@4.1.0)](https://cdn.jsdelivr.net/npm/phaser@4.1.0/docs/Phaser%204%20Pixel%20Art%20Guide/Phaser%204%20Pixel%20Art%20Guide.md)
- PixiJS v8: `autoDetectRenderer()` with `preference: 'webgpu' | 'webgl'`; WebGLRenderer is default, "recommended and stable"; WebGPURenderer "experimental", feature complete but "browser inconsistencies may cause unexpected behavior"; CanvasRenderer "coming soon" (experimental Canvas renderer landed in 8.16.0). v8 "faster across the board" than v7 and supports multi-touch. — [PixiJS renderers guide](https://pixijs.com/8.x/guides/components/renderers); [PixiJS v8 launch](https://pixijs.com/blog/pixi-v8-launches); [PixiJS blog](https://pixijs.com/blog/tags/tagged-text)
- PixiJS mobile/iOS issues open as of Oct 2026: context loss during shader compilation leaves a blank scene (#12281); WebGL reclaimed after inactivity (#11731); `INVALID_ENUM activeTexture` on iOS 12.5/13.7 with v8.6.6 (#11216); WebGPU-to-WebGL fallback sometimes fails (#10906). — [pixijs issues search](https://github.com/pixijs/pixijs/issues/12281)
- PixiJS DPR practice: `resolution = window.devicePixelRatio` or output loses clarity (older `PIXI.settings` API). — [html5gamedevs devicePixelRatio tag](https://www.html5gamedevs.com/tags/devicePixelRatio/)
- Excalibur: input via `engine.input.pointers` following the W3C Pointer Events spec, normalizing mouse and touch; `pointers.at(n)` for multi-touch; `pointerScope` Canvas vs Document; `pixelArt: true` enables pixel-art antialiasing settings, `antialiasing: false` for sharp pixels; low resolutions "may benefit from a pixelRatio of 2 or 3"; `FitScreen` keeps aspect and resolution, `FitScreenAndFill` avoids letterboxing but only the configured area is safe to draw in; latest release seen 0.30.3 (Jan 2025). Docs do not cover `touch-action`/scroll prevention. — [Excalibur pointers docs](https://excaliburjs.com/docs/pointers); [Excalibur pixel art docs](https://excaliburjs.com/docs/pixel-art); [Excalibur display modes](https://beta.excaliburjs.com/docs/displaymodes); [Excalibur 0.29.0 notes](https://www.nuget.org/packages/Excalibur/0.29.0)
- melonJS: site describes an MIT ES-module engine; package pages reference melonJS 10.0 with a changelog dated 2024-06-22; no 2025-2026 release found. — [melonJS.org](https://melonJS.org); [melonjs on Yarn](https://classic.yarnpkg.com/en/package/melonjs)
- DPR and pixel art: when "the devicePixelRatio is not an integer, certain pixels may be drawn larger than others, resulting in a non-uniform appearance"; MDN's recipe is a small canvas scaled with CSS and `image-rendering: pixelated`. web.dev's canvas-hidipi technique (backing store = CSS size x DPR) suits vector drawing, not pixel art. — [MDN: Crisp pixel art look](https://developer.mozilla.org/en-US/docs/Games/Techniques/Crisp_pixel_art_look); [web.dev: High DPI Canvas](https://web.dev/articles/canvas-hidipi)
- Phaser high-DPR pitfall: input hit areas and arcade bodies drift from sprites when the game resolution is set to 2. — [html5gamedevs: Phaser canvas highdpi size input problems](https://www.html5gamedevs.com/topic/31088-phaser-canvas-highdpi-size-input-problems/)
- Safe areas: `viewport-fit=cover` + `env(safe-area-inset-*)`; Capacitor 8 handles Android edge-to-edge insets natively via `SystemBars`. — [Phaser Capacitor tutorial](https://phaser.io/tutorials/bring-your-phaser-game-to-ios-and-android-with-capacitor); [Ionic: Announcing Capacitor 8](https://ionic.io/blog/announcing-capacitor-8)
- Memory: PixiJS issue about "too many active WebGL contexts even after destroyed" (open since 2022) and WKWebView's opaque memory ceiling (Q2) bound how many canvases/RenderTextures a mobile viewer should create. — [pixijs #8215](https://github.com/pixijs/pixijs/issues/8215); [Apple forums thread 133449](https://developer.apple.com/forums/thread/133449)

### Inferences
- Integer scaling on phones: compute the scale as `floor(min(physicalW / gameW, physicalH / gameH))` in device pixels (CSS px x DPR), size the canvas backing store to game size x scale, set CSS size to backing / DPR, and accept letterboxing or an "extra tiles at the edge" fill. iPhones have integer DPRs (2, 3); many Androids are fractional (2.625, 2.75), so on Android the CSS-size step will land on fractional CSS pixels, which is fine as long as the backing store is integer-scaled and `image-rendering: pixelated` is set. For a 320x180 native canvas on a 3x iPhone (~1179x2556 physical landscape 2556x1179), scale = 6. Do all this in the viewer, not in the engine's default "resolution = DPR" path, which produces non-integer scales.
- Tap-to-walk only needs `pointerdown`/`pointerup` on one pointer; every engine above covers that. Set `touch-action: none` on the canvas and `user-select: none` to stop Safari's scroll/zoom/long-press behaviours; the engines' docs (Excalibur, Phaser) do not spell this out, so the viewer must.
- Renderer-library ranking for this project under mobile constraints: PixiJS v8 (lean, explicit control over resolution and scale mode, WebGL default) or Phaser 4 (batteries included, documented context restoration and pixel-art guide, heavier); Excalibur is viable but has the smallest mobile track record; melonJS and raw Canvas 2D are not recommended (inactivity; lack of batching and lost-context semantics respectively). Whichever is chosen, the viewer must own context-loss recovery (rebuild textures from the atlas on `webglcontextrestored` / `visibilitychange`) because the iOS reports show it will happen.
- Audio: route all sound through one AudioContext created lazily on first `pointerdown`, resume it on `visibilitychange`, and fail silently; the iOS 26 Home Screen bug means audio cannot be a hard requirement on iOS PWA.

- Excalibur and PixiJS documentation on `touch-action`, passive listeners and context-loss policy was not found in the fetched pages.
- No primary measurement of how Phaser 4's automatic context restoration behaves in WKWebView (the claim is from Phaser's own announcement).
