# Map authoring tooling, text/code map formats, and procedural building/town layout (researched 2026-10-23)

Scope: what Tiled and LDtk give a headless, code-driven author; ASCII/DSL map formats used as source by games; procedural building/interior layout methods; and validation of layouts without a human walking them. World data model and interior rendering/transitions are covered by other researchers and are only touched where a tool feature directly addresses floors or interiors.

## Q1. Tiled: worlds, JSON, objects/templates, infinite maps, interiors/floors, CLI export, Node libraries

### Takeaway
Tiled's formats are all plain JSON (map `.tmj`, tileset `.tsj`, template `.tj`, and `.world`) and are small enough to read and write from Node with a few hundred lines; the `.world` file is the only multi-map container and it only records map file names plus pixel positions. There is no first-class concept of interiors or floors; the community convention is one map per floor/interior, and the CLI exporter needs an X server (Xvfb) on Linux, which makes it a poor fit as a headless pipeline step compared to writing JSON directly.

### Cited Findings

**`.world` format**
- A `.world` file is JSON with `"type": "world"` and a `maps` array; each entry needs `fileName` and a pixel position `x`, `y`; each map may also carry `width` and `height` in pixels, which are needed for adjacency filtering. Verbatim example from the docs:
  ```json
  { "maps": [ { "fileName": "001-1.tmx", "x": 0, "y": 0 },
              { "fileName": "002-1.tmx", "x": 0, "y": 3200 },
              { "fileName": "006-1.tmx", "x": 3840, "y": 4704 } ],
    "type": "world" }
  ```
  — [Tiled manual: Worlds](https://doc.mapeditor.org/en/stable/manual/worlds/)
- Pattern-based worlds use a `patterns` array; each pattern has `regexp` (matched against files in the world file's directory; first capture group is x, second is y), `multiplierX`/`multiplierY`, `offsetX`/`offsetY`, and optional `mapWidth`/`mapHeight` (default to the multipliers). Example: `"regexp": "ow-p0*(\\d+)-n0*(\\d+)-o0000\\.tmx", "multiplierX": 6400, "multiplierY": 6400, "offsetX": -6400, "offsetY": -6400`. Manually listed maps and patterns can be combined in one file. — [Tiled manual: Worlds](https://doc.mapeditor.org/en/stable/manual/worlds/)
- `"onlyShowAdjacentMaps": true` at top level loads only direct neighbours of the current map (fixed one-map radius; configurable distance is only a possible future addition); maps need sizes defined for this to work. — [Tiled manual: Worlds](https://doc.mapeditor.org/en/stable/manual/worlds/)
- Worlds were introduced in Tiled 1.2, editing tools (World Tool: add/remove/drag maps, arrow keys, World > Save World) in 1.4. "No interface exists for defining or modifying pattern-based worlds. Those files must be edited by hand." Worlds reload automatically when the file changes on disk. — [Tiled manual: Worlds](https://doc.mapeditor.org/en/stable/manual/worlds/)

**Map / tileset / template JSON**
- Top-level map fields: `version` (string since 1.6), `tiledversion`, `type: "map"`, `class` (1.9+), `orientation` (orthogonal/isometric/staggered/hexagonal), `infinite`, `width`/`height` in tiles, `tilewidth`/`tileheight`, `layers`, `tilesets`, `properties`, `nextlayerid`, `nextobjectid`, `renderorder`, `compressionlevel` (default -1), parallax origin (1.8+). — [Tiled JSON Map Format](https://doc.mapeditor.org/en/stable/reference/json-map-format/)
- Layer `type` is `tilelayer`, `objectgroup`, `imagelayer`, or `group`. Tile layers store `data` as a GID array (`"data":[1, 2, 1, 2, 3, ...]`) or base64 string selected by `encoding` (`csv` default or `base64`), with `compression` of `zlib`, `gzip`, `zstd` or empty. Infinite maps store tiles in `chunks`, each with `x`, `y` (tile coordinates, can be negative, e.g. `"x":0,"y":-16`), `width`, `height`, `data`; tile layers of infinite maps also carry `startx`/`starty`. Common layer fields: `id`, `name`, `opacity`, `visible`, `locked`, `offsetx`/`offsety`, `parallaxx`/`parallaxy`, `tintcolor`, `mode` (blend mode, 1.12+). Group layers nest child `layers`. — [Tiled JSON Map Format](https://doc.mapeditor.org/en/stable/reference/json-map-format/)
- Object fields: `id`, `name`, `type`, `x`, `y`, `width`, `height`, `rotation`, `visible`, `opacity`; shape flags `ellipse`, `point`, `capsule`; `polygon`/`polyline` point arrays relative to the object position; `gid` for tile objects; `template` for template instances; `text` for text objects. The `type` field was saved as `class` in Tiled 1.9 only and reverted to `type` in 1.10 (a known compatibility trap for parsers). — [Tiled JSON Map Format](https://doc.mapeditor.org/en/stable/reference/json-map-format/)
- Properties are `{name, type, value}` with `type` in string (default), int, float, bool, color, file, object, class, plus optional `propertytype` for custom property types (1.8+); a `class`-typed value is a JSON object. Example: `"name":"hp","type":"int","value":12`. — [Tiled JSON Map Format](https://doc.mapeditor.org/en/stable/reference/json-map-format/)
- Template files are stored separately with `type: "template"`, an optional external `tileset`, and the `object` they instantiate. — [Tiled JSON Map Format](https://doc.mapeditor.org/en/stable/reference/json-map-format/)
- Tilesets: `firstgid` (first tileset is always 1), `source` for external tileset files, `tiles[]` with local `id`, optional `animation`, `objectgroup` (collision shapes), `terrain`, `probability`, `properties`, and sub-rectangle `x`/`y`/`width`/`height`. Wang sets: `wangsets[]` each with `name`, `type` (corner/edge/mixed), `colors[]` (`color`, `name`, `probability`, `tile`, `properties`) and `wangtiles[]` each `{tileid, wangid}` where `wangid` is an array of color indexes, e.g. `"wangid": [2, 0, 1, 0, 1, 0, 2, 0]`. — [Tiled JSON Map Format](https://doc.mapeditor.org/en/stable/reference/json-map-format/)

**Interiors and floors**
- Tiled forum consensus on multi-floor buildings: "Most commonly you would have one tmx per level. Layers in a single file quickly become super-tedious and confusing once there are many." — [Tiled forum: Floors/Levels aka Z-Axis](https://discourse.mapeditor.org/t/floors-levels-aka-z-axis/1408)
- Show/hide layers as the player climbs stairs is described as a valid strategy; separate maps per floor were used by The Mana World and Source of Tales when heights differ across large areas; hiding layers "still doesn't show what happens on lower floors" (a problem for Tibia-style games that render floors beneath). — [Tiled forum: Tiled have Floor system?](https://discourse.mapeditor.org/t/tiled-have-floor-system/3269); [Tiled forum: Correct approach for tiling a building](https://discourse.mapeditor.org/t/correct-approach-for-tiling-a-building/5357)
- Tiled has no built-in "floor" property; floors/interiors are expressed via naming, custom properties, or world placement (the docs on worlds and the JSON format do not mention floors at all). — [Tiled manual: Worlds](https://doc.mapeditor.org/en/stable/manual/worlds/); [Tiled JSON Map Format](https://doc.mapeditor.org/en/stable/reference/json-map-format/)

**CLI export and headless use**
- Exports can be automated with `--export-map` and `--export-tileset`. "On Linux, command-line export still requires an X server. To automate exports in a headless environment, you can use a headless X server such as Xvfb", e.g. `xvfb-run tiled --export-map ...`. — [Tiled manual: Export Formats](https://doc.mapeditor.org/en/stable/manual/export/)
- CLI export options as named in `src/tiled/main.cpp` (quoted on the forum by the Tiled author): `--embed-tilesets` ("Export the map with tilesets embedded"), `--detach-templates`, `--resolve-types-and-properties`, `--minimize` (omit unnecessary whitespace). Editor preferences do not affect command-line export; the CLI has its own options. The forum example command was `tiled --export-maps json map_in.tmx map_out.json`, and the author acknowledged embedding "broke again" at that time (Nov 2019). — [Tiled forum: Can I export maps with embedded tilesets from the command line?](https://discourse.mapeditor.org/t/can-i-export-maps-with-embedded-tilesets-from-the-command-line/4227)
- The export options (embed tilesets, detach templates, resolve object types and properties) are "also available for those exporting using the command-line". — [Tiled devlog: Export Options and Polishing](https://thorbjorn.itch.io/tiled/devlog/43780/export-options-and-polishing)
- Export formats listed: JSON, Lua, CSV; Defold; GameMaker (1.4 and 2); Godot 4; tBIN/tIDE (Stardew's map formats); custom formats via JavaScript, Python or C++ plugins; Export as Image. — [Tiled manual: Export Formats](https://doc.mapeditor.org/en/stable/manual/export/)

**Node/TypeScript libraries**
- `@kayahr/tiled` is "a set of TypeScript interfaces, types and enums, API documentation, JSON file typings, JSON schema and helper functions" for Tiled JSON. It provides no loaders (you `fetch` and cast to `tiled.Map`); helpers are type guards (`isTilesetRef`, `isEmbeddedTileset`, `isTileLayer`, `isObjectGroup`, `isImageLayer`, `isGroup`, `isEncodedTileLayer`, `isUnencodedTileLayer`) and `decodeTileLayer` (base64 + zlib/gzip/zstd). File typings cover only `*.map.json`, `*.tileset.json`, `*.template.json`; `.world` is not mentioned. — [kayahr/tiled README](https://github.com/kayahr/tiled/)
- `@mapeditor/tiled-api` (JSR) is typings for Tiled's scripting API and documents a `WorldPattern` class ("Patterns added to a World, which are used to automatically match maps"), i.e. the editor's in-process scripting API, not a standalone parser. — [JSR: @mapeditor/tiled-api WorldPattern](https://jsr.io/@mapeditor/tiled-api/doc/~/WorldPattern)
- `parse-tmx` is a TypeScript `.tmx` (XML) parser that supports only embedded tilesets ("At the moment, external tilesets are not supported!"). — [npm: parse-tmx](https://www.npmjs.com/package/parse-tmx)
- A community "Tiled project file and map parser" flattens custom-class properties and parses `.tiled-project` files into TypeScript-friendly output. — [Tiled forum: Tiled project file and map parser](https://discourse.mapeditor.org/t/tiled-project-file-and-map-parser-with-property-flattening/6241)

### Inferences
- Because `.world`, `.tmj`, `.tsj` and `.tj` are plain JSON with documented, stable fields, an agent can generate them directly (and validate them with `@kayahr/tiled`'s JSON schema) and treat the Tiled GUI as an optional viewer, bypassing the Xvfb requirement entirely. The CLI is only needed if you author in TMX/TSX (XML) and want JSON out.
- The `wangid` array has 8 entries in the documented example (`[2,0,1,0,1,0,2,0]`); corner sets leave even positions 0 and edge sets leave odd positions 0 (the docs page retrieved did not spell out the position ordering, so verify against the TMX reference before relying on it).
- A town with many interiors maps naturally onto one `.world` per "overworld" plus one map file per interior/floor, with interior maps either placed off-screen in the same world (so adjacency loading stays cheap) or kept out of the world file and linked via object properties (door objects with `type: "object"` or `file` properties). Tiled itself expresses no opinion here.

### Gaps
- Could not fetch Tiled's current `main.cpp` (raw GitHub returned 404) to confirm the exact current spelling of `--export-formats`, `--export-map [format] <source> <target>`, or `--project`; the flag names above come from a 2019 forum quote and should be checked against `tiled --help` on the installed build.
- No source found that documents `QT_QPA_PLATFORM=offscreen` as an alternative to Xvfb for Tiled; the docs only mention Xvfb.
- No Node library was found that parses `.world` files or resolves a world into a merged coordinate space; this would have to be hand-written (small).
- Phaser's and Excalibur's Tiled loaders were not researched in detail; no evidence found either way on `.world` support.

## Q2. LDtk: world layouts, neighbours, depth, multi-worlds, entities/refs, IntGrid, auto-layer rules, JSON schema, Super Simple Export, writing files from code

### Takeaway
LDtk's JSON is thoroughly documented field-by-field (Draft 7 JSON Schema published), has explicit world layouts (Free, GridVania, LinearHorizontal/Vertical), per-level `worldDepth` for stacking levels at the same position (a natural "floor" axis), computed `__neighbours` including depth relations, typed entity fields with cross-level `EntityRef`s, and IntGrid layers that drive rule-based autotiling. The rule engine's semantics live in editor code and the editor bakes `autoLayerTiles` into the file on save, so a file written from code will not have auto-tiles until it is opened and re-saved in LDtk (or you re-implement the matcher).

### Cited Findings

**Root, worlds, layouts**
- Root fields: `jsonVersion` (string), legacy `worldLayout`/`worldGridWidth`/`worldGridHeight` (can be null; grid sizes only matter for GridVania; layouts are Free, GridVania, LinearHorizontal, LinearVertical), `worlds` ("Empty unless Multi-Worlds is enabled"; a project currently holds one world and its layout and levels stay at root; multi-worlds format described as a "preview"), `externalLevels` (if TRUE each level is its own file in a sub-folder), `simplifiedExport`, `toc` (entities with `exportToToc`, each with `identifier` and `instancesData` carrying `fields`, `heiPx`, `widPx`, `worldX`, `worldY`, `iids`), `levels` (array order only matters for Linear layouts; otherwise use `worldX`/`worldY`). — [LDtk JSON_DOC.md](https://github.com/deepnight/ldtk/blob/master/docs/JSON_DOC.md)
- World (preview) fields: `identifier`, `iid`, `worldLayout`, `worldGridWidth`, `worldGridHeight`, `levels`. — [LDtk JSON_DOC.md](https://github.com/deepnight/ldtk/blob/master/docs/JSON_DOC.md)
- Layout semantics: LinearHorizontal/Vertical arrange levels one after another; Free places levels anywhere in 2D; GridVania snaps levels to a world grid and "each level's dimensions must also fit that grid". — [LDtk docs: World](https://ldtk.io/docs/general/world/)
- Multi-worlds (1.3.0): one project holds several worlds with their own levels and layouts but shared definitions (layers, entities, enums); enabled under Project settings > advanced options; "experimental preview", "PLEASE BACKUP YOUR PROJECTS BEFORE TRYING IT!", and "Multi-worlds projects cannot be imported using older loaders." — [LDtk devlog 1.3.0](https://deepnight.itch.io/ldtk/devlog/522221/130-multi-worlds-preview)
- LDtk 1.0 added the `worlds` array and `World` structure as a preview, and "Levels can now be organized in 'depth' to support stacked levels". Also in 1.0: `levelUid` in neighbours replaced by `levelIid`; `tileId` in entity defs replaced by `tileRect`; `autoTilesetDefUid` merged into `tilesetDefUid`; `__smartColor` added to entity instances; `worldX`/`worldY` are -1 and `__neighbours` empty for Linear layouts. — [LDtk devlog 1.0](https://deepnight.itch.io/ldtk/devlog/363094/100-gone-gold)

**Levels, neighbours, depth**
- Level fields: `identifier`, `iid`, `uid`, `worldX`/`worldY` (pixels; -1 in Linear layouts), `worldDepth` (default 0; "Higher values sit 'above' and lower values sit 'below.' It is mainly for display."), `pxWid`/`pxHei`, `externalRelPath` (to the `.ldtkl` file when levels are saved separately), `fieldInstances`, `layerInstances` (display order, top-most first; `null` when levels are external). — [LDtk JSON_DOC.md](https://github.com/deepnight/ldtk/blob/master/docs/JSON_DOC.md)
- `__neighbours[]` entries are `{levelIid, dir}` with `dir` in `n`,`s`,`w`,`e`; `<` and `>` for a neighbour at lower/greater depth (since 1.4.0); `o` for overlapping levels at the same depth (since 1.4.0); `nw`,`ne`,`sw`,`se` for corner-touching (since 1.5.3). — [LDtk JSON_DOC.md](https://github.com/deepnight/ldtk/blob/master/docs/JSON_DOC.md)
- The godot-ldtk-importer groups levels into `LDTKWorldLayer` nodes "sorted by worldDepth", showing how importers treat depth as a floor/layer axis. — [heygleeson/godot-ldtk-importer](https://github.com/heygleeson/godot-ldtk-importer)

**Layers, IntGrid, tiles, entities, fields, refs**
- LayerInstance: `__type` in IntGrid/Entities/Tiles/AutoLayer; `__cWid`, `__cHei`, `__gridSize`; `intGridCsv` (left-to-right, top-to-bottom; 0 = empty, values start at 1; length `__cWid*__cHei`); `autoLayerTiles` (rule output "sorted in display order"; tiles hidden behind opaque ones may be discarded); `gridTiles`; `entityInstances`; `overrideTilesetUid`; `pxOffsetX/Y` (prefer `__pxTotalOffsetX/Y`); `seed` (auto-layer random seed, editor). — [LDtk JSON_DOC.md](https://github.com/deepnight/ldtk/blob/master/docs/JSON_DOC.md)
- Tile instance: `px` [x,y] in layer, `src` [x,y] in tileset, `f` flip bits (bit0 X, bit1 Y), `t` tile id, `a` alpha, `d` editor-only `[ruleId, coordId]` for auto tiles or `[coordId]` for tile layers. — [LDtk JSON_DOC.md](https://github.com/deepnight/ldtk/blob/master/docs/JSON_DOC.md)
- EntityInstance: `__identifier`, `defUid`, `iid`, `__grid` [x,y], `px` [x,y], `width`, `height`, `__pivot`, `__tags`, `__tile`, `__smartColor`, `__worldX`/`__worldY` (GridVania/Free only), `fieldInstances`. — [LDtk JSON_DOC.md](https://github.com/deepnight/ldtk/blob/master/docs/JSON_DOC.md)
- FieldInstance: `__identifier`, `defUid`, `__type` (e.g. `Int`, `Float`, `String`, `Enum(my_enum_name)`, `Bool`, Multilines), `__value` (Color as `#rrggbb`; Enum as string; Point as `{cx, cy}`; Tile as TilesetRect; EntityRef as EntityReferenceInfos; arrays as JSON arrays), `__tile`, `realEditorValues` (editor). EntityReferenceInfos is `{entityIid, layerIid, levelIid, worldIid}`. — [LDtk JSON_DOC.md](https://github.com/deepnight/ldtk/blob/master/docs/JSON_DOC.md)
- Field definitions: `__type` in Int, Float, String, Multilines, Bool, Color, ExternEnum.X, LocalEnum.X, Point, FilePath, with arrays as `Array<...>` (internal types also include F_Tile and F_EntityRef); `isArray`, `canBeNull`, `min`/`max`, `regex` (strings), `allowedRefs` (Any/OnlySame/OnlyTags/OnlySpecificEntity), `allowedRefTags`, `allowOutOfLevelRef` (no description given), `symmetricalRef` (no description given), `editorDisplayMode`. — [LDtk JSON_DOC.md](https://github.com/deepnight/ldtk/blob/master/docs/JSON_DOC.md)
- EntityRef was introduced in 1.0: "a Button entity can reference a Door entity. You can create arrays of references or restrict which Entity types they can point to." — [LDtk devlog 1.0](https://deepnight.itch.io/ldtk/devlog/363094/100-gone-gold)
- Entity definitions: `limitBehavior` (DiscardOldOnes/PreventAdding/MoveLastOne), `limitScope` (PerLayer/PerLevel/PerWorld), `maxCount`, `allowOutOfBounds` (1.5.0+), `tileRenderMode` (Cover/FitInside/Repeat/Stretch/FullSizeCropped/FullSizeUncropped/NineSlice), `nineSliceBorders`, `resizableX/Y`, `keepAspectRatio`, `tags`, `fieldDefs`. Layer definitions: `intGridValues[]` (`value`, `identifier`, `color`, `tile`, `groupUid`; "The array is not ordered by value"), `intGridValuesGroups`, `autoSourceLayerDefUid`, `autoRuleGroups` (each `uid`, `name`, `active`, `isOptional`, `rules`), `requiredTags`/`excludedTags` for entity layers, `tilesetDefUid`. Tileset definitions: `enumTags` (`enumValueId`, `tileIds`), `customData` (`tileId`, `data`), `tags`, `tagsSourceEnumUid`, `cachedPixelData` (`averageColors`, `opaqueTiles` base64). — [LDtk JSON_DOC.md](https://github.com/deepnight/ldtk/blob/master/docs/JSON_DOC.md)

**Auto-layer rules**
- Two auto-layer types: an IntGrid layer with a tileset attached ("IntGrid layers with rules"), or a "pure auto-layer" that contains only rules and takes its source from a separate IntGrid layer (useful for separate foreground/background layers from one IntGrid). Rules are "grid patterns that will decide if a specific tile should be painted". SHIFT+R hides rendered tiles to show the raw IntGrid. — [LDtk docs: Auto-layers](https://ldtk.io/docs/general/auto-layers/); [LDtk docs: Auto-layer rules](https://ldtk.io/docs/general/auto-layers/auto-layer-rules/)
- AutoLayerRuleDefinition (JSON): `pattern` (Ints, `size*size`), `size` (1, 3, 5 or 7), `tileRectsIds` (array of arrays of tile IDs; one picked randomly; old `tileIds` removed in 1.5.0), `chance` (0..1), `breakOnMatch` ("If TRUE (default), a match prevents later rules from applying in that cell"), `flipX`/`flipY`, `outOfBoundsValue`, `perlinActive`/`perlinSeed`/`perlinScale`/`perlinOctaves`, `xModulo`/`yModulo`/`xOffset`/`yOffset`, `checker` (None/Horizontal/Vertical), `tileMode` (Single/Stamp), `pivotX/Y` (Stamp only), `tileRandomXMin/Max`, `tileRandomYMin/Max`, `tileXOffset/YOffset`, `alpha`, `active`, `invalidated` (1.5.2+), `uid`. The doc says "game developers can ignore this section, since the editor resolves these rules before saving." — [LDtk JSON_DOC.md](https://github.com/deepnight/ldtk/blob/master/docs/JSON_DOC.md)
- Pattern encoding (from editor source): the flat array is indexed `px + py*size`; `0` = ignored cell; `+AUTO_LAYER_ANYTHING` = cell must be non-zero, `-AUTO_LAYER_ANYTHING` = cell must be zero; `abs(v)` in 1..999 = exact IntGrid value required (positive) or rejected (negative); `abs(v) > 999` = IntGrid value group, group index `floor(abs(v)/1000) - 1`, positive requires membership, negative rejects. Matching: fail if `tileRectsIds` empty; if `chance < 1` a seeded per-coordinate roll vs `chance*100`; if Perlin active, fail when noise at the coordinate is below 0; for each non-zero pattern cell read source at `cx + dirX*(px-radius)`, `cy + dirY*(py-radius)` where `dirX/dirY` = ±1 implement flips; out-of-bounds reads use `outOfBoundsValue`, and if that is null the match fails for any non-zero pattern cell. `breakOnMatch` defaults to false on load "to avoid breaking old maps". Single mode: each tile id is its own random choice; Stamp mode: all ids are placed together as a group. — [LDtk source: AutoLayerRuleDef.hx](https://github.com/deepnight/ldtk/blob/master/src/electron.renderer/data/def/AutoLayerRuleDef.hx)
- Constants: `AUTO_LAYER_ANYTHING = 1000001`, `MAX_AUTO_PATTERN_SIZE = 9`, `MAX_GRID_SIZE = 1024`. — [LDtk source: Const.hx](https://github.com/deepnight/ldtk/blob/master/src/electron.renderer/Const.hx)
- Feature history: Perlin noise filtering for rules arrived in 0.1.5; Modulo (fire every N columns/rows) and Checker mode (brick patterns) in 0.3.0; Checker was later moved into the Modulo window (1.3.1). — [LDtk v0.1.5 release](https://github.com/deepnight/ldtk/releases/tag/v0.1.5-alpha); [LDtk v0.3.0 release](https://github.com/deepnight/ldtk/releases/tag/v0.3.0-beta); [LDtk v1.3.1 notes](https://newreleases.io/project/github/deepnight/ldtk/release/v1.3.1)

**Schema, Super Simple Export, code-written files**
- The format page is at JSON version 1.5.3 and publishes `JSON_SCHEMA.json`, `MINIMAL_JSON_SCHEMA.json` and QuickType-generated parser files; it has a toggle for "internal values that are only used by the editor". — [LDtk JSON structure](https://ldtk.io/json/)
- The schema follows JSON Schema Draft 7 and "allows JSON 'parser' generation using QuickType, so you can generate Rust, C#, JS or Python parsers easily"; the Rust `ldtk` crate is generated from it and implements Serialize and Deserialize via serde. — [docs.rs: ldtk crate](https://docs.rs/ldtk)
- Super Simple Export (Project settings): each level gets its own folder with `_composite.png` (all layers merged), one PNG per layer (e.g. `backgroundLayer.png`), one PNG per IntGrid layer where each pixel is a cell coloured by IntGrid value (e.g. `collisions-int.png`), one CSV per IntGrid layer (e.g. `collisions.csv`), and `data.json` with level info and entities. — [LDtk docs: Super simple export](https://ldtk.io/docs/game-dev/super-simple-export/)
- With "Separate level files" enabled the main `.ldtk` keeps most level data but heavy sections like `layerInstances` are null, and `externalRelPath` points to the `.ldtkl`. — [docs.rs: ldtk crate](https://docs.rs/ldtk)
- A Defold community importer generates Defold tilemaps from LDtk JSON by script; "works perfectly fine for 160x160 levels, though they take a few seconds to generate". — [Defold forum: LDtk importer](https://forum.defold.com/t/need-help-tips-and-feedback-for-simple-ldtk-defold-importer/77929)

### Inferences
- `worldDepth` plus `__neighbours` with `<`/`>`/`o` is the closest thing either editor has to native floors: a two-storey inn can be two levels at the same `worldX/worldY` with `worldDepth` 0 and 1, and the neighbour list tells a loader which level is "upstairs". LDtk itself only treats depth as display ordering.
- Writing `.ldtk` from code is feasible because the schema is complete and machine-readable, but two things will be missing until the editor re-saves: `autoLayerTiles` (rules are evaluated in the editor) and editor caches (`cachedPixelData`, `__smartColor`, `toc`). A code-first pipeline should therefore either (a) implement the documented `pattern` matcher itself (the semantics above are small) or (b) treat LDtk's rules as a reference and run its own autotiler from the IntGrid CSV.
- `intGridCsv` is a logical, render-independent grid, which makes it a good target for ASCII-to-LDtk conversion: glyph -> IntGrid value, then rules produce art.
- GridVania's constraint that level sizes are multiples of the world grid suits a town where lots are a fixed size; Free suits irregular overworlds.

### Gaps
- Could not retrieve the detailed rules page content (ordering across rule groups, per-level rule-group toggles via `isOptional`, stamp pivot behaviour) from ldtk.io; only the JSON doc and editor source were available.
- Super Simple Export's `data.json` field list, `_bg.png`, and folder naming for multi-world projects were not retrievable from the docs page.
- No official statement found on whether LDtk hot-reloads a project file edited externally while the editor has it open, or whether it tolerates missing editor-only fields; the Rust crate and QuickType docs imply the schema is sufficient, but this is untested here.
- The LDtk multi-worlds docs page returned 404; status of the feature beyond "preview" as of 1.5.3 is unconfirmed.

## Q3. Text and ASCII map formats as source (roguelike vaults, PuzzleScript, Quickfort, Spelunky, Qud, Cogmind): how they handle objects, layers, floors, and what goes wrong

### Takeaway
Every mature ASCII map format converges on the same shape: a fixed-width glyph block plus a legend that binds glyphs to terrain, items, monsters or stacks, with a small set of randomisation operators (substitution, shuffle, counted substitution) and, in the stronger systems, an embedded scripting layer (Lua) for anything the DSL cannot express. Multi-floor is handled either by separate blocks per z-level with explicit level-change markers (Quickfort `#>`/`#<`) or by separate files; the recurring failure modes are glyph exhaustion (one character per distinct thing), stacked objects on one cell needing legend aggregates, and vaults that are unreachable, which the engines catch with connectivity validators rather than by eye.

### Cited Findings

**DCSS `.des` vaults**
- A vault is a header plus a `MAP`/`ENDMAP` block of fixed-width lines; `NAME` must come first; `#` lines are comments. Example:
  ```
  NAME:    useless_temple_entry
  TAGS:    temple_entry
  ORIENT:  float
  MONS:    butterfly, plant
  ITEM:    stone q:1
  KFEAT:   O = enter_temple
  MAP
  xx.d.xx
  x..1..x
  @d2O2d.
  x..1..x
  xx.d.xx
  ENDMAP
  ```
  `1`,`2` are the first and second `MONS` entries, `d` the first `ITEM`, `@` the entry point, `O` redefined by `KFEAT`. — [DCSS levels/introduction.txt](https://github.com/crawl/crawl/blob/master/crawl-ref/docs/develop/levels/introduction.txt)
- Default glyph table: unmapped glyphs become floor; walls `x` rock, `X` permanent rock, `c` stone, `m` clear rock, `n` clear stone, `v` metal, `b` crystal, `t` tree; `.` floor, `+` closed door, `=` runed door; `W` shallow water, `w` deep water, `l` lava; `@` entry point (on the outside edge); `}{`, `)(`, `][` stair pairs, `>`/`<` escape hatches; `A` arch, `B` altar, `C` random altar, `G` statue, `T` fountain, `^` trap; items `$` gold, `%` normal, `*` good, `|` superb, `d`-`k` item array; monsters `0` normal, `9` depth+5, `8` depth+2 x2, `1`-`7` monster array. — [DCSS levels/syntax.txt](https://github.com/crawl/crawl/blob/master/crawl-ref/docs/develop/levels/syntax.txt)
- Randomisation operators: `SUBST: ? = T:20 U V` (weighted random per cell, default weight 10); `SUBST: ? : TUV` (colon = one pick shared by all `?`); multiple SUBST lines apply in order. `NSUBST: ? = 3:w / *:l` (first three `?` become `w`, rest `l`; each spec uses `:` for one shared choice or `=` for per-cell choice; omitted count means 1, last spec defaults to `*`). `SHUFFLE: 123w` permutes glyphs; `SHUFFLE: 12/3w` swaps equal-size blocks. `CLEAR: xyz` turns glyphs into blanks that are not part of the map. — [DCSS levels/syntax.txt](https://github.com/crawl/crawl/blob/master/crawl-ref/docs/develop/levels/syntax.txt)
- Custom glyph bindings: `KFEAT: G = C / net trap / antique armour shop / altar_zin`; `KMONS: ? = orc knight / deep elf knight w:3`; `KITEM: ? = potion of curing / potion of haste` (comma lists put several items on one square); `KMASK: W = no_monster_gen`; `KPROP: x = bloody` (applies to cells with that glyph at that point in the sequence, so order relative to SUBST matters); `KFEAT: Z = W` + `KMONS: Z = rat` stacks a monster on terrain under one glyph. `MARKER: A = feat:<name>` or `lua:<expr>`, placed after SUBST/NSUBST/SHUFFLE. `SUBVAULT: X : some_vault_tag / other:20` replaces a glyph region with another vault. — [DCSS levels/syntax.txt](https://github.com/crawl/crawl/blob/master/crawl-ref/docs/develop/levels/syntax.txt)
- Placement: `ORIENT` in `float`, `encompass`, `centre`, compass points; omitting ORIENT makes a minivault; `DEPTH: D:7-13`, `DEPTH: Lair, !Lair:4-6`; `WEIGHT` (default 10); `TAGS` including `no_rotate`, `no_hmirror`, `no_vmirror` (by default the builder may rotate or mirror a vault), `allow_dup`, `uniq_*`, `transparent`, `overwritable`, `no_monster_gen`, `no_item_gen`, `layout_*`. Lua: `: chance(500)` single-line prefix and `{{ }}` blocks. — [DCSS levels/syntax.txt](https://github.com/crawl/crawl/blob/master/crawl-ref/docs/develop/levels/syntax.txt)
- "A vault that is completely inaccessible will fail to load." Wizard-mode testing: `&L "map name"` places the vault on the current level, `&P "map name"` builds a level guaranteed to contain it, `&{` reveals layout. — [DCSS levels/introduction.txt](https://github.com/crawl/crawl/blob/master/crawl-ref/docs/develop/levels/introduction.txt)

**NetHack des-files and Lua**
- 3.6.x des-files: `MAZE:"soko3-2",' '` (name up to 8 chars, fill char or `random`); `FLAGS:noteleport,hardfloor,graveyard`; `GEOMETRY:xadj,yadj` with xadj in left/half-left/center/half-right/right/random and yadj in top/center/bottom/random; `MAP`...`ENDMAP` "can be up to 21 lines high, with lines up to 76 characters, all the same length"; glyphs: space stone, `#` corridor, `.` floor, `-`/`|` walls, `+` door, `S` secret door, `H` secret corridor, `T` tree, `F` iron bars, `{` fountain, `\` throne, `K` sink, `}` moat, `P` pool, `L` lava, `I` ice, `W` water, `A` air, `C` cloud, `B` boundary for irregular REGIONs. Placement by coordinates, `random`, or shuffled registers (`RANDOM_PLACES`, `place[0]`); percent-chance syntax `TRAP[25%]:"polymorph",random`; `ROOM: "ordinary", lit, (3,3), (center,center), (11,9)` and `SUBROOM:"shop",lit,(10,10),(3,3),"town"`; `NON_DIGGABLE:(00,00,13,12)`; `BRANCH:levregion(51,2,77,18),(0,0,40,20)`. ROOM-type levels cannot have arbitrary room shapes. — [NetHackWiki: Des-file format](https://nethackwiki.com/wiki/Des-file_format)
- NetHack 3.7 moves levels to Lua: `des.map({ halign = "center", valign = "center", map = [[ ... ]] })`, also `x`/`y` or `coord`, `lit`, and a `contents = function(map) ... end` callback whose coordinates are relative to the map and which receives `map.width`/`map.height`; `des.level_init({ style = "mines", fg = ".", bg = "}", smoothed=true, joined=true, lit=0 })` and `style = "maze"` with `corrwid`, `wallthick`, `deadends`; `des.room({ type="ordinary", lit=1, x=3,y=3, xalign="center",yalign="center", w=11,h=9 })` with a `contents` callback; `des.door("nodoor", 1, 2)` with states random/open/closed/locked/nodoor/broken/secret; `des.stair("down", 4, 7)`; `des.levregion` types stair-down/stair-up/portal/branch/teleport/teleport-up/teleport-down; `des.terrain(21,12, ".")`; `des.replace_terrain`; `des.non_diggable`; `des.exclusion`; `des.level_flags("noteleport", "mazelevel")`. The map character table adds `Z` wall of lava, `x` "transparent" (for des.map parts) and `w` "any wall" (for selection.match). — [NetHack 3.7 doc/lua.adoc](https://github.com/NetHack/NetHack/blob/NetHack-3.7/doc/lua.adoc)

**Caves of Qud `.rpm`**
- `.rpm` is XML: root `<Map ID Width Height>` containing `<cell X Y>` elements each holding `<object Name="..."/>` elements; zones are 80x25 cells. `Load="Merge"` appends to a cell without deleting existing contents (e.g. the floor); without it a cell's contents are replaced ("The world map expects one terrain object per cell"). Maps resolve by `ID`; if unset the ID is generated from file name and relative path ignoring separators, case and extension (`StreamingAssets/Base/GritGate.rpm` -> `GritGate`; `YourMod/RPM/MyMapFile.rpm` -> `RPM_MyMapFile`); a mod file with the same name as a shipped `.rpm` patches it. Zones reference maps via `<map FileName="Path/To/YourNewMap.rpm" />` or `<map ID="NewMapID" ClearBeforePlace="true" />` in `Worlds.xml`; a chunk file like `preset_tile_chunks/JoppaSultanShrine_3x3.rpm` is mentioned. Example:
  ```xml
  <Map ID="Joppa" Width="80" Height="25" Load="Merge">
    <cell X="41" Y="7"><object Name="Ctesiphus" /></cell>
  </Map>
  ```
  An in-game map editor exists (Modding Utilities > Map Editor; Ctrl+click add, Shift+click flood fill). — [Caves of Qud wiki: Modding:Maps](https://wiki.cavesofqud.com/wiki/Modding:Maps)

**Dwarf Fortress Quickfort (DFHack)**
- Blueprints are `.csv` or multi-sheet `.xlsx`; each cell is one map tile; the first cell is a modeline `#mode` (`dig`, `build`, `place`, `zone`, `burrow`, `notes`, `ignore`, `meta`; no modeline = `#dig`); cells beginning `# ` are comments; backtick and tilde cells are empty; many blueprints per file, each new modeline starting one. Modeline options: `label(name)`, `start(x;y;comment)`, `hidden()`, `message(text)`. Example `#dig start(3; 3; Center tile of a 5-tile square) Regular blueprint comment`. — [DFHack Quickfort user guide](https://docs.dfhack.org/en/stable/docs/guides/quickfort-user-guide.html)
- Symbols: dig `d h u j i r z x s e ...` with priorities (`d1`) and marker prefixes (`mb`, `mw`, `md`); build `Cw` wall, `Cf` floor, `Cr` ramp, `Cu`/`Cd`/`Cx` stairs, `d` door, `b` bed, `t` table, `c` seat, `ga` bridge, `trackNS` tracks; zone `b` bedroom, `h` dining, `o` office, `T` tomb; place stockpiles `f s w a ...` with container counts (`s5`). Expansion syntax `text(WxH)` with negative numbers expanding the other way, e.g. `ga(4x-2)` and `wm(60x3)`; properties in braces `f{name=Seeds links_only=true}:=seeds(3x2)`. — [DFHack Quickfort user guide](https://docs.dfhack.org/en/stable/docs/guides/quickfort-user-guide.html)
- Multi-z-level: `#>` moves down one z-level and `#<` up, with an optional count (`#>2`):
  ```
  #dig Two double-level quarries
  r(10x10)
  #>2
  r(10x10)
  ```
  `#meta` blueprints sequence others by `/label` or `sheet/label` with modifiers `repeat(down 5)`, `shift(0 10)`, `transform(cw flipv)`. Commands: `quickfort list`, `quickfort list --hidden`, `quickfort run library/dreamfort.csv`. — [DFHack Quickfort user guide](https://docs.dfhack.org/en/stable/docs/guides/quickfort-user-guide.html)

**Spelunky room templates**
- Levels are 16 rooms in a 4x4 grid. Room types: 0 side room (no exit guarantees), 1 left+right exits, 2 left+right+bottom (plus top if a type 2 is above), 3 left+right+top. Path algorithm: start in top row; random 1-5 picks left (1-2), right (3-4), down (5); at an edge, drop and reverse; moving down overrides the current room to type 2; after a type 2 the next room must be 2 or 3; dropping from the bottom row places the exit. Solvability is by construction of the path, not by a validator. — [Darius Kazemi: Spelunky Generator Lessons part 1](https://tinysubversions.com/spelunkyGen/)
- Each room template is a 10-column x 8-row grid string; roughly 8-16 templates per room type; rooms are sometimes mirrored. Glyphs: `0` empty, `1` solid, `L` ladder, `P` ladder-top platform, `2` 50% block, `4` 25% push block atop a ladder, `7` 33% spike, `5` ground obstacle placeholder, `6` air obstacle placeholder. Obstacle blocks are 5x3 sub-templates substituted into placeholder areas. Verbatim room template:
  ```
  1100000000
  40L6000000
  11P0000000
  11L0000000
  11L5000000
  1100000000
  1100000000
  1111111111
  ```
  and ground obstacle `00000 / 00102 / 71177`. — [Darius Kazemi: Spelunky Generator Lessons part 2](https://tinysubversions.com/spelunkyGen2/)

**PuzzleScript**
- Levels live in a `LEVELS` section as grids of single characters separated by blank lines, with `MESSAGE ...` lines between levels; the `LEGEND` maps a character to an object or to a stack via `and` (`@ = Crate and Target`); Ctrl/Cmd-click a level in the editor loads it. Example:
  ```
  #########
  #.....@.#
  #.P.*.O.#
  #.......#
  #########
  ```
  — [PuzzleScript docs: Levels](https://www.puzzlescript.net/Documentation/levels.html)

**Cogmind**
- Prefabs are hand-made map pieces; each is split across files: one stores "the data that allows the engine to decipher what objects are referenced within the prefab" and a separate file stores the layout; encounters may replace a room with a prefab or use an existing space. Map generation "Step 1" is to go down a list of potential prefabs and configurations and place them. Cogmind maps export as ASCII text and REXPaint can import those via `-txt2xp`. — [Cogmind: Map prefabs in depth](https://www.moddb.com/news/map-prefabs-in-depth); [Cogmind: Map composition](https://www.moddb.com/games/cogmind/news/map-composition); [Cogmind: ASCII morgue maps](https://www.moddb.com/news/building-the-ultimate-roguelike-morgue-file-part-2-ascii-maps)

### Inferences
- The common grammar across DCSS, NetHack, Spelunky and PuzzleScript is: fixed-width glyph block + legend + per-glyph randomisation + an escape hatch to code. A TypeScript DSL for a town game can copy exactly these primitives: a glyph block, a legend that can bind one glyph to a *stack* (terrain + object + NPC, as DCSS does with `KFEAT`+`KMONS` on one glyph and PuzzleScript does with `and`), and `SUBST`/`NSUBST`-style operators for variation.
- Glyph exhaustion is real: DCSS reserves most of printable ASCII and still needs `KFEAT`/`KMONS`/`KITEM` to redefine glyphs per vault; NetHack uses more than 20 reserved characters. Per-map legends (local redefinition) rather than a global glyph table are the fix every format adopts.
- Multi-floor: Quickfort's `#>`/`#<` z-markers between blocks in a single file is the only format surveyed with native multi-level support; everything else uses one block/file per floor. Quickfort's `#meta` blueprints that compose labelled blocks with `shift`/`transform`/`repeat(down N)` are a good model for composing a building from floor blocks.
- Alignment hazards: NetHack requires all MAP lines the same length (76 max, 21 high); DCSS turns unmapped glyphs into floor silently, which hides typos. A parser for an agent-authored format should error on ragged rows and unknown glyphs rather than defaulting. (Wide/multibyte characters were not discussed in any source found; treat as an inference that a format should restrict glyphs to single-column ASCII.)
- Qud's XML-per-cell with `Load="Merge"` shows the alternative to glyphs: explicit object lists per cell, verbose but with no glyph limit; a hybrid (ASCII for terrain, object list/overlay for stacked things) is what Spelunky and DCSS effectively do.

### Gaps
- Brogue: its "machines" are blueprint tables in C (feature flags, depth ranges), not ASCII; the source file could not be fetched (404) and the Brogue wiki page on machine rooms was not retrieved, so no field-level detail is included.
- Baba Is You level format: not researched (no source retrieved).
- Cogmind's exact prefab file syntax was not found; only the two-file split and REXPaint workflow are documented.
- DCSS map size limits (GXM/GYM) were not stated in the docs retrieved; only "Abyss vaults no larger than 28x23, 23x23 preferred".
- Quickfort `#query`/`#config` modes: the fetched guide text did not document them; the mode list above is as reported by the fetch and may be incomplete.
- No source discussed wide (CJK/emoji) characters or tab alignment problems in ASCII maps explicitly.

## Q4. Rule-based autotiling: Tiled terrain sets and Automapping, LDtk rules, Godot terrains, going from a logical grid to rendered tiles

### Takeaway
Three systems solve "logical grid -> art": Wang/terrain sets (Tiled, Godot) pick tiles by matching corner/edge labels against neighbours, and LDtk/Tiled Automapping use pattern rules (match N x N neighbourhoods of logical values, emit tiles, with chance/noise/modulo). All of them have a scriptable or re-implementable core (Godot exposes `set_cells_terrain_connect`; LDtk's matcher is ~50 lines of documented semantics; Tiled's terrain rules are data in the tileset JSON), so an agent can keep ASCII/IntGrid as the source of truth and generate tiles in a build step.

### Cited Findings
- Tiled terrain set types: Corner (complete 2-terrain set = 16 tiles), Edge (16 tiles; roads, fences, platforms), Mixed (complete 2-terrain set = 256 tiles; reduced 47-tile "Blob" sets also use this type). Up to 254 terrains per set; all tiles must be in one tileset; terrains only interact within one set; the brush also adjusts neighbours and inserts intermediate transitions when two terrains have no direct transition (dirt on cobblestone routed through sand). Tile probability = tile probability x terrain probabilities at each corner/side; probability 0 disables automatic use. Tile transformations (1.5+: flip H/V, rotate 90/180/270, "Prefer Untransformed Tiles") reduce the 47-tile Blob set to 15 tiles. Terrain info from 1.5+ is not readable by older versions. Embedded tilesets should be avoided so terrain info is shared. — [Tiled manual: Terrain Sets](https://doc.mapeditor.org/en/stable/manual/terrain/)
- Tiled Automapping: `rules.txt` lists rule maps in order (with `[town*]` filename filters, Tiled 1.9+), set project-wide via the "Automapping rules" project property (1.4+) or per-directory. A rule map is a normal map with tile layers named `input[not][index]_<target>` and `output[index]_<target>`; rules are 8-connected regions of tiles; by default all rules match simultaneously and apply top-to-bottom then left-to-right, or `MatchInOrder` applies each immediately. Special tiles (1.9+ "Automapping Rules Tileset", via a `MatchType` property): Empty, Ignore, NonEmpty, Other, Negate. Map properties: `DeleteTiles`, `AutomappingRadius`, `MatchOutsideMap` (default true for infinite maps), `OverflowBorder`, `WrapBorder`, `MatchInOrder` (1.9+), `NoOverlappingOutput`. Per-rule options via a `rule_options` object layer: `ModX`/`ModY`, `OffsetX`/`OffsetY`, `Probability` (0..1), `Disabled`, `IgnoreLock` (1.10+). Output layer `Probability` weights random output indices (1.10+). Input layers can `IgnoreHorizontalFlip`/`IgnoreVerticalFlip`/`IgnoreDiagonalFlip` (1.11+). Objects can be output with caveats. Legacy `regions` layers switch on the pre-1.9 system. Terrains "can reliably place cliff tops but not the vertical cliff sides, which Automapping handles". — [Tiled manual: Automapping](https://doc.mapeditor.org/en/stable/manual/automapping/)
- LDtk rules: pattern sizes 1/3/5/7 (`MAX_AUTO_PATTERN_SIZE = 9`), cell values encode exact value / not value / any non-zero / zero / value-group membership, with `chance`, Perlin gating, `xModulo`/`yModulo`/offsets, `checker`, flips, `outOfBoundsValue`, `breakOnMatch`, Single vs Stamp tile modes; the editor bakes results into `autoLayerTiles`. — [LDtk source: AutoLayerRuleDef.hx](https://github.com/deepnight/ldtk/blob/master/src/electron.renderer/data/def/AutoLayerRuleDef.hx); [LDtk JSON_DOC.md](https://github.com/deepnight/ldtk/blob/master/docs/JSON_DOC.md); [LDtk source: Const.hx](https://github.com/deepnight/ldtk/blob/master/src/electron.renderer/Const.hx)
- Godot 4 terrain sets: modes Match Corners and Sides, Match Corners, Match Sides (corresponding to Godot 3's 3x3, 2x2 and 3x3 minimal bitmasks; "similar to the Tiled editor"); terrain set IDs and terrain IDs start at 0, -1 means none; each tile has "Terrain Peering Bits" where -1 is empty space, e.g. top-left/top/top-right = -1 means the tile is used only when there is empty space above. — [Godot docs: Using TileSets](https://docs.godotengine.org/en/stable/tutorials/2d/using_tilesets.html)
- Godot scripted autotiling: `set_cells_terrain_connect(cells: Array[Vector2i], terrain_set: int, terrain: int, ignore_empty_terrains: bool = true)` joins same-terrain neighbours and may update neighbouring tiles for correct transitions; `set_cells_terrain_path(path, terrain_set, terrain, ignore_empty_terrains)` connects successive path cells; both require the TileSet to contain "all required terrain combinations" or results are "unexpected"; updates are batched until end of frame (`update_internals()` forces). — [Godot docs: TileMapLayer](https://docs.godotengine.org/en/stable/classes/class_tilemaplayer.html)
- Marching-squares framing of tile sets (Boris the Brave): choose tiles by whether each corner is solid or empty; "If you line up tiles so the black and white corners always match, the red lines always connect together nicely"; missing rare combinations are safe in WFC because it "never build[s] configurations that require those tiles". — [Boris the Brave: WFC tips and tricks](https://www.boristhebrave.com/2020/02/08/wave-function-collapse-tips-and-tricks/)

### Inferences
- For an agent-authored pipeline, the cleanest split is: ASCII/IntGrid is canonical; a deterministic autotiler (either a Wang-set resolver reading Tiled `wangsets` JSON or an LDtk-style rule matcher) produces the render layer; the render layer is never hand-edited. This keeps diffs readable and lets tests compare logical grids.
- Wang/terrain sets handle floors, grass/dirt, water and walls-as-regions well; pattern rules (LDtk/Automapping) are needed for asymmetric art such as cliff faces, wall tops versus wall faces in a top-down view, and anything that depends on "what is above me". Both Tiled and LDtk docs make this distinction.
- Godot's `set_cells_terrain_connect` is the only engine API among those surveyed that runs autotiling at runtime from code without an editor; in Node you would reimplement one of the two algorithms (both are small).

### Gaps
- Tiled's `wangid` position order was not spelled out on the page retrieved (TMX reference would have it).
- No benchmark or source was found comparing rule-pattern autotiling versus Wang-set autotiling for top-down building walls specifically.

## Q5. Procedural building, interior and town layout: treemaps/BSP, grammars, constraint-based furniture, graph-based rooms, WFC/Townscaper, Watabou, Shadows of Doubt, Unexplored, Sims walls, RimWorld

### Takeaway
The published pipelines share a three-stage shape: footprint/lot partition (Voronoi/bisection for towns, polyomino-split-into-rectangles or squarified treemap for a building), room connectivity from an adjacency/connection graph with corridor insertion where required rooms are not adjacent, then furniture by cost-function optimisation (simulated annealing with accessibility, visibility, pathway and prior-distance terms) or by preset room configurations. WFC is strong for texture-like detail and organic towns but needs extra constraints (fixed tiles, path constraints, multi-pass) to guarantee connectivity.

### Cited Findings

**Floor plans: treemaps, BSP, constrained growth**
- Marson & Musse (2010) introduced squarified-treemap room subdivision; the 2012 extension (Mirahmadi & Shami) takes a rectangular footprint with aspect ratio sampled from Uniform(1,2), draws room count/bedrooms from 2001 Canadian census distributions, areas Uniform(8,18) for bedrooms and Uniform(3,11) for others, groups rooms into social/service/private zones, subdivides footprint -> zones -> rooms with a squarified treemap (chosen because standard treemaps produce elongated rooms), then builds corridors: identify rooms that must reach the living room but are not adjacent, build a graph of their interior walls, prune degree-1 edges, Dijkstra for the shortest connecting path (corridor area treated as waste), apply Shift/Lengthen edge actions so vertex-touching rooms get door space, discard awkward shapes, pick the smallest corridor, extrude it from overlapping rooms. Doors: connection graph from the hierarchy tree plus random function-based extras (kitchen-dining), prohibitions (bedroom-kitchen, bedroom-bedroom), fixed door size at random positions on shared walls; exterior rooms get windows unless prohibited (bathrooms); at least one exterior door. Claims real-time but reports no timings. — [Mirahmadi & Shami, arXiv 1211.5842](https://ar5iv.labs.arxiv.org/html/1211.5842)
- BSP floorplans (hobbyist report): recursively split space, one room per leaf; "There is not that much variety because of the way BSP works and my room sizes being very limited." — [Py-Py-Pyramid devlog: Procedural Map Generation](https://mappi.itch.io/py-py-pyramid/devlog/269210/procedural-map-generation-1)
- Lopes, Tutenel, Smelik, de Kraker, Bidarra (2010) "A constrained growth method for procedural floor plan generation": per the paper's retrievable snippet, "Using the A* algorithm, a shortest path is determined, visiting all rooms that need a connection with the corridor." — [bidarra.GAMEON10.pdf](https://graphics.tudelft.nl/~rafa/myPapers/bidarra.GAMEON10.pdf) (server returned 503 on full fetch; only this snippet confirmed)

**Furniture: cost-function optimisation**
- Yu et al. 2011 "Make it Home" (SIGGRAPH 2011; authors Yu, Yeung, Tang, Terzopoulos, Chan, Osher): extracts spatial and hierarchical relationships from example scenes (for each object, prior distance and angle to the nearest wall `(d̄_i, θ̄_i)`; parent-child "on top of" hierarchies; pairwise relationships such as TV facing sofa with mean relative distance/angle extracted), represents each object as a 2D bounding box with per-surface "accessible spaces" (size from examples or human body dimensions) and a viewing frustum for objects whose front must be visible (TV, painting). Cost terms: accessibility (penalty when any object overlaps another's accessible space), visibility, pathway (pathways between doors are cubic Bezier curves represented as a series of rectangles, cost defined like visibility over those rectangles, and control points are themselves movable), prior distance `C_prd = Σ ||d_i - d̄_i||` (Eq. 6) and prior orientation `C_prθ = Σ ||θ_i - θ̄_i||` (Eq. 7), pairwise distance and orientation; weights `w_a, w_v, w_pair, w_path, w_prd, w_prθ`. Optimisation: simulated annealing with a Metropolis-Hastings step; state `φ = {(p_i, θ_i)}`; moves are translation `p_i + δp` with `δp ~ N(0, σ_p²)` and rotation `θ_i + δθ` with `δθ ~ N(0, σ_θ²)` performed separately ("more stable"), plus swapping two objects' `(p, θ)` for global reconfiguration, with step size proportional to temperature. Initialisation is random; an example converges in 25,000 iterations; Table 1 reports 18,000-42,000 iterations taking 22-376 s per scene on a 3.33 GHz Intel Xeon. Ablations show omitting accessibility yields blocked furniture, omitting the pathway term blocks doors, omitting prior distance leaves furniture off the wall. — [Yu et al., Make it Home (UCLA CAM report 11-49)](https://ww3.math.ucla.edu/camreport/cam11-49.pdf)
- A 3D indoor-scene survey summarises the same system: priors "tied to ergonomic factors such as visibility and accessibility" combined into a cost function; "factors including accessibility, visibility and pathway connecting the doors are added to the cost function." — [Analysis and Modeling of 3D Indoor Scenes (arXiv 1706.09577)](https://arxiv.org/pdf/1706.09577)
- A student thesis on interior generation notes that randomly placed furniture "is almost always unlivable", e.g. "a bookshelf placed in the middle of a room rather than against a wall". — [Lampert, Procedural generation of interior settings (HSLU)](https://blog.hslu.ch/games/files/2021/11/Manuel_Lampert_Procedural_generation_of_interior_settings.pdf)

**Cyclic / grammar-based dungeon layout (Unexplored)**
- Unexplored builds a level on a grid of graph nodes (about 5x5) that are only annotated, never deleted or moved. Stage 1: draw start, goal and a loop; the entrance and goal split the loop into two arcs; pick one of 24 major cycle types (alternative routes, lock-and-key with one-way "valves", hubs, lake, ThreeLeverHub with three keys and a guardian); add minor cycles, lengthen, add dead ends; shuffle. The circle alone takes about 40 rules; variable-size structures use setup/grow/cleanup rules because each PhantomGrammar rule matches a fixed number of nodes. Stage 2 resolves abstractions (biomes, non-terminal "Obstacle" nodes, key/lock pairs kept consistent by a special edge). Stage 3: double the grid so corridor pieces fill gaps, expand 5x and shape each 5x5 block with rules (doors to single tiles, rooms get walls, caves via cellular automata), convert to a fine grid, place items/enemies, terrain by noise and seed growth, smoothing, vegetation. About 5,000 find-replace rules across Ludoscope modules. Relationship data (which key opens which lock, which enemy patrols where) is kept in the output and used by a "Pray For Help" feature that detects what blocks progress and fixes it, acting as a completability safety check. — [Boris the Brave: Dungeon Generation in Unexplored](https://www.boristhebrave.com/2021/04/10/dungeon-generation-in-unexplored/)

**WFC and Townscaper**
- WFC overlapping model: count NxN patterns (N typically 3) in the input, optionally with rotations/reflections; the wave is an output-sized array of boolean pattern coefficients; loop: observe the minimal-nonzero-entropy cell and collapse by weighted choice, propagate (AC-4), until all cells are decided or some cell has zero options (contradiction; "surprisingly rare"; the problem is NP-hard). Simple tiled model: initialised from a tile list and adjacency data; each tile has a symmetry type under D4 so only adjacencies up to symmetry are listed. Uses: Bad North (with a heuristic so each observed zone stays navigable), Townscaper (WFC + marching cubes on irregular grids), Caves of Qud (multi-pass pipeline). — [mxgmn/WaveFunctionCollapse README](https://github.com/mxgmn/WaveFunctionCollapse)
- Practical WFC constraints: a path constraint "looks globally across the entire generated output" to force connectivity between annotated tiles; without it WFC "will often generate a bunch of disconnected rooms"; fix tiles before generation (entrances/exits; or "draw the level's floorplan and let WFC fill in the interior"); multi-pass (another algorithm places structure, WFC fills detail; Caves of Qud subdivides the map and runs WFC with different tile sets per area); avoid or down-weight T-junction tiles for roads/rivers; big tiles spanning several cells; biome filtering; large single-pass WFC maps "start to look very samey". — [Boris the Brave: WFC tips and tricks](https://www.boristhebrave.com/2020/02/08/wave-function-collapse-tips-and-tricks/)
- Townscaper's irregular grid: start from a hexagon of equilateral triangles, merge random pairs into quads, subdivide so every face is a quad, relax the mesh; Stålberg describes building square tiles and skewing them to fit the grid to break repetition. He presented "Organic Towns from Square Tiles" at IndieCade Europe 2019. — [Sylves: Townscaper grid tutorial](https://boristhebrave.com/docs/sylves/1/articles/tutorials/townscaper.html); [Game Developer: How Townscaper works](https://www.gamedeveloper.com/game-platforms/how-townscaper-works-a-story-four-games-in-the-making)
- Brian Bucklew presented "Dungeon Generation via Wave Function Collapse" at Roguelike Celebration 2019. — [Caves of Qud press kit](https://cavesofqud.com/press-kit/)

**Watabou**
- Medieval Fantasy City Generator: the map is partitioned into cells the author calls "patches"; a few central patches are marked as city and most city patches become "regular" patches cut into blocks whose cuts become streets; newer versions merge patches and build streets across whole districts so cell edges are "almost invisible"; version 0.9.0 added a "Lots method" dropdown with Bisection, Voronoi and Twisted; warp tools Relax/Equalize cannot change mesh topology ("you can't merge or split cell"). — [Watabou on Patreon: MFCG 0.10.0](https://www.patreon.com/posts/87882877); [Watabou on Patreon: MFCG 0.9.0](https://www.patreon.com/posts/61026228)
- Procgen Mansion, in the author's words: "generate a polyomino, split it into rectangles" — a footprint is built from a chosen size, divided into rectangular wings, and floor count depends on wing size. The newer Dwellings generator (multi-floor export, stairs, roofs) is replacing it as Procgen Arcana's building generator. — [Procgen Mansion comments](https://watabou.itch.io/procgen-mansion/comments?before=14); [Dwellings devlog 1.3.2](https://watabou.itch.io/dwellings/devlog/798071/132-permalinks-and-multi-floor-export)

**Shadows of Doubt**
- Buildings are "split into floors, then divided into 'addresses', and within them 'rooms'" with the goal of generating large numbers of apartments, offices and cafes with variety but little hand-designed work; floors are planned on a 5x5 grid in a floor editor with zoning (ground-floor retail, residential above) and floor presets; layouts are kept simple because of citizen pathfinding; procedural decoration is designed to avoid being "too random and cookie-cutter"; ventilation ducts are generated per building with per-room vent-count ranges. — [Shadows of Doubt DevBlog #13](https://colepowered.com/2019/02/); [DevBlog #14: Interior Colours](https://colepowered.com/?p=34717); [DevBlog #17: Ventilation Shafts](https://colepowered.itch.io/shadows/devlog/98636/shadows-of-doubt-devblog-17-ventilation-shafts)

**RimWorld**
- RimWorld's settlement generation resolves named symbols against rects; a modding error shows the shape: `Could not find any RuleDef for symbol "..." with any resolver that could resolve rect=(25,38,64,77)`, i.e. a symbol-resolver grammar over rectangles (BaseGen). — [Steam Workshop discussion (error log)](https://steamcommunity.com/workshop/filedetails/discussion/2798478679/4632610189255714853)

### Inferences
- For a Stardew/Ultima-scale town (dozens of buildings, each a few rooms), the treemap/polyomino approach is the right size: lot -> polyomino footprint -> rectangles -> rooms via squarified treemap, then a connection graph with prohibitions and a corridor only when a required adjacency is missing. The Mirahmadi/Marson pipeline is fully specified above and has no dependencies beyond Dijkstra.
- Make it Home's cost terms translate directly to a tile grid: accessible spaces become "keep these tiles free" masks per furniture piece, the pathway term becomes a required walkable path between doors, and prior wall distance becomes "beds/wardrobes against walls". On a small tile grid, exhaustive or greedy search over tile positions replaces annealing; the paper's 22-376 s runtimes are for continuous 2D with many objects.
- Unexplored's lesson applies at town scale: generate the abstract graph (which shop connects to which street, which house has a back door) before any tiles, and keep relationship data in the output for validators.
- WFC is the wrong primary tool for an interior floorplan (connectivity and room semantics need global constraints) but is reasonable for decorative passes (floor patterns, garden plots, rooftops) after structure is fixed, which is how Caves of Qud and Bad North use it.
- Sims-style "walls on tile edges" was not documented in any source found; the Shadows of Doubt and Quickfort models (`Cw` wall as a tile) treat walls as cells, which is also how Stardew/Ultima-style tilesets are drawn.

## Q6. Validating and testing layouts without a human: connectivity, door checks, flood fill, playtest bots/planners, snapshot tests, editor/mod validators

### Takeaway
Every roguelike with a vault format runs a connectivity validator (DCSS `validate {{ glyphs_connected('{', '>') }}` and `has_exit_from_glyph`, with automatic re-roll of random transforms and eventual level discard), Spelunky avoids validation by constructing the solution path first, Unexplored keeps lock/key relationship data to detect and repair blockers, and Rebellion tests whole games with a numeric domain-independent planner. Editors offer little: LDtk and Tiled validate schema, not gameplay. For an agent, flood-fill reachability plus door/warp target checks plus ASCII file snapshots (Vitest `toMatchFileSnapshot`) are the cheap, proven combination.

### Cited Findings
- DCSS: a `validate` block runs after SUBST and SHUFFLE transforms; returning false or nil makes the builder reapply the transforms and validate again, and if validation keeps failing the level is discarded and retried. Examples: `validate {{ return has_exit_from_glyph('{') }}` and `validate {{ return glyphs_connected('{', '>') }}`. `has_exit_from_glyph()` returns true if the player can leave the vault from that glyph without digging (accounting for merfolk swimming deep water). `veto {{ ... return true ... }}` rejects a map; vetoing a `PLACE`-tagged vault with no replacement makes level generation fail and the game close. The dgn API also lists `points_connected`, `orig_glyphs_connected`, `gly_point`/`gly_points`, `num_matching_markers`. A `scripts/placement.lua` debug tool tests vault placement. — [DCSS levels/advanced.txt](https://github.com/crawl/crawl/blob/master/crawl-ref/docs/develop/levels/advanced.txt)
- DCSS: "A vault that is completely inaccessible will fail to load"; `&P "map name"` forces a level containing the vault for testing. — [DCSS levels/introduction.txt](https://github.com/crawl/crawl/blob/master/crawl-ref/docs/develop/levels/introduction.txt)
- Spelunky guarantees a solution path by construction (room types with guaranteed exits along the generated path) rather than by validating; the write-up never uses the term validation. — [Darius Kazemi: Spelunky Generator Lessons part 1](https://tinysubversions.com/spelunkyGen/)
- Unexplored keeps relationship data (which key opens which lock, which enemy patrols which area) in the level output; the game uses it for debugging and for "Pray For Help", which determines what is blocking progress and can fix it, acting as a completability safety check. — [Boris the Brave: Dungeon Generation in Unexplored](https://www.boristhebrave.com/2021/04/10/dungeon-generation-in-unexplored/)
- WFC connectivity: Tessera's path constraint enforces a path between annotated tiles globally; Bad North used a heuristic so each observed zone stays navigable. — [Boris the Brave: WFC tips and tricks](https://www.boristhebrave.com/2020/02/08/wave-function-collapse-tips-and-tricks/); [mxgmn/WaveFunctionCollapse README](https://github.com/mxgmn/WaveFunctionCollapse)
- Rebellion, GDC 2021 AI Summit, "Automated Game Testing Using a Numeric Domain Independent AI Planner" (Bram Ridder): "Instead of testing a part of a game, or have a bot play a level for an amount of time, we developed a system that plays entire games from start to finish like a player would", combining a numeric domain-independent planner with behaviour trees, shown on Zombie Army 4, Sniper Elite and Evil Genius 2. — [GDC Vault: AI Summit: Automated Game Testing](https://gdcvault.com/play/1027236/AI-Summit-Automated-Game-Testing)
- Related industry talks: Ubisoft GDC 2019 client bots for The Division; EA SEED on automated game testing (2021). — [80.lv: Using AI-controlled players to test The Division](https://80.lv/articles/gdc-using-ai-controlled-players-to-test-the-division/); [EA SEED: RE-WORK 2021 automated game testing](https://ea.com/seed/news/re-work-2021-automated-game-testing)
- Stardew/SMAPI map checks (community documentation): Content Patcher reports which mod's map failed and names the missing tilesheet ("invalid tilesheet path"); SMAPI refuses to load a farm map that reorders vanilla tilesheets (crash near the greenhouse) so extra tilesheets are prefixed with "z"; SMAPI auto-adds missing newer tilesheets to older replacement maps and warns; Content Patcher reports `Load ... has a FromFile which matches non-existent file`. — [Stardew Modding Wiki: How to read your SMAPI log](https://stardewmodding.wiki.gg/wiki/Tutorial:_How_to_read_your_SMAPI_log); [Stardew forums: Common modding issues in 1.5](https://forums.stardewvalley.net/threads/common-modding-issues-in-1-5.3199/latest)
- Pokémon decomp maps: Porymap "is a nearly universally-used editor" for Gen 3 decomp map JSON, events, warps and connections; the Archipelago Emerald randomiser documents that "a single doorway often comprises several warp events", that warps can be one-way (marked with `!` when the destination does not lead back), and that map connections come from warps, overworld borders, or Dive. — [pret Emerald wiki: Useful Modding Tools](https://code.heni.lol/decomp/emerald/wiki/Useful-Modding-Tools); [Archipelago Pokémon Emerald: warps.md](https://git.hollymcfarland.com/monorail/Archipelago/src/branch/main/worlds/pokemon_emerald/docs/warps.md); [Archipelago Pokémon Emerald: region data.md](https://git.hollymcfarland.com/monorail/Archipelago/src/branch/main/worlds/pokemon_emerald/docs/region%20data.md)
- Snapshot testing in Node: Vitest `toMatchSnapshot()` writes `__snapshots__/<test>.snap`; `toMatchInlineSnapshot()` embeds in the test; `await expect(result).toMatchFileSnapshot('./test/basic.output.html')` compares against a named external file with any extension (recommended for non-JS content); `vitest -u` updates; in CI (`process.env.CI` truthy) snapshots are not written and mismatches/missing/obsolete snapshots fail; `expect.addSnapshotSerializer` and `test.snapshotSerializers` customise serialisation. — [Vitest guide: Snapshot](https://vitest.dev/guide/snapshot)
- LDtk entity definitions carry `maxCount`, `limitScope` (PerLayer/PerLevel/PerWorld) and `limitBehavior`, and field definitions carry `min`/`max`, `regex`, `canBeNull`, `allowedRefs`/`allowedRefTags`; these are the editor's only built-in content constraints. — [LDtk JSON_DOC.md](https://github.com/deepnight/ldtk/blob/master/docs/JSON_DOC.md)

### Inferences
- The DCSS pattern (randomise -> validate -> re-roll -> give up after N) is directly reusable as a test harness for procedural buildings: generate, run `glyphs_connected(door, every room)`-style checks, and on failure reseed; count failure rate as a metric.
- "Every door leads somewhere" is the Archipelago warps model: a door is a pair of warp events that must be mutually consistent unless explicitly one-way; a validator can assert that for each door object in map A pointing at B, B contains a return door pointing at A, and flag `!` one-ways.
- Flood-fill room detection falls out of the Spelunky/DCSS glyph model: walls are a glyph class, rooms are connected components of non-wall cells, and each component must contain at least one door cell; this also catches the Mirahmadi "awkward shapes" case by component bounding-box fill ratio.
- Vitest's `toMatchFileSnapshot` with a `.txt` extension is the right fit for ASCII renders of generated maps: reviewers read the diff as a picture, and CI fails on drift without any GUI.
- A planner-driven bot (Rebellion) is overkill for a 2D town; a BFS over the walkability grid plus a schedule check ("can every NPC reach every location on its daily schedule") is the equivalent for this genre.

### Gaps
- GDC Vault pages for the Rebellion talk are access-limited; no transcript or slide details beyond the abstract were obtained.
- Porymap's own validation features (e.g. connection checks, heal location checks) were not found in documentation; only the decomp community's warp conventions.
- Content Patcher's official map validation rules were not retrieved; findings are from community troubleshooting pages.
- No roguelike-community meta-post on level validators was found beyond DCSS's own docs.
- The escholarship Go-Explore thesis on level traversal testing returned empty content.

## Q7. Headless hot-reload and live-edit loops: watch, validate, re-render ASCII/PNG

### Takeaway
Both editors already watch files (Tiled reloads worlds "when their file changes on disk"; LDtk writes Super Simple Export PNGs/CSVs on every save), and `sharp.composite()` can composite hundreds of tile crops into a PNG from Node without a display, so a watch -> validate -> ASCII snapshot -> PNG render loop is achievable with stock tools.

### Cited Findings
- Tiled: "Worlds reload automatically when their file changes on disk." — [Tiled manual: Worlds](https://doc.mapeditor.org/en/stable/manual/worlds/)
- LDtk Super Simple Export regenerates `_composite.png`, per-layer PNGs, IntGrid PNG/CSV and `data.json` per level on save (project must be saved at least once). — [LDtk docs: Super simple export](https://ldtk.io/docs/game-dev/super-simple-export/)
- sharp: `composite(images) => Sharp` (since 0.22.0) composites one or more overlays over the base image; each item is `{ input, left, top, gravity, blend, tile, ... }` where `input` is a Buffer, file path, `{create:{width,height,channels,background}}`, `{text}` or `{raw:{width,height,channels}}`; `top`/`left` override `gravity`; `blend` defaults to `'over'`; overlays must be no larger than the base; resize/extract/rotate on the pipeline apply to the base before compositing; per-overlay `limitInputPixels` default 268402689. Example: `sharp('input.gif', { animated: true }).composite([{ input: 'overlay.png', tile: true, blend: 'saturate' }]).toBuffer()`. — [sharp API: composite](https://sharp.pixelplumbing.com/api-composite/)
- Cogmind's workflow is a precedent for ASCII renders as a review artefact: maps export as ASCII text which REXPaint imports via `-txt2xp`. — [Cogmind: ASCII morgue maps](https://www.moddb.com/news/building-the-ultimate-roguelike-morgue-file-part-2-ascii-maps)
- Vitest file snapshots for arbitrary text output, updated with `-u`, never written in CI. — [Vitest guide: Snapshot](https://vitest.dev/guide/snapshot)

### Inferences
- A render step with sharp is: pre-`extract` each used tile once from the tileset into Buffers (cache by tile id), then one `composite()` call with one entry per non-empty cell (`left = x*tw, top = y*th`), layers in order. The overlay-count cost is linear and no source gives a hard cap; for a 64x64 map that is ~4k overlays per layer, which is fine but worth batching per layer or per chunk.
- Because LDtk's Super Simple Export already emits IntGrid CSVs and composite PNGs on save, an agent that does author in LDtk JSON can get a "look" artefact for free by having the editor open; headless, the sharp path is the equivalent.
- A practical loop: `chokidar`-style watch on `maps/**/*.txt|*.json` -> parse -> validators (ragged rows, unknown glyphs, connectivity, door targets) -> write `renders/<map>.txt` ASCII and `renders/<map>.png` -> Vitest file snapshots of the ASCII. (Watcher library choice is an inference; no source compared them.)

### Gaps
- No source documented sharp's performance with thousands of composite overlays; node-canvas was not researched as an alternative.
- No official statement found on whether LDtk reloads a project edited externally while open.
