# Hand-roll the sim, commit the bindings, wrap for stores last

Researched 2026-10-23. Synthesizes the three `stack3_*` notes in `notes/` (Rust sim toolkit, Rust/TS boundary, mobile paths), building on `engine-deep-dive.md` and the `engine2_*` notes. Crate and package versions are as reported by crates.io and npm on 2026-10-23. Sentences with an inline link are backed by a source in the notes. Sentences marked "Inference" are a reading of that evidence. Vendor claims are labelled as such.

Build the Rust core as four small crates (`content`, `sim`, `tools`, `sim-wasm`) with no framework in the middle: a `BinaryHeap` keyed by `(tick, seq)` for the event queue, a closed `Event` enum, `Vec`s indexed by typed ids, `BTreeMap` wherever iteration order matters, one `rand_pcg` stream per subsystem seeded from the input, integer math only, `postcard` for snapshots and the input log, JSON plus `schemars` for content, and `xxh3` over the serialized state as the per-tick hash. The DES frameworks on crates.io are dead or built for other problems, the generational arenas and ECS crates hide allocator state that a replay needs explicit, and every determinism bug reported by the Rust precedents (Egregoria, ggrs, Rapier, OpenTTD, Factorio) falls into a class that integer-only, single-threaded, BTreeMap/Vec code with the whole state in one serde struct removes by construction. The boundary is kept honest by committing `ts-rs` 12 output into the TypeScript workspace and failing CI on `git diff`, by pinning `wasm-bindgen` crate and CLI to the same `0.2.129` (they must match since `0.2.128`), by a shared `fixtures/` directory that both `insta` and vitest read, and by one `just check` that runs the Rust suite, regenerates types, builds the wasm, and compares the native and wasm hash sequences. On mobile, the web build is the product: ship it as a PWA first (iOS 26 made every site installable), wrap it with Capacitor 8 for the stores, build iOS on a rented macOS runner (Codemagic's 500 free M2 minutes a month, then $0.095/min), and treat SharedArrayBuffer, WebGPU and orientation lock as unavailable. The viewer library recommendation under those constraints is PixiJS v8 used as a renderer, not an engine, behind the project's own viewer seam, with the viewer owning integer scaling, the frame loop and WebGL context-loss recovery; Phaser 4 is the named alternative if its documented automatic context restoration (a vendor claim) proves out in a one-week spike on WebKit. Ian's doubt about PixiJS is right on one axis (context loss is an open-issue area) and misplaced on maturity, and the typed, deterministic part of this stack now lives in Rust where the compiler and clippy enforce it, which lowers what the viewer library has to be.

## Four small crates and a hand-rolled event heap cover the whole sim

The first finding of the toolkit note is negative: nothing on crates.io should sit between the project and its own event queue. `nexosim` 1.0.0 (2026-02-03) is an async, multi-threaded actor framework drawn from "experience on spacecraft real-time simulators", with no determinism or wasm statement in its README ([nexosim README](https://github.com/asynchronics/nexosim)); `desim` last released in 2023 and has 69 downloads in 90 days ([crates.io](https://crates.io/crates/desim)). The indexed heaps (`priority-queue` 2.7.0, `keyed_priority_queue` 0.4.2) add a map that must also be serialized, and `keyed_priority_queue` documents no serde support and no pluggable hasher ([docs.rs](https://docs.rs/keyed_priority_queue/latest/keyed_priority_queue/)). Inference: a `std::collections::BinaryHeap<Reverse<Scheduled>>` where `Scheduled` derives `Ord` over `(tick, seq, event)` and `seq` comes from a counter stored in the sim state is about fifty lines, serializes with serde out of the box, and gives a total order with no ties, which matters because OpenTTD lists "unstable sort ordering for equal keys" among its known desync causes ([OpenTTD desync.md](https://github.com/OpenTTD/OpenTTD/blob/master/docs/desync.md)). Cancellation is lazy: each villager carries a `plan_generation` counter, events record the generation they were scheduled under, and stale events are dropped on pop. The `Event` type is a closed enum (`WakeUp`, `ArriveAt`, `ObjectFree`, `DayRollover`, and so on), never boxed closures, because only an enum derives `Serialize`, `Ord` and `Hash` and can enter the state hash. The calendar is derived arithmetic over a single `tick` (86,400 ticks per day at one game-second per tick), so there is no second clock to desync.

### Determinism rules, enforced by clippy rather than by memory

The rand book is explicit that `StdRng` and `SmallRng` carry "no reproducibility guarantee", that everything else in the ecosystem is "expected to give results that are reproducible across platforms and patch releases", that `usize` ranges are non-portable, and that `f32`/`f64` distributions "may not be portable" because of platform transcendental functions ([rand book: reproducibility](https://rust-random.github.io/book/crate-reprod.html)). rand 0.9.0 changed `shuffle`, `choose` and the `Uniform` algorithms and so broke value stability, and 0.10.0 (2026-02-08) moved `StdRng` onto the `chacha20` crate and removed the `small_rng` feature ([rand CHANGELOG](https://github.com/rust-random/rand/blob/master/CHANGELOG.md)). The recipe: `rand = { version = "0.10", default-features = false }` so that `sys_rng`, `thread_rng` and therefore `getrandom` never enter the graph ([rand features](https://docs.rs/crate/rand/latest/features)), plus `rand_pcg` 0.10.2 `Pcg32` (or `rand_xoshiro` 0.8.1) with the `serde` feature, one stream per subsystem (schedule jitter, idle choice) held inside the sim state so that adding a cosmetic random call cannot shift a gameplay stream, which is the "separate RNG for cosmetic effects" rule in the desync guide ([bugnet.io](https://bugnet.io/blog/how-to-debug-desync-in-deterministic-lockstep-games)). Sample with `random_range` on `u32`, never on `usize` or a float.

Collections follow the same logic. aHash's README says "different computers or computers on different versions of the code will observe different hash values" and that it "is not intended for ... applications which persist hashed values" ([aHash README](https://github.com/tkaitchuck/aHash/blob/master/README.md)); std's `HashMap` iteration order depends on the hasher seed, which is what bit Qiskit until it swapped in `IndexMap` ([Qiskit commit](https://cdn05042023.gitlink.org.cn/scnc/qiskit/commit/48cfab601e16517eca1a5249a45cc43726bf7d61)), and Egregoria recommends `BTreeMap`/`BTreeSet` "at a modest runtime cost" ([Egregoria #90](https://github.com/uriopass/egregoria/issues/90)). Inference: at a few dozen villagers and places the BTree cost is immaterial, so `BTreeMap` is the default for anything iterated during simulation, `Vec` indexed by typed ids is the hot path, and `IndexMap` 2.14.2 is used only where insertion order is semantically wanted. Math is integer: ticks, tiles, durations and path costs. Rust does not guarantee NaN bit patterns are "portable or even fully deterministic" ([f32 docs](https://doc.rust-lang.org/nightly/core/primitive.f32.html)), and the wasm spec makes NaN sign nondeterministic ([LLVM Discourse](https://discourse.llvm.org/t/semantics-of-nan/66729?page=2)), so the sim has no floats at all; `fixed` 1.31.0 (MSRV 1.93, no trig built in) is the fallback if sub-tile motion is ever simulated rather than rendered ([docs.rs fixed](https://docs.rs/fixed/latest/fixed/)).

These rules go in `crates/sim/clippy.toml` as `disallowed-types` and `disallowed-methods` entries (`std::collections::HashMap`, `HashSet`, `RandomState`, `std::time::Instant`, `SystemTime`, `rand::rngs::StdRng`, `rand::rngs::SmallRng`, `rand::rng`, `rand::random`), each with a `reason`, using `allow-invalid = true` for paths from optional dependencies so clippy does not error when the crate is absent ([Clippy lint configuration](https://doc.rust-lang.org/clippy/lint_configuration.html)). The one documented gotcha is that these lints do not block `cargo build` and that test-only usage slips through unless clippy runs with `--all-targets` ([schneems.com](https://schneems.com/2025/11/19/find-accidental-code-usage-with-a-custom-clippytoml/)). Floats cannot be banned by clippy config; `#![deny(clippy::float_arithmetic)]` at the crate root plus a grep test over `crates/sim/src` is the practical guard (Inference). Add `unsafe_code = "forbid"` at the workspace level; nothing in this sim needs it.

### Hash the serialized state, by subsystem, and bisect

Factorio's debug mode "makes a CRC from the whole map every tick", and at the first divergent tick "the difference is usually very small, often a single variable" ([FFF #47](https://www.factorio.com/blog/post/fff-47)). The desync guide adds the method that makes this usable: hash subsystems separately and find "the subsystem that diverged first", because divergence cascades, and hash each tick's inputs too so simulation bugs can be told from input-delivery bugs ([bugnet.io](https://bugnet.io/blog/how-to-debug-desync-in-deterministic-lockstep-games)). Inference: the simplest correct implementation is serialize-then-hash, `postcard::to_allocvec(&state)` fed to `xxh3_64`, which also doubles as a snapshot-completeness check because anything not in the snapshot is not in the hash. postcard serializes a 367 KB dataset in about 433 µs in the current benchmark ([rust_serialization_benchmark](https://github.com/djkoloski/rust_serialization_benchmark)), so hashing a town-sized state every tick is affordable and every 60 ticks is free. Use `xxhash-rust` 0.8.19 (xxh3, stable algorithm, versions track xxHash releases) ([docs.rs](https://docs.rs/xxhash-rust/latest/xxhash_rust/)) or unseeded `rustc-hash` 2.1.3, never `DefaultHasher`, whose algorithm std reserves the right to change. Keep per-subsystem hashes (`calendar`, `rng`, `queue` sorted by `(tick, seq)`, `villagers`, `objects`) and a combined hash; record `[tick, combined, parts]` every N ticks into the replay file. bevy_ggrs does the same with seahash and an insertion-ordered rollback list ([docs.rs bevy_ggrs](https://docs.rs/bevy_ggrs/)).

### Pathfinding: the maintained crate for the search, a hand-rolled door graph for the hierarchy

`pathfinding` 4.16.0 (2026-09-07, MSRV 1.88, 596k downloads in 90 days) exposes `astar`, `dijkstra` and `bfs` generic over a successors closure, so one crate serves both the door graph and the tile grid with no adapter types; its docs say nothing about which path is returned when several share a cost ([docs.rs astar](https://docs.rs/pathfinding/latest/pathfinding/directed/astar/fn.astar.html)). `hierarchical_pathfinding` has not shipped since 2021 and `bevy_northstar` is Bevy-only ([crates.io](https://crates.io/crates/hierarchical_pathfinding); [docs.rs bevy_northstar](https://docs.rs/bevy_northstar/)). Inference: determinism comes from the caller, so the successors closure yields neighbours in a fixed order (N, E, S, W), nodes are plain `(u16, u16)`, costs are integers with a Manhattan heuristic, and equal-cost paths get a small deterministic tiebreak (cost in units of 10, plus 1 per turn) so they stay visually stable across content edits. The hierarchy the layout design already describes is small enough to write by hand: at content load, BFS from every door to every other door inside each place, build a door graph whose edges are those distances plus a unit crossing edge to the twin door, run Dijkstra over it for the leg sequence, then grid A* inside the current place one leg at a time. The all-pairs door matrix is derived data (`#[serde(skip)]`, rebuilt on load) so it never enters the snapshot or the hash, and it is directly the travel-time matrix text view. A shuffle test over the door declaration order, which `world-layout.md` already asks for, catches the Stardew first-found-route bug class.

### Entities: typed ids over Vecs, not arenas, not ECS

The precedents all point one way. `slotmap`'s free list "isn't preserved across serialization", so running operations, round-tripping and continuing "produces different keys" than running straight through; the issue has been open since July 2023 and the maintainer suggested forking ([slotmap #104](https://github.com/orlp/slotmap/issues/104)). Egregoria removed `hecs` "in favor of simple 'entity lists'" to "get a better grip on determinism and serialization" ([Egregoria #90](https://github.com/uriopass/egregoria/issues/90)), and `hecs` 0.11.2 still cannot implement `Serialize` for `World` directly ([docs.rs hecs::serialize](https://docs.rs/hecs/latest/hecs/serialize/index.html)). `thunderdome` and `generational-arena` have had no release in over three years ([crates.io thunderdome](https://crates.io/crates/thunderdome)). Inference: this sim's villagers and objects are fixed by content, so no runtime allocator is needed at all. Content ids become dense newtypes (`VillagerId(u16)`, `PlaceId(u16)`, `DoorId(u16)`) assigned in sorted string-id order at load, so the same files always produce the same numeric ids and `Vec` order; `typed-index-collections` 3.5.0 gives `TiVec<K, V>` if indexing by newtype is wanted. If dynamic entities ever appear, a `Vec<Option<T>>` with an explicit serialized free list is forty lines and keeps allocator state inside the snapshot. The whole deterministic state is one `#[derive(Serialize, Deserialize)] struct SimState`.

### Serialization, snapshots and content

The original `bincode` is gone: RUSTSEC-2025-0141 (2025-12-16) marks it unmaintained after the team "decided to cease development permanently", and `cargo-audit` flags dependents ([RUSTSEC-2025-0141](https://rustsec.org/advisories/RUSTSEC-2025-0141); [Mozilla bug 2011119](https://bugzilla.mozilla.org/show_bug.cgi?id=2011119)). `postcard` 1.1.3 (2025-07-24) is compact and maintained ([crates.io](https://crates.io/crates/postcard)); `bitcode` 0.6.9 is smaller and faster in the benchmark (128 µs serialize, 327,688 bytes on the same dataset) ([rust_serialization_benchmark](https://github.com/djkoloski/rust_serialization_benchmark)) but postcard's wider adoption (33M downloads in 90 days) is the safer default. Inference: `struct Snapshot { version: u32, protocol_version: u32, content_hash: u64, seed: u64, state: SimState }` in postcard; the replay file is a header plus length-prefixed frames of `Input { tick, event }` and `Hash { tick, combined, parts }`. Since the state at any tick is a pure function of (content, seed, inputs), the input log is the save game and a periodic snapshot is the quick-load accelerator, which is OpenTTD's `commands.log` plus `dmp_cmds` design ([OpenTTD desync.md](https://github.com/OpenTTD/OpenTTD/blob/master/docs/desync.md)). Because postcard is positional, `#[serde(default)]` does not help old snapshots migrate; refuse old versions during early development and emit a JSON dump alongside when a human needs to read one.

For content the decision log allows "RON or JSON with schemas". RON is maintained again (0.10.1 April 2025 through 0.12.2 June 2026) but has no official schema language; the only schema tools are small third-party ones ([crates.io ron](https://crates.io/crates/ron); [docs.rs ron-schema-cli](https://docs.rs/ron-schema-cli/)). `schemars` 1.2.3 emits JSON Schema from the same serde structs, with the caveat that "the exact structure of generated schemas may change between versions", which is "not considered a breaking change" ([docs.rs schemars](https://docs.rs/schemars/latest)). Inference: for an agent-authored project, JSON content plus a committed `schemas/*.json` from schemars (pinned `=1.2.3`) is the lower-friction path: editors and agents validate inline, and a TS tool can reuse the schema through `json-schema-to-zod`. Schema validation covers scalars only, so `content::validate(&Content) -> Result<(), Vec<ContentError>>` runs the referential checks from the `world-layout.md` validator table after deserialization, and every error names the file, id and field (`villagers/mara.json: schedule[2].place "bakery" not found`) because the agent fixes from test output.

### Testing: insta goldens, proptest invariants, nextest isolation

insta 1.49.0's `INSTA_UPDATE` defaults to `auto`, which is "`no` in CI environments, otherwise `new`", and `cargo insta test --unreferenced=reject` fails on stale snapshot files ([insta advanced docs](https://insta.rs/docs/advanced/); [insta CLI docs](https://insta.rs/docs/cli/)). Inference: the policy for an agent-driven repo is that the agent runs `cargo insta test --accept` locally, reads the `*.snap` diff, and commits with a reason; CI runs with `CI=true` and `--unreferenced=reject` so any mismatch fails. File snapshots for ASCII renders and itineraries, inline snapshots for hashes. Golden replays live in `fixtures/replays/` and a test asserts the recorded hash sequence; a behaviour change is then a reviewed diff, which is the regression guard Egregoria recommends ([Egregoria #90](https://github.com/uriopass/egregoria/issues/90)). `proptest` 1.12.0 covers the invariants: two sims from the same seed and input log produce equal hashes; a snapshot at tick t restored into a fresh sim matches the original at t+k (the "incomplete savegame" class); every villager is in bed within X ticks of bedtime; no two villagers share a tile; every step moves to an adjacent walkable tile or crosses a door. `rstest` 0.28.0 supplies the loaded-town fixture, `cargo-nextest` 0.9.149 gives per-test process isolation and a slow-timeout so a runaway loop fails rather than hangs, and `cargo-mutants` 27.1.0 is a cheap check that the determinism tests bite.

### Wasm export: a thin cdylib, no getrandom, measured size

`sim` stays a plain rlib with no wasm dependency; `sim-wasm` is `crate-type = ["cdylib", "rlib"]` over it with `wasm-bindgen = "=0.2.129"`. Keeping `getrandom` out of the graph entirely avoids the `wasm_js` backend and the `--cfg getrandom_backend="wasm_js"` rustflag dance, which getrandom's docs warn "will bloat Cargo.lock on all platforms" ([getrandom docs](https://docs.rs/getrandom/0.3/)); a CI step asserts `cargo tree -p sim-wasm --target wasm32-unknown-unknown | grep -E 'getrandom|ahash|instant|web-time'` is empty, which also guards against `Instant::now()` panicking at runtime on wasm32 (Inference). The release profile is `opt-level = "s"` (measure against `"z"`), `lto = true`, `codegen-units = 1`, `panic = "abort"`, then `wasm-opt -Oz`, which the rustwasm book says saves "roughly 15-20% on code size" ([rustwasm book](https://rustwasm.github.io/docs/book/reference/code-size.html)). The `wasm-opt` crate wrapper is pinned at binaryen 116 from 2024 ([crates.io](https://crates.io/crates/wasm-opt)), so install a current binaryen binary instead. Keep `panic = "abort"` deliberately: wasm-bindgen 0.2.122 made `-Cpanic=unwind` emit exnref exception handling that needs Node 22.22.3+ ([CHANGELOG](https://github.com/wasm-bindgen/wasm-bindgen/blob/main/CHANGELOG.md)), and traps are easier to tell apart from typed errors. Rapier's wasm build is "fully cross-platform deterministic across browsers, OSes, and processors", confirmed by matching snapshot hashes ([rapier determinism](https://rapier.rs/docs/user_guides/rust/determinism/)); with integer-only state the same should hold here, and CI asserts it rather than assumes it.

## Committed ts-rs output and one `just check` keep the boundary honest

The decision log already names the processes (generated types, typed events out, typed inputs in, shared fixtures, pinned toolchains, CI drift checks). The boundary note's contribution is which tools make each one mechanical. For type generation, `ts-rs` 12.0.1 (2026-01-31, MSRV 1.88) writes `bindings/*.ts` when `cargo test` runs, honours the serde attributes that matter (`rename_all`, `tag`, `content`, `untagged`, `skip`, `flatten`, `default`), and renders `Option<T>` as `T | null` ([docs.rs ts-rs](https://docs.rs/ts-rs/latest/ts_rs/)). It has no built-in drift check, but one is not needed: commit the output and run `git diff --exit-code` on the directory (Inference). `tsify` 0.5.8 is the alternative when the same types must appear in wasm-bindgen's own `.d.ts`; it recently deprecated `into_wasm_abi`/`from_wasm_abi` in favour of a `Ts<T>` wrapper because a failed deserialization through `throw_str` "skips destructors and leaks" ([docs.rs tsify](https://docs.rs/crate/tsify/latest)), and the Bitwarden page that most agent training data reflects still shows the old style ([Bitwarden SDK](https://contributing.bitwarden.com/architecture/sdk/web/interoperability)). `typeshare` is alive but on a slow cadence and multi-language oriented; `specta` is still on release candidates (2.0.0-rc.27 as of 2026-10-21) ([crates.io specta](https://crates.io/crates/specta)). The agent-legibility ranking is ts-rs (committed `.ts`, diffable) ahead of schemars JSON ahead of tsify (types live in a gitignored build output). One hard constraint applies to all source-scanning generators: boundary types must not use `#[serde(with)]` or `serialize_with`, because the wire shape cannot be inferred ([docs.rs ts-typegen](https://docs.rs/crate/ts-typegen/1.2.0)).

Encoding splits by purpose. Events that only feed the viewer cross as JS values through `serde-wasm-bindgen` 0.6.5, which the wasm-bindgen project "now officially prefers" over JSON; its defaults turn `BTreeMap` into a JS `Map` and `None` into `undefined`, and `u64` fails outside the safe-integer range, so every boundary call goes through one helper that uses `Serializer::json_compatible()` (missing as `null`, maps as objects) and never bare `to_value` ([docs.rs serde-wasm-bindgen](https://docs.rs/serde-wasm-bindgen/latest/serde_wasm_bindgen/)). That preset matches ts-rs's `T | null` rendering, which is otherwise the most likely silent mismatch (Inference). Snapshots and replays cross as `Vec<u8>` to `Uint8Array` and TypeScript treats them as opaque: no TS decoder for postcard with meaningful adoption exists, and none is needed if TS only stores and passes the bytes back. sandspiel's raw `*const Cell` pointer into linear memory is the classic bulk-state path ([sandspiel lib.rs](https://raw.githubusercontent.com/MaxBittker/sandspiel/master/crate/src/lib.rs)), but the pointer is invalid after any memory growth and nothing in the types says so; a DES emits events, not grids, so this path is not needed (Inference). serde-wasm-bindgen itself has had no release since 2024-02-27 ([crates.io](https://crates.io/crates/serde-wasm-bindgen)), a maintenance risk to note and pin rather than a reason to avoid it.

The API shape is one opaque handle. An exported Rust struct becomes a JS class holding a pointer with a `free()` method ([wasm-bindgen design doc](https://wasm-bindgen.github.io/wasm-bindgen/contributing/design/exporting-rust-struct.html)); Bitwarden's rule is tsify-style records by default and wasm-bindgen objects only for live Rust state ([Bitwarden SDK](https://contributing.bitwarden.com/architecture/sdk/web/interoperability)). Inference: `new Sim(contentBytes, seed)`, `applyInput(input)`, `stepUntil(tick): SimEvent[]`, `snapshot(): Uint8Array`, `load(bytes)`, `hash(): string` (hex, so no bigint crosses), `tick(): number`, `renderPlace(id): string`, `protocolVersion(): number`. Wrap the class in a TS `Sim` with `dispose()` and rely on FinalizationRegistry as a backstop. Errors are a serde `SimError` enum exported through ts-rs and thrown as a JS exception; a TS helper narrows `unknown` to `SimError`. Keep `Tick` as `u32` everywhere (2^32 game-seconds is about 136 game-years, Inference) so no `u64` appears in any boundary struct and `TS_RS_LARGE_INT` never matters. A `PROTOCOL_VERSION` constant is exported from Rust and asserted in TS at init, and it goes into every snapshot and replay header.

Contract tests share a `fixtures/<case>/` directory with `input.json` (seed, content version, scripted inputs), `events.json` and `hash.txt`. The Rust test runs natively and uses `insta::Settings::set_snapshot_path` to point at the fixture; the vitest test loads the wasm and compares the same events and hash; `tsc` type-checks the fixture against the generated `SimEvent` type, so a protocol change fails compilation before it fails a runtime test (Inference). Loading wasm in vitest 5 is easiest from a `--target nodejs` (CommonJS) package, because the default bundler output has a `module` field but no `main`, which stopped Node tooling in at least one project ([sigma-rust #632](https://redirect.github.com/ergoplatform/sigma-rust/issues/632)); build `pkg/` (bundler) and `pkg-node/` (nodejs) from the same `.wasm` with two `wasm-bindgen` invocations. The native-versus-wasm hash comparison on the fixtures is the test that proves the determinism rules; the wasm spec lists NaN bits, relaxed SIMD and shared memory as its only nondeterminism, none of which an integer-only single-threaded module touches ([WebAssembly Nondeterminism.md](https://github.com/WebAssembly/design/blob/main/Nondeterminism.md)).

Pinning is where the boundary most often breaks silently. wasm-bindgen 0.2.128 (2026-09-04) "requires matching `wasm-bindgen` and CLI versions (schema bump)" and 0.2.129 improved the mismatch message ([CHANGELOG](https://github.com/wasm-bindgen/wasm-bindgen/blob/main/CHANGELOG.md)), so pin `wasm-bindgen = "=0.2.129"` and `cargo install wasm-bindgen-cli --version 0.2.129 --locked` in CI; a mismatch is loud, which is the desirable failure. wasm-pack survived the rustwasm sunset (now under the `wasm-bindgen` org, 0.15.0 on 2026-05-15) ([Rust blog](https://blog.rust-lang.org/inside-rust/2025/07/21/sunsetting-the-rustwasm-github-org); [crates.io wasm-pack](https://crates.io/crates/wasm-pack)), but two `wasm-bindgen` command lines in a `justfile` are smaller and more predictable than a tool with 332 open issues (Inference). `rust-toolchain.toml` pins the channel and adds `wasm32-unknown-unknown` to `targets` ([rustup overrides](https://rust-lang.github.io/rustup/overrides.html)); `Swatinem/rust-cache@v2` keys its cache on the toolchain file, `Cargo.lock` and `.cargo/config.toml` and should run after `rustup toolchain install` ([rust-cache](https://github.com/Swatinem/rust-cache)). On the Vite side, `vite-plugin-wasm` 3.6.0 pairs with `vite-plugin-top-level-await` unless `build.target` is `esnext` ([vite-plugin-wasm README](https://unpkg.com/vite-plugin-wasm@3.4.1/README.md)). No first-hand 2025-2026 reports of agents working across Rust/TS wasm boundaries were found; the guardrails below are inferred from the tools' CI modes rather than from post-mortems.

## PWA first, Capacitor for the stores, iOS from a rented Mac

The packaging question has one mature answer for a wasm-plus-TS game. Capacitor 8 (announced 2025-12-08) supports iOS 15+ with Xcode 26 and Android API 24+ with a WebView at Chrome 60 or later, serves the bundle from `capacitor://localhost` on iOS and `https://localhost` on Android, and makes Swift Package Manager the default ([Ionic blog](https://ionic.io/blog/announcing-capacitor-8); [Capacitor iOS docs](https://capacitorjs.com/docs/ios); [Capacitor Android docs](https://capacitorjs.com/docs/android); [Capacitor config docs](https://capacitorjs.com/docs/config)). Its games page is thin and names Phaser as its one example engine ([Capacitor games guide](https://capacitorjs.com/docs/guides/games)), and Phaser's own tutorial covers `viewport-fit=cover`, safe-area padding and DPR sizing but not orientation, audio or performance ([Phaser Capacitor tutorial](https://phaser.io/tutorials/bring-your-phaser-game-to-ios-and-android-with-capacitor)). Tauri 2 mobile is real (v2.10.1, March 2026) but documented for app UIs, and "iOS development requires Xcode and is only available on macOS" there too ([Tauri prerequisites](https://v2.tauri.app/start/prerequisites/)); it buys nothing for a game that is already wasm-in-JS (Inference). React Native and Expo end in a WebView or a partial-WebGL2 `GLView` ([DEV: RN game engine gap](https://dev.to/grzott/the-react-native-game-engine-gap-in-2026-rnge-skia-phaser-in-webview-expo-gl-55hp)), and the Wasmer Swift SDK runs WASIX inside a hidden WKWebView, needs iOS 27+, and is experimental ([RuntimeWire](https://runtimewire.com/article/wasmer-swift-sdk-ios-macos)). Apple requires the iOS 26 SDK for all App Store Connect uploads from 2026-04-28, which is about the build SDK, not the deployment target ([Capgo](https://capgo.app/blog/xcode-26-requirement-for-capacitor-apps/)).

The PWA is the first channel because iOS finally allows it. In iOS 26 "every site can run as a web app" from the Home Screen with no manifest required ([WebKit: Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)); Web Push and badging have existed since 16.4 ([WebKit: Web Push](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados)); Home Screen web apps get Safari's storage quota (up to 60% of disk, versus 15% inside WKWebView) with LRU eviction and no prompt ([WebKit: storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/)). What is still missing: there is no install prompt, `ScreenOrientation.lock` is unsupported on iOS through 26.5 because iPhone has no Fullscreen API ([caniuse](https://caniuse.com/mdn-api_screenorientation_lock); [WebKit bug 257695](https://bugs.webkit.org/show_bug.cgi?id=257695)), and an open WebKit bug says iOS 26 Home Screen web apps "will only work with Web Audio on the first run" ([WebKit bug 291892](https://bugs.webkit.org/show_bug.cgi?id=291892)). Inference: design for both portrait and landscape rather than a lock, create one `AudioContext` lazily on first `pointerdown`, resume it on `visibilitychange`, and never make audio a hard requirement. The same service worker and manifest carry into the Capacitor build unchanged, so PWA-first costs nothing later.

Store policy is not a blocker for a self-contained game. Apple 2.5.2 requires apps to be "self-contained in their bundles" and not "download, install, or execute code which introduces or changes features"; 4.2 rejects apps that are "a repackaged website"; 4.7 governs host apps that serve HTML5 mini-games they did not embed and was tightened in late 2025 ([App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)). Google Play's rule targets apps that "provide a webview of a website without permission from the website owner" ([Google Play spam policy](https://support.google.com/googleplay/android-developer/answer/9899034)). Inference: ship all JS and wasm inside the bundle, never load from `server.url` in production, and a living town with saved state clears the "lasting entertainment value" bar. The practical gates are elsewhere: a Phaser developer who shipped Fuel Field on Capacitor said Google Play's closed-testing requirement for new personal accounts "caught him off guard" ([Phaser: Fuel Field interview](https://phaser.io/news/2026/07/fuel-field-phaser-roguelite-interview)), and both stores prompt or warn above 200 MB ([Google Play size limits](https://support.google.com/googleplay/android-developer/answer/9859372)), a ceiling a pixel-art game with a sub-megabyte wasm module sits far below.

### What headless Linux can and cannot build

Android is fully owned from the container: the SDK and Gradle run on Linux, `ubuntu-latest` x86_64 GitHub runners expose `/dev/kvm` for the emulator and are "2-3 times faster than the macOS ones" ([android-emulator-runner](https://github.com/ReactiveCircus/android-emulator-runner)), and Redroid or the SDK emulator with `-no-accel -gpu swiftshader_indirect` work without KVM, slowly ([Codersera](https://codersera.com/blog/android-emulator-docker-without-kvm/)). iOS cannot be built, signed, simulated or debugged without macOS. Cloud macOS closes the build gap: GitHub Actions macOS at $0.062/min against Linux at $0.006/min ([GitHub billing](https://docs.github.com/en/billing/managing-billing-for-your-products/about-billing-for-github-actions)), Codemagic with 500 free M2 minutes a month then $0.095/min and App Store Connect API-key signing from Linux, though "you will still need a Mac if you need to do any debugging ... on a iOS Simulator or real device" ([Codemagic pricing](https://codemagic.io/pricing/); [Codemagic signing](https://blog.codemagic.io/automatic-code-signing-for-ios-that-doesnt-require-a-mac/)), EAS at $2 per iOS build ([Expo pricing](https://expo.dev/pricing)). Device clouds close the on-device gap: Firebase Test Lab (deprecated, shutting down 2027-09-30) at $5 per physical-device-hour on Blaze with 30 free physical minutes a day ([Firebase Test Lab pricing](https://firebase.google.com/docs/test-lab/usage-quotas-pricing)), AWS Device Farm at $0.17 per device-minute ([Quash](https://quashbugs.com/blog/best-firebase-test-lab-alternatives)), BrowserStack from $175 a month ([BrowserStack pricing](https://www.browserstack.com/pricing?product=app-automate)). Playwright's WebKit is "derived from the latest WebKit main branch sources" and is not Safari; "for the closest-to-Safari experience you should run WebKit on mac" ([Playwright: Browsers](https://playwright.dev/docs/browsers)). Inference: the agent's iOS loop is push, trigger a macOS job, read logs and screenshots, and each iteration costs minutes and cents; design the viewer so that nearly every bug reproduces in Playwright WebKit with `devices['iPhone 15']` or on the Android emulator first.

## WebGL2 and owned context recovery decide the viewer library

Inside the wrappers the renderer target is WebGL2. WebGPU shipped in Safari 26 and is on by default in WKWebView from iOS 26 per an Apple engineer on the forums ([WebKit: Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/); [Apple forums 770862](https://developer.apple.com/forums/thread/770862)), but a later report describes WebContent crashes with WebGPU on an iPhone 15 at 26.4 (single report), Chrome on Android enables it only on Android 12+ with Qualcomm and ARM GPUs ([Chrome WebGPU overview](https://developer.chrome.com/docs/web-platform/webgpu/overview)), Android System WebView status is unconfirmed, and PixiJS has an open issue where the WebGPU-to-WebGL fallback "doesn't occur in some instances" ([pixijs #10906](https://github.com/pixijs/pixijs/issues/10906)). Inference: for a few hundred sprites at integer scale WebGPU brings nothing measurable; keep it behind a flag.

Context loss is the constraint that reorders the library ranking. iOS 17 introduced "WebGL: context lost" after backgrounding, reproduced with Babylon, Three and vanilla WebGL ([WebKit bug 261331](https://bugs.webkit.org/show_bug.cgi?id=261331)), with a PlayCanvas thread confirming it inside WKWebView through 17.2 with no fix ([PlayCanvas forum](https://forum.playcanvas.com/t/webgl-context-lost-in-ios-17-wkwebview/34247)). Phaser 4's renderer article says it "supports context restoration out of the box" and recovers automatically when "a mobile app goes to the background" (vendor claim, April 2026) ([Phaser 4 renderer article](https://phaser.io/news/2026/04/phaser-4-renderer-faster-cleaner-and-built-for-modern-games)). PixiJS v8 has two open issues in this area as of October 2026: a blank scene after context loss during shader compilation ([pixijs #12281](https://github.com/pixijs/pixijs/issues/12281)) and WebGL reclaimed after inactivity with no maintainer answer ([pixijs #11731](https://github.com/pixijs/pixijs/issues/11731)). The WKWebView memory limit "cannot be increased" and "is not a fixed number" ([Apple forums 133449](https://developer.apple.com/forums/thread/133449)). SharedArrayBuffer should be treated as unavailable in the wrapped app: Capacitor could not reliably keep COOP/COEP headers through an internal reload on iOS and the reporter stated Android WebView "does not currently support the COOP header" ([ionic-team/capacitor #6182](https://github.com/ionic-team/capacitor/issues/6182)), so the wasm sim is single-threaded and a Web Worker with `postMessage` is the only portable off-main-thread option, which the message-shaped API above already allows (Inference).

Integer scaling on phones belongs to the viewer, not the library. MDN's recipe is a small canvas scaled with CSS and `image-rendering: pixelated`, and warns that a non-integer `devicePixelRatio` makes "certain pixels ... drawn larger than others" ([MDN: crisp pixel art](https://developer.mozilla.org/en-US/docs/Games/Techniques/Crisp_pixel_art_look)); Phaser's guide says "non-integer scale produces non-integer pixel positions, which causes blurring" ([Phaser 4 Pixel Art Guide](https://cdn.jsdelivr.net/npm/phaser@4.1.0/docs/Phaser%204%20Pixel%20Art%20Guide/Phaser%204%20Pixel%20Art%20Guide.md)). Inference: compute `scale = floor(min(physicalW / gameW, physicalH / gameH))` in device pixels (CSS px times DPR), size the backing store to game size times scale, set the CSS size to backing divided by DPR, and accept letterboxing or edge fill. iPhones have integer DPRs (2, 3); many Androids are fractional (2.625, 2.75), which lands on fractional CSS pixels but keeps the backing store integer-scaled. Do not use any engine's default "resolution = DPR" path. Set `touch-action: none` and `user-select: none` on the canvas; neither Excalibur's nor Phaser's docs spell this out, so the viewer must. Click-to-walk needs only `pointerdown`/`pointerup` on one pointer, which every candidate supports.

| Library | Version | Mobile-relevant strengths | Mobile-relevant risks | Fit for a thin viewer over a Rust sim |
|---|---|---|---|---|
| PixiJS v8 | 8.22.0 (2026-10-01), 265 KB gzip | Renderer, not engine; explicit `resolution`/`roundPixels`/`scaleMode: 'nearest'`; WebGL default, WebGPU and Canvas optional; monthly releases; 25 agent skill files in the package | Context-loss issues open; no first-party tilemap (`@pixi/tilemap` idle since 2025-07) | Best: the viewer owns the loop and the rules, Pixi batches sprites |
| Phaser 4 | 4.2.1 (2026-07-09), 356 KB gzip | Documented automatic context restoration (vendor claim); pixel-art guide; `SpriteGPULayer`; Capacitor tutorial | Owns the loop (a second clock); Canvas renderer deprecated; `roundPixels` only on axis-aligned unscaled objects; v3-era training data stale | Viable alternative if context restoration proves out on WebKit |
| Excalibur | 0.32.0 (2025-12-23), 145 KB gzip | TypeScript-first; W3C Pointer Events; `pixelArt: true`; first-party TileMap | 0.x with 133 alphas in 2026 and "breaking changes will occur"; thin mobile record | Typed, but not stable |
| melonJS | 20.10.1 (2026-10-21) | `scaleRounding: "integer"`; auto fallback across WebGPU/WebGL2/Canvas | API changed at 20.0 so training data is stale; small community | Spike only |
| Raw Canvas 2D | n/a | Zero dependencies | No batching; only 2014-era mobile data (WebGL ~17,500 vs Canvas ~360 objects at 30 FPS) ([WHATWG archive](https://lists.w3.org/Archives/Public/public-whatwg-archive/2014Aug/0038.html)) | Withdrawn, as decided |

Sizes and dates are from `engine-deep-dive.md`, which took them from the npm registry and bundlephobia on 2026-10-23.

Inference on the recommendation: with the sim in Rust, the "robust, highly typed, deterministic" requirement is met where it matters, and the viewer is a presentation layer that reads an event stream, interpolates, and draws. That favours a renderer the project drives over an engine that drives the project. PixiJS v8 as a batched sprite renderer behind the project's own `Viewer` module (frame loop, camera, Y-sort, roof alpha groups via `cacheAsTexture`, integer scaling, input, and a `webglcontextlost`/`webglcontextrestored` handler that rebuilds every texture from the atlas) is the recommendation. Pixi's context-loss issues are the reason the viewer owns recovery rather than a reason to avoid Pixi; the iOS reports say loss will happen under any library. Phaser 4 is the named alternative, chosen if a one-week spike shows that its automatic restoration works in Playwright WebKit and on the Android emulator and that its loop ownership does not fight the sim clock. Excalibur matches Ian's taste on typing and would be the pick if it had a stable 2026 release; it does not.

### Boundary protocol

Direction one, sim to viewer: `stepUntil(tick: number): SimEvent[]`, each event a tagged union (`#[serde(tag = "kind")]`) with `tick: number` and integer payloads, serialized by one `to_js` helper using `Serializer::json_compatible()`. Direction two, viewer to sim: `applyInput(input: PlayerInput)`, a tagged union typed by ts-rs, deserialized by one `from_js` helper. Bytes: `snapshot(): Uint8Array`, `load(bytes)`, `recordInput` into the log; TS never decodes them. Diagnostics: `hash(): string` (hex of the combined xxh3), `hashParts(): string[]`, `renderPlace(id: string): string`, `whereIsEveryone(): string`, `protocolVersion(): number`. Rules: boundary types live in `crates/sim/src/protocol.rs`, derive `Serialize, Deserialize, TS, JsonSchema`, use no `#[serde(with)]`, carry no `u64`, no `usize`, no `HashMap`, no floats; `PROTOCOL_VERSION` bumps on any change and is asserted at `Sim` construction; `packages/protocol/src/generated/**` and `schemas/**` are never hand-edited.

## Conclusion

The three notes converge on a stack that is smaller than the question suggested. The Rust side needs no simulation framework, no ECS and no arena; the maintained crates it does need (`pathfinding`, `postcard`, `rand_pcg`, `xxhash-rust`, `insta`, `proptest`, `ts-rs`, `wasm-bindgen`) are each doing one job, and the determinism rules become clippy configuration plus two tests (same seed, same hashes; snapshot, restore, same hashes) that fail loudly. The boundary is tight when its artifacts are text in the repository: committed generated types, committed schemas, committed fixtures, and a CI step that diffs them. What the Rust decision changed about the viewer is that the typed, deterministic part of the system no longer depends on the renderer library, which turns the PixiJS question from "is it robust enough to build on" into "does it batch sprites and let the viewer own scaling, the loop and context recovery", and the answer to the second question is yes.

The mobile research changes the order of work rather than the design. Nothing on iOS or Android touches the Rust module; what the phones add is a list of things the viewer must assume are absent (threads, WebGPU, orientation lock, reliable audio, a persistent WebGL context) and a build pipeline where iOS costs money and minutes per iteration. Designing the viewer so that its bugs reproduce in Playwright WebKit and the Android emulator first is the decision that keeps an agent in a Linux container productive on a product that will probably ship to iPhones.
